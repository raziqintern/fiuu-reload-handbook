Value vs. Reference Types

A new track: the "why did my code do that" theory every C#/VB.NET developer eventually needs, once syntax alone stops explaining the behavior you're seeing.

How to use this track

Each lesson explains one mental model, shows it happening in both languages, and connects it to a real, cited pattern elsewhere on this site or in reload itself. These are the topics that separate "I can write C#" from "I understand why C# behaves the way it does."

The core distinction

KindExamplesWhat assignment/passing does
Value typeint, double, bool, struct, DateTimeCopies the actual value. The new variable is fully independent.
Reference typeclass, arrays, string*, List<T>Copies the reference (a pointer to the object). Both variables point at the same object.

* string is technically a reference type, but it's immutable — every operation that looks like it "changes" a string actually creates a new one, so it behaves like a value type in practice. This is worth knowing so it doesn't confuse the mental model below.

Example: watch the difference happen

public class Terminal
{
    public string Id;
}

static void Main()
{
    // Value type: b gets a COPY of a
    int a = 5;
    int b = a;
    b = 10;
    Console.WriteLine("a = " + a + ", b = " + b);

    // Reference type: t1 and t2 point to the SAME object
    Terminal t1 = new Terminal { Id = "TNG-0042" };
    Terminal t2 = t1;
    t2.Id = "TNG-9999";
    Console.WriteLine("t1.Id = " + t1.Id + ", t2.Id = " + t2.Id);
}
a = 5, b = 10
t1.Id = TNG-9999, t2.Id = TNG-9999
Public Class Terminal
    Public Id As String
End Class

Sub Main()
    ' Value type: b gets a COPY of a
    Dim a As Integer = 5
    Dim b As Integer = a
    b = 10
    Console.WriteLine("a = " & a & ", b = " & b)

    ' Reference type: t1 and t2 point to the SAME object
    Dim t1 As New Terminal()
    t1.Id = "TNG-0042"
    Dim t2 As Terminal = t1
    t2.Id = "TNG-9999"
    Console.WriteLine("t1.Id = " & t1.Id & ", t2.Id = " & t2.Id)
End Sub
a = 5, b = 10
t1.Id = TNG-9999, t2.Id = TNG-9999

Changing b never touches a — they're independent copies. But changing t2.Id also changes what t1.Id reports, because t1 and t2 are two labels pointing at the exact same Terminal object in memory. This is the single most common source of "I didn't even touch that variable, why did it change?" bugs in object-oriented code.

Where they actually live: stack vs. heap

As a working simplification: local value-type variables live on the stack — a fast, function-call-scoped region that's automatically reclaimed the instant the method returns. Objects created with new (reference types) live on the heap — a larger, longer-lived region managed by the garbage collector (see Garbage Collection & Object Lifetime), which can outlive the method that created them. A local variable holding a reference type is itself just a small pointer on the stack, pointing into the heap.

This is a simplification, not the full CLR spec Value types nested inside a class (a field of type int on a heap-allocated object) actually live on the heap too, as part of that object. The "value types = stack, reference types = heap" rule of thumb is the right first mental model, not a universal law — don't repeat it as an absolute in a technical interview without this caveat.

Best practice

Be deliberate when passing a reference-type object into a method that might mutate it — the caller's object changes too, which is sometimes exactly what you want (mutating a shared cache) and sometimes a bug (an unintended side effect on data the caller still needs unchanged).

Check your understanding

A method receives a Terminal object as a parameter and changes one of its properties. What happens to the caller's original object after the method returns?

  • Nothing — the method only had a copy, so the original is untouched.
  • The caller's object is changed too — the method was working on the same object, not a copy.
  • It depends on whether the method has explicit permission to mutate it.
