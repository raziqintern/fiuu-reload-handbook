Forms & Inputs

Reload lives and dies by forms: top-up amount, terminal login, merchant search. Knowing the anatomy of a form is what lets you tell "the form posted wrong data" from "the server rejected valid data".

Anatomy of a form

<!doctype html>
<html>
<body>
  <form>
    <label for="amount">Reload amount (RM)</label><br>
    <input type="number" id="amount" name="amount" min="5" max="500" value="10"><br><br>

    <label for="method">Payment method</label><br>
    <select id="method" name="method">
      <option value="tng">Touch 'n Go</option>
      <option value="card">Credit Card</option>
    </select><br><br>

    <input type="checkbox" id="confirm" name="confirm">
    <label for="confirm">I confirm this reload</label><br><br>

    <button type="submit">Reload Now</button>
  </form>
</body>
</html>

Every field that matters has three things: a name (the key the server receives), a value (what gets sent), and usually a matching <label> linked by for/id (accessibility + click target).

Input typeUsed for
textFree text — names, references.
numberNumeric input — the browser enforces min/max client-side (never trust this alone — the server must validate too).
checkboxBoolean on/off, e.g. a confirmation.
select/optionA fixed dropdown of choices, e.g. payment method.
Official documentation MDN's <input type="checkbox"> reference states the rule for an unchecked box precisely: "If a checkbox is unchecked when its form is submitted, neither the name nor the value is submitted to the server." Not sent as empty or false — not sent at all. This is exactly why "the field is just missing" (not "the field is blank") is the correct way to describe this symptom in a bug report.
Real, verified: this WebForms grid does the same thing underneath a server control <asp:CheckBox runat="server" Checked='<%# Eval("Checked") %>' ID="CheckBoxAllSupplier" /> is a WebForms server control, not plain HTML — but it still compiles down to an ordinary <input type="checkbox"> at render time, so the exact same submission rule applies underneath the asp: wrapper.

Why this matters for debugging When a "reload failed" ticket comes in, one of the first things to check is: did the form actually send the field the server expected? A mismatched name attribute, or a field disabled by JavaScript (disabled fields aren't submitted at all), is a classic silent-failure cause you can spot in seconds with DevTools' Network tab, before touching any server code.

Best practice

  • Always pair an input with a real <label>, linked by matching for/id. It's what makes the label clickable to focus the field, and it's what a screen reader announces when the field gets focus.
  • Set sensible HTML-level constraints (min, max, required) as a first line of defense for user experience — but never as the only validation. They're trivially bypassed by anyone calling the API directly.
  • When debugging a "missing field," check whether it was ever submitted at all before assuming a server-side bug. An unchecked checkbox, a disabled input, or a field outside the <form> tag are all real reasons a field never reaches the server.

Better ways

Official documentation MDN's Constraint validation guide is direct about why client-side checks alone are never enough: "HTML Constraint validation doesn't remove the need for validation on the server side... invalid [requests] can still be sent in many ways: By modifying HTML via the browser's developer tools. By hand-crafting an HTTP request without using the form... Therefore, you should always validate form data on the server side, consistent with what is done on the client side."

Client-side constraints improve the experience for a well-behaved browser user; they do nothing for a malicious or buggy API caller who skips the form entirely. The actual security/correctness boundary has to be server-side — exactly why reload validates again at the C# layer (C# Fundamentals → Methods & Parameters's ValidateReload example) regardless of what the form already checked.

Check your understanding

A checkbox field is missing from the data the server receives when a form is submitted. What's the most likely HTML-side cause?

  • The checkbox was left unchecked — unchecked checkboxes aren't submitted at all.
  • The checkbox's id doesn't match its name.
  • The checkbox was placed after the submit button in the HTML.

A reload form sets min="5" and max="500" on the amount field. Why can't the server trust that every submitted amount actually falls in that range?

  • Because min/max aren't real HTML attributes — they don't do anything.
  • Because HTML constraints only run in a well-behaved browser — a hand-crafted HTTP request, or a request built after editing the page in DevTools, skips them entirely.
  • Because min/max only work on type="text", not type="number".
