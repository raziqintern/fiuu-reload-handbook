Grounded in 3,620 real review comments read across the 24 highest-discussion merge requests in reload's history. Every rule below is backed by an actual, quoted comment — not a generic best-practices list. Full source: gitlab-analysis/reload-mr-review-checklist.md.

Two reviewers, two different jobs

A human lead reviewer (1,398 of the sampled comments) catches style, business-logic, and "did you check the spec" issues. An AI review bot, added mid-2025 (1,090 of the sampled comments), catches mechanical correctness issues — type mismatches, null-dereference risks, stale references, typos. Knowing which kind of issue you're looking at tells you which kind of review is likely to catch it before it ships.

Judging whether a fix actually matches the reported bug

Official documentation Google's published Engineering Practices — What to Look For in a Code Review names this as the reviewer's first and most important question, ahead of style: "Does this CL do what the developer intended? Is what the developer intended good for the users of this code?" The reload MR history quoted throughout this lesson is a real, local instance of exactly that question — every "does this actually fix the issue" judgment call below is applying this same general reviewer responsibility, not a codebase-specific quirk.

Reviewing an existing MR against its linked issue is a different skill from spotting a style nit — it's about whether the diff really addresses the exact reported symptom, not a paraphrase of the MR title. Working from MR !1906 against issue #2461 (a search filter throwing Object variable or With block variable not set for every status except "All"/"Approved"): the fix wraps the crashing line in a null guard, which directly neutralizes the exact file:line from the issue's own stack trace — a small diff, and a complete fix, not a partial one just because it's short.

Three verdicts, not two Grade a fix against its issue as fixes it completely (the exact reported symptom and repro steps now behave correctly), partially fixes it (say precisely what part of the original symptom still reproduces), or doesn't address it (say what the diff does instead). Don't default to "partial" just because the diff is small, or because reading the surrounding code turned up other things worth mentioning — a narrowly-scoped diff that exactly matches the reported symptom is a complete fix; confusing "narrowly scoped" with "incomplete" is the most common way to get this judgment wrong.

Reading the file around the diff (not just the diff hunk) in that same review turned up a second call site with the identical unguarded pattern, reachable only via grid paging/sorting — not the button the issue reported. That's a real finding, but it belongs in its own section, explicitly labelled as out of scope for this MR and worth its own ticket — not folded into the verdict on whether this MR fixes issue #2461, and not treated as evidence the MR is deficient.

Best practice

  • Run through the checklist in §C of the real source doc as a self-review pass before requesting review, not after receiving comments about them. Datatype prefixes, blank-line discipline, no double-logging, merchant timestamp, keyed log lines, bounded queries, dead-code removal, right-fit models on the human side; type-widening call sites, null checks, stale parameter references, duplicated logic, renamed-variable leftovers, secrets handling on the automated side.
  • When judging whether an MR fixes its linked issue, grade against the exact reported symptom, not the diff's size or your own broader read of the surrounding code. A small, narrowly-scoped diff that neutralizes the exact stack-trace line is a complete fix; unrelated findings from reading nearby code belong in their own out-of-scope note, not folded into that verdict.
