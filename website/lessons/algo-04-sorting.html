Sorting: How & Why

You'll essentially never hand-write a sort algorithm in real code — but understanding how one works is what lets you predict and debug the built-in one's behavior.

Example: the built-in sort, and why C#/VB.NET dodge a common trap

int[] nums = { 10, 1, 21, 2 };
Array.Sort(nums);
Console.WriteLine(string.Join(", ", nums));
1, 2, 10, 21
Dim nums() As Integer = {10, 1, 21, 2}
Array.Sort(nums)
Console.WriteLine(String.Join(", ", nums))
1, 2, 10, 21
Official documentation MDN's Array.prototype.sort() reference names the JS trap precisely: "If compareFn is not supplied, all non-undefined array elements are sorted by converting them to strings and comparing strings in UTF-16 code unit order." Its own example: [1, 30, 4, 21, 100000].sort() produces [1, 100000, 21, 30, 4] — sorted as text, not as numbers. Microsoft's Array.Sort reference confirms the C# side has no equivalent default-comparison ambiguity to fall into in the first place — it documents the actual algorithm used ("introspective sort (introsort)... If the partition size is less than or equal to 16 elements, it uses an insertion sort algorithm... Otherwise, it uses a Quicksort algorithm") and its complexity ("This method is an O(n log n) operation"), both defined in terms of the array's actual, statically-known element type.
A trap this codebase's languages don't have JavaScript's default .sort() converts numbers to text and compares them alphabetically — [10, 1, 21, 2].sort() gives the surprising [1, 10, 2, 21] unless you pass an explicit numeric comparator. C#/VB.NET don't have this trap: int[] is statically typed, so Array.Sort only ever compares actual integers numerically. The equivalent C#/VB.NET failure mode is different — sorting a custom class without implementing IComparable or supplying a comparer is a compile error, not a silent wrong answer.
What if not: two equal elements — does Array.Sort keep their original relative order? Microsoft's own reference calls this out specifically: "This implementation performs an unstable sort; that is, if two elements are equal, their order might not be preserved. In contrast, a stable sort preserves the order of elements that are equal." Sorting a list of transactions by amount, where several transactions happen to share the exact same amount, is not guaranteed to leave those tied transactions in their original order — Array.Sort doesn't promise that. If preserving original order among ties actually matters, Enumerable.OrderBy (LINQ) is the one to reach for instead — Microsoft's own reference states plainly: "This method performs a stable sort; that is, if the keys of two elements are equal, the order of the elements is preserved."

How a sort actually works: bubble sort, the simplest one

Bubble sort repeatedly walks through the list, swapping any two adjacent elements that are out of order, until a full pass makes no swaps. It's O(n²) — genuinely slow for large lists — but it's the clearest way to see the mechanism.

static int[] BubbleSort(int[] arr)
{
    int[] a = (int[])arr.Clone(); // copy — don't mutate the caller's array
    for (int i = 0; i < a.Length; i++)
    {
        for (int j = 0; j < a.Length - i - 1; j++)
        {
            if (a[j] > a[j + 1])
            {
                int temp = a[j];
                a[j] = a[j + 1];
                a[j + 1] = temp;
            }
        }
    }
    return a;
}

static void Main()
{
    int[] result = BubbleSort(new int[] { 5, 3, 8, 1, 9, 2 });
    Console.WriteLine(string.Join(", ", result));
}
1, 2, 3, 5, 8, 9
Function BubbleSort(arr() As Integer) As Integer()
    Dim a() As Integer = CType(arr.Clone(), Integer()) ' copy — don't mutate the caller's array
    For i As Integer = 0 To a.Length - 1
        For j As Integer = 0 To a.Length - i - 2
            If a(j) > a(j + 1) Then
                Dim temp As Integer = a(j)
                a(j) = a(j + 1)
                a(j + 1) = temp
            End If
        Next
    Next
    Return a
End Function

Sub Main()
    Dim result() As Integer = BubbleSort({5, 3, 8, 1, 9, 2})
    Console.WriteLine(String.Join(", ", result))
End Sub
1, 2, 3, 5, 8, 9

Why you'll never actually use bubble sort in real code Real language built-ins (Array.Sort, C#'s List<T>.Sort) use well-tested algorithms achieving O(n log n) — dramatically faster than bubble sort's O(n²) on any list bigger than a handful of items. The value of learning bubble sort isn't to use it — it's understanding "sorting compares and rearranges elements" well enough to reason about correctness when you use the built-in.

Best practice

  • Always use Array.Sort/List<T>.Sort/LINQ's .OrderBy(...) for real code. Hand-rolling a sort in production is almost always a sign something else went wrong (usually: not knowing the built-in existed).
  • Reach for Enumerable.OrderBy specifically when the original relative order of tied elements matters. Array.Sort/List<T>.Sort are documented as unstable; LINQ's OrderBy is documented as stable.

Check your understanding

Why does Array.Sort on an int[] never need an explicit comparator to sort correctly, unlike JavaScript's default .sort()?

  • The array's element type is known and fixed at compile time, so the default comparison for that type (numeric, for integers) is always well-defined.
  • C# secretly requires you to always pass a comparator; the example above is a special case.
  • Array.Sort is simply a newer, unrelated algorithm to JavaScript's sort.

A list of transactions is sorted by amount using Array.Sort. Two transactions happen to have the exact same amount. What does Microsoft's own documentation say about their relative order after sorting?

  • It's not guaranteed — Array.Sort is documented as an unstable sort, so tied elements' original order might not survive.
  • It's guaranteed to be preserved — Array.Sort is a stable sort.
  • It throws an exception, since Array.Sort can't handle duplicate values.
