Fiuu Code Conventions

Naming

Fiuu has no documented coding standard for this codebase. Everything in this track is reverse-engineered straight from real code — with file:line citations — not idealized guidelines. Full source: conventions/naming.md.

This track covers both languages reload is actually written in The shared class-library and most newer components are C#. The BackOffice WebForms UI — where most of the worked bugs in the Debugging Reload track happen — is VB.NET (.aspx.vb code-behind). Most lessons here use C# examples since that's the shared-library convention source; CSV Export Escaping is VB.NET specifically, pulled straight from BackOffice code. If you're heading into WebForms work, also see the VB.NET Fundamentals track.

What's rock-solid: PascalCase types, I-prefixed interfaces, layer suffixes

public class TerminalService : ITerminalService
{
    private TerminalProvider _provider;
    public bool Login(Auth auth) { ... }

reload/class-library/Reloads/TNG/Services/TerminalService.cs:8

Standard .NET PascalCase for types, public methods, and properties holds with zero exceptions across everything sampled. Interfaces are always I-prefixed. Class-name suffixes double as an architecture signal: *Provider (data access), *Service (business logic), *Model/plain noun (DTOs), *Helper (static utility bag), *Validator, *Exception.

What isn't: Hungarian notation on locals, module by module

This is the single biggest naming inconsistency in the codebase. Some modules prefix local variables/parameters the old-school way (s = string, i/l = int/long, dt = DateTime, b = bool):

string sLogFilePath = GetAvailableFileName(string.Format("{0}_{1}", sAppName, DateTime.Now.ToString("yyyyMMdd")));

public bool UpdateGameSalesTransactionStatus(string sReferenceId, string sStatus, string sReceiptNo, DateTime? dtTransactionDateTime)

Other modules use plain idiomatic C# with no prefixes for the same kind of code:

public TerminalSummary GetTerminalSummaryByTransNo(string transNo)

reload/class-library/Reloads/TNG/Providers/TerminalProvider.cs:60

This tracks the author, not the layer TNG and InComm/Secure are architecturally identical peers — one uses Hungarian notation heavily, the other doesn't at all. Don't assume you can predict which style a file uses from its module or age; check the file you're actually editing and match its existing style, not a house rule that doesn't exist.

The M-prefix: a genuine cross-cutting convention

Any column that's a foreign key into a lookup/master/status table is prefixed M (for "Master"), in both C# models and SQL, regardless of module:

// the DB-facing param name in the Provider is M-prefixed:
param.Add("@MTransTypeId", DbType.Int32, activity.TransType);
param.Add("@MTransStatusId", DbType.Int32, activity.TransStatus);

reload/class-library/Reloads/TNG/Providers/TerminalProvider.cs:20-21

Seen across unrelated modules (MServiceTypeId, MSourceTypeId, MDeliveryStatusId, MRequestStageId) — this one really is a house convention, not module-local. Note the model property itself sometimes drops the M and exposes a friendly enum name (TransStatus) while the raw DB parameter keeps MTransStatusId — the mapping is done by hand, field by field, in a Get*Model(DataRow dr) method (more on this in Data Access).

Best practice — for working inside this specific codebase

  • Match the file, not a textbook rule. If the file you're editing uses Hungarian prefixes, use them for your new variables too; if it doesn't, don't introduce them. Consistency within a file matters more here than consistency with an external standard.
  • Always apply the M-prefix to a new foreign-key-into-a-lookup-table column or parameter — it's the one naming rule that's genuinely universal across this codebase, not module-local.

Better ways

If you're ever asked to clean up naming in a file you're already touching for another reason, do it in a separate, clearly-labeled commit/MR from the actual functional change — mixing a rename with real logic changes makes the diff much harder for a reviewer to verify correctness on.

Check your understanding

You're editing a file in the TNG module and notice every existing local variable uses plain idiomatic names (transNo, not sTransNo). You need to add a new string parameter. What should you name it?

  • sNewParam — Hungarian notation is the safe default everywhere in reload.
  • Match the file's existing style — a plain name with no prefix, since that's what this file already does.
  • Run the project's naming linter and follow whatever it suggests.

You see a new column MPaymentTypeId in a code review. What does the M prefix tell you, based on this codebase's actual convention?

  • The column is mutable/nullable.
  • It's a foreign key into a lookup/master/status table.
  • The column belongs to a specific module named starting with M.
