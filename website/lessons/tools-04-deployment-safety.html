Deploying Safely to a Shared Server

A real BackOffice release walkthrough — checking out a release branch, deploying to UAT, and the runbook steps a manual deploy to a shared Windows server actually involves. Every one of these is a real, easy-to-make mistake, not a hypothetical one.

The task, as it was actually given

A typical instruction for this kind of release looks like: check out the release branch, deploy BackOffice to the UAT server, zip the release with a dated name, and add a tester to the UAT merge request. Each of those is a separate tool/step — GitHub Desktop only covers the branch checkout; the rest is manual server work, file zipping, and GitLab, done outside any single tool.

Step 1 — strip build-time config before copying anything

Your build's config is not the server's config Publishing/building the app locally produces an output folder whose config files (Web.config, and appsettings.json for newer .NET apps) contain whatever settings your build environment resolved — a different database, different endpoints, a different mail server than the live target. The live server already has its own correct config for that specific environment. Removing .config files (and appsettings.json, where applicable) from the release output before copying it anywhere means the deploy physically cannot clobber the server's real settings, even by accident.

Step 2 — confirm which server, every time

Different apps in this system live on different servers (BackOffice, Terminal API, API Portal, Terminal Server, Scheduler each have their own instance) — there's no single box a deploy always targets. Before touching anything, confirm which server this specific app/environment combination actually maps to, rather than assuming it's the same one as last time.

A real near-miss: a connection literally named "-prod" Mid-deploy, the active RDP connection in use was named rmsq-sg-backoffice-ec2-prod — while the task was to deploy to UAT, and a separately-named RMSQ-pipeline-uat connection existed right next to it in the same connection list. Two explanations were both plausible: either the wrong connection had genuinely been grabbed, or the team's internal naming just labels the QA group's primary node with "-prod" for unrelated reasons. Either way, the right move is the same — stop and confirm which server this actually is before backing up, uploading, or overwriting anything on it, rather than trusting that a connection's position in a list or its similarity to a past deploy means it's the right target.

Step 3 — back up before you touch anything

Copy the current live files into a dated backup folder (e.g. C:\00-Backup\<date>\) before any new files are written. This is the rollback point — if the new release breaks something, you restore from here instead of trying to reconstruct what was previously live from memory or source control alone (a manually-deployed server's exact live state isn't guaranteed to match any single commit).

Step 4 — stage before you promote

Upload the new release into a separate, dated staging folder (e.g. C:\00-Updates\<date>\) — not the live application path directly. This lets you confirm the files actually transferred correctly (right contents, no partial copy) before they touch anything a real user or terminal is currently hitting. Only once that's confirmed do you copy from staging into the live path, overwriting the previous version.

Official documentation — the same principle, at platform scale This manual copy-to-a-staging-folder-first discipline is a smaller-scale version of a pattern Microsoft's own Azure App Service deployment slots reference builds directly into the platform: "You can validate app changes before you swap the slot into production." Azure's version automates the swap and warm-up; this codebase's manual server deploy achieves the same underlying goal — a new release exists somewhere real before it touches live traffic — with a dated folder and a deliberate copy step instead of a platform feature. The principle doesn't change just because the mechanism is manual.

The generalizable lesson

The whole sequence is one repeatable shape: strip anything environment-specific from your release → confirm the target → back up current → stage the new version → promote staging to live. Every step exists to make a mistake at that step non-destructive — a wrong config gets stripped before it can be copied, a wrong server gets caught before it's touched, a bad release gets caught in staging before it's live, and a live break is recoverable from the backup. None of these steps are unique to this codebase; they apply to any manual deploy onto a shared, stateful server.

Best practice

  • Never assume a remote connection or environment name matches the task just because it's the one you were already using, or the one that looks similar to what you used last time. Read the actual label before you act on a shared server.
  • If a deploy runbook doesn't already separate "stage" from "promote to live" as two distinct steps, treat that as a gap worth raising, not something to work around by being extra careful during a single combined step.

Check your understanding

You're about to RDP into a server to deploy a UAT release, and the connection you have open is named rmsq-sg-backoffice-ec2-prod. What should you do?

  • Proceed — connection names are just labels and don't necessarily reflect the actual environment.
  • Stop and confirm with whoever assigned the task (or the app-to-server reference) which server this actually is before doing anything else.
  • Delete the connection and create a new one to avoid confusion.

Why remove .config/appsettings.json files from a release build before copying it to a live server, rather than just being careful not to overwrite the wrong values?

  • It makes it structurally impossible for the copy to overwrite the server's real settings, instead of depending on the deployer not making a manual mistake every time.
  • It's required for the application to run at all after deployment.
  • It reduces the size of the release zip for faster upload.
