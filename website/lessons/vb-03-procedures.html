VB.NET Fundamentals

Procedures: Sub, Function, Optional & ByRef

VB.NET splits what C# calls a "method" into two explicit keywords based on whether it returns a value, and has its own real parameter-passing idioms — Optional defaults and explicit Overloads — that don't map onto a single C# keyword.

Sub vs. Function

KeywordEquivalent in C#
SubA method returning void — does something, hands nothing back.
FunctionA method with a real return type — must end with Return value.
Function CalculateFee(amount As Double) As Double
    Return amount * 0.02
End Function

Sub Main()
    Dim fee As Double = CalculateFee(100)
    Console.WriteLine(fee)
End Sub

Access modifiers — six levels, not just Public/Private

Every procedure declaration so far has quietly included an access modifier (Public, Private) without stopping to name what it does. The underlying question every one of them answers is the same: "what code, from where, is allowed to see and call this?" — and VB.NET has six distinct answers, not two.

Official documentation Microsoft's own Access Levels reference defines all six precisely:
  • Public: "can be accessed from code anywhere in the same project, from other projects that reference the project, and from any assembly built from the project" — unrestricted.
  • Private: "can be accessed only from within the same module, class, or structure" — the tightest restriction.
  • Protected: "can be accessed only from within the same class, or from a class derived from this class" — visible to subclasses, invisible to unrelated code, even in the same file.
  • Friend: "can be accessed from within the same assembly, but not from outside the assembly" — VB's equivalent of C#'s internal.
  • Protected Friend: "can be accessed either from derived classes or from within the same assembly, or both" — the union of the two, not their intersection.
  • Private Protected (VB 15.5+): "can be accessed only from within the same class, as well as from derived classes found in the same assembly" — narrower than Protected Friend: it requires both derived-class and same-assembly, not either alone.

All four in real, verified use in the same one file — a shared base class every restricted BackOffice page inherits from:

Public MustInherit Class RestrictedPage
    Inherits System.Web.UI.Page

    Protected bIsGlobalApplications As Boolean
    ...
    Protected Function FindControlRecursive(id As String) As Control
    Private Function FindControlRecursiveInternal(...) As Control

    Public Class RestrictedPageEventArgs
        Friend Sub New(...)
        Friend Property FunctionId As Integer
    End Class
End Class

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/RestrictedPage.vb:11-221 (line numbers approximate across the excerpted members)

Reading the access level tells you who this member is actually for, before you read its body RestrictedPage itself is Public — every page in BackOffice needs to inherit from it, including pages in effect from other projects that reference this one. bIsGlobalApplications and FindControlRecursive are Protected — meant for pages that inherit from RestrictedPage, not for arbitrary outside code, which is exactly the relationship a derived .aspx.vb page has with its base class. FindControlRecursiveInternal is Private — an implementation detail of FindControlRecursive itself, not something even a derived page should call directly. The nested RestrictedPageEventArgs class is Public, but its own members are Friend — usable throughout this assembly, but not exposed to a different project that merely references this one. Four modifiers, four different real audiences, all visible in one file without reading a single method body.
Protected Friend is a union, not an intersection — an easy misreading It's natural to read Protected Friend as "must be both a derived class and in the same assembly" — that's backwards. Per the official definition above, it's satisfied by either condition alone: a derived class in a completely different assembly can access it, and so can unrelated code in the same assembly that isn't derived from anything. Private Protected is the one that actually requires both conditions together — it's the narrower combination, despite reading like it should be the more permissive one from the word order alone. Don't guess from the words; check which one is the union and which is the intersection.

Optional parameters — a default value, right in the signature

Real, verified examples from BackOffice — this pattern is common here, not a rarity:

Public Sub ShowConfirmMessage(ByVal message As String, Optional id As String = "", Optional extField As String = "")
Private Sub LoadWalletType(Optional dealer As IDealer = Nothing)
Private Function GetCSVContents(stockReinstateList As List(Of Reinstate), stockProvisionList As List(Of IStockProvision), Optional iStartIndex As Integer = 0, Optional iEndIndex As Integer = 0) As String

reload/web/DEV/NET/Applications/BackOffice/Web/UserControls/MessageBox.vb:273; .../WebForms/DealerEdit.aspx.vb:1902; .../WebForms/ReportStockAllocation.aspx.vb:277

Official documentation Microsoft's Optional Parameters guide states the grammar rules directly: "Every optional parameter in the procedure definition must specify a default value... Every parameter following an optional parameter in the procedure definition must also be optional." There's no way to mark a parameter optional without also giving it a fallback, and no way to follow an optional parameter with a required one — both are compile errors, not conventions.

A caller can omit any trailing optional argument and the default fills in automatically. What if you need to know whether the caller actually supplied the value, versus silently got the default? The same guide is explicit that VB.NET cannot tell you this directly: "A procedure cannot detect at run time whether a given argument has been omitted or the calling code has explicitly supplied the default value." Its documented workaround is a sentinel default unlikely to occur naturally — the guide's own example defaults an office parameter to the string "QJZ" specifically so the body can check If office = "QJZ" Then and treat that as "not supplied."

When to reach for Optional vs. a genuine method overload Optional parameters are the right tool when omitting an argument means "use this one sensible default" — id defaulting to an empty string, a start index defaulting to 0. Reach for Overloads instead (below) when the different call shapes represent genuinely different behavior, not just a default value for the same behavior — e.g. one overload that looks up a record by ID vs. one that takes the record object directly, rather than the same lookup with a parameter defaulted.

ByRef — the same keyword you'd ask about in code review

ByRef passes a variable by reference instead of by value — the callee can reassign it and the caller sees the new value after the call returns. It's VB's version of C#'s ref/out, and it's the historical VB default before VB.NET made ByVal the default (unlike VB6, where ByRef was implicit if you wrote nothing):

Official documentation Microsoft's Passing Arguments by Value and by Reference guide confirms the default explicitly — "The default in Visual Basic is to pass arguments by value" — and states the actual decision rule as one of intent, not habit: "If the procedure has a genuine need to change the underlying element in the calling code, declare the corresponding parameter ByRef... The advantage of passing an argument ByVal is that it protects a variable from being changed by the procedure."

Two versions of the same idea, differing only in the parameter modifier — proving the effect is entirely about that one keyword, not about Integer specifically:

Sub Increment(ByRef x As Integer)
    x = x + 1
End Sub

Dim n As Integer = 5
Increment(n)
Console.WriteLine(n)
6 — the caller's own variable was mutated by the call.
Sub Increment(ByVal x As Integer)
    x = x + 1
End Sub

Dim n As Integer = 5
Increment(n)
Console.WriteLine(n)
5 — ByVal copies the value in; the reassignment inside the Sub
only changes the local copy, and the caller never sees it.

The main real use is a "hand back more than one value" pattern — a Function returns one value directly, but a Sub (or a Function that also needs a second output) can use one or more ByRef parameters to hand back additional results. Prefer a genuine Function return value when there's only one thing to hand back — a ByRef parameter existing purely to fake a return value on a Sub is a sign it should be a Function instead.

ByRef on a reference type doesn't mean what it looks like it means ByRef vs ByVal on a String or object parameter is a genuinely separate question from mutating the object's own contents — with ByVal obj As SomeClass, the caller's reference is copied, but it still points at the same object, so calling a method that mutates that object's internal state (e.g. setting one of its properties) is still visible to the caller. What ByVal actually protects here is only the caller's variable being reassigned to point at a different object entirely — ByRef is needed only if the callee should be able to make the caller's variable reference a new object.

Overloads — plain same-class overloading doesn't need it; shadowing a base member does

It's tempting to assume VB.NET requires an explicit keyword everywhere C# infers overloading automatically — it doesn't, for the ordinary case. Real, verified same-class overloading with no Overloads keyword anywhere:

Private Function GetDataRowIndex(ByVal sender As Object,
                                 ByVal e As System.Web.UI.WebControls.GridViewUpdateEventArgs) As Integer
    Dim grv As GridView = CType(sender, GridView)
    Return e.RowIndex + (grv.PageIndex * grv.PageSize)
End Function

Private Function GetDataRowIndex(ByVal sender As Object,
                             ByVal e As System.Web.UI.WebControls.GridViewDeleteEventArgs) As Integer
    Dim grv As GridView = CType(sender, GridView)
    Return e.RowIndex + (grv.PageIndex * grv.PageSize)
End Function

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/Supplier.aspx.vb:307-321 (same pattern repeats in SupplierEdit.aspx.vb)

Official documentation Microsoft's Overloads modifier reference is explicit about this: "You do not have to use the Overloads modifier when you are defining multiple overloaded properties or procedures in the same class. However, if you use Overloads in one of the declarations, you must use it in all of them." The keyword's real, documented purpose is different: "Overloads can also be used to shadow an existing member, or set of overloaded members, in a base class." The one genuine, verified use of the keyword anywhere in this codebase is exactly that case — Friend Overloads Function [GetType]() As Global.System.Type in My Project/MyExtensions/MyWebExtension.vb:110, deliberately shadowing Object.GetType() from the base class.
The keyword only becomes mandatory once one overload uses it Two same-named, different-signature procedures in the same class compile as ordinary overloads with no keyword at all, as the real example above shows. The rule that actually bites: the moment any one of them declares Overloads, every other procedure sharing that name in the class must declare it too, or it's a compile error. This matters most when a file already has an Overloads-shadowed base member (like the real GetType() example) and a later same-named addition forgets to match it.

Best practice

  • If a Sub starts needing to hand information back to its caller (beyond a ByRef parameter), make it a Function instead. Trying to bolt a return value onto a Sub after the fact usually means reworking every call site anyway.
  • Reach for Optional when a missing argument means "use this sensible default"; reach for a genuine overload when different call shapes mean genuinely different behavior. Not a different default for the same behavior.
  • Default to ByVal; reach for ByRef only when the callee has a genuine need to reassign the caller's variable. Remember ByVal on an object parameter still lets the callee mutate the object's own contents — it only blocks reassigning the caller's variable to a different object.
  • Choose the narrowest access level that still lets every real caller reach the member. Private by default, widen to Protected only for members a derived class genuinely needs, and to Public only for a real external contract — not because widening "might be useful later."

Better ways

A long run of Optional parameters with defaults (four or more) is usually a sign the method is doing several configurable things at once — consider whether a small options object, or splitting into two more specifically-named methods, would communicate the caller's intent more clearly than a long positional parameter list where it's easy to lose track of which optional argument is which.

Check your understanding

You're reading a VB.NET class and see a method declared with Sub. What does that tell you?

  • It returns no value — the equivalent of a C# method declared void.
  • It's private to the class by default.
  • It can't take any parameters.

A VB.NET class already has one Public Function FindDealer(dealerId As String) As IDealer. A second method with the same name but a different parameter list is added, without the Overloads keyword on either one. What happens? (Real, verified pattern — GetDataRowIndex in Supplier.aspx.vb does exactly this.)

  • It compiles fine as a normal overload — VB.NET, like C#, only requires the keyword once one of the declarations uses it.
  • It's a compile error — VB.NET always requires every procedure sharing a name to declare Overloads explicitly.
  • It compiles, but the second method silently shadows the first using an implicit Shadows.

A method has Optional office As String = "QJZ". The caller doesn't pass a value for office. Can the method body tell the difference between "caller omitted it" and "caller explicitly passed "QJZ""?

  • Yes — VB.NET provides an IsMissing()-style check for this.
  • No — both cases look identical inside the method; there's no runtime way to distinguish them.
  • Only if Option Strict is On for the file.

Sub Increment(ByVal x As Integer) reassigns x inside the method. What does the caller's own variable look like after the call returns?

  • Unchanged — ByVal copies the value in, so the reassignment inside the method only affects the local copy.
  • Changed to whatever the method reassigned x to.
  • It throws a compile error, since ByVal parameters can't be reassigned at all inside the method body.

A member is declared Protected in a real base class like RestrictedPage. What can access it?

  • Any code anywhere in the project or in any project that references it.
  • Only code inside the same class, or inside a class that derives from it — such as a BackOffice page that inherits from RestrictedPage.
  • Any code in the same assembly, regardless of whether it inherits from the class.

A member is declared Protected Friend. Which statement correctly describes who can access it, per Microsoft's own definition?

  • Only code that is both in a derived class AND in the same assembly — both conditions must hold together.
  • Code that is either in a derived class OR in the same assembly — satisfying just one of the two conditions is enough.
  • It's actually more restrictive than plain Protected alone.

The real RestrictedPage.vb has a nested Public Class RestrictedPageEventArgs whose own members (a constructor, a property) are declared Friend. What does this combination actually achieve?

  • The class itself is visible outside the assembly, but only code within this same assembly can actually construct an instance or use its members.
  • This doesn't compile — a Public class can't contain Friend members.
  • It means only classes that inherit from RestrictedPageEventArgs can use those members.
