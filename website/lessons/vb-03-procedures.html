VB.NET Fundamentals

Procedures: Sub, Function, Optional & ByRef

VB.NET splits what C# calls a "method" into two explicit keywords based on whether it returns a value, and has its own real parameter-passing idioms — Optional defaults and explicit Overloads — that don't map onto a single C# keyword.

Sub vs. Function

KeywordEquivalent in C#
SubA method returning void — does something, hands nothing back.
FunctionA method with a real return type — must end with Return value.
Function CalculateFee(amount As Double) As Double
    Return amount * 0.02
End Function

Sub Main()
    Dim fee As Double = CalculateFee(100)
    Console.WriteLine(fee)
End Sub

Optional parameters — a default value, right in the signature

Real, verified examples from BackOffice — this pattern is common here, not a rarity:

Public Sub ShowConfirmMessage(ByVal message As String, Optional id As String = "", Optional extField As String = "")
Private Sub LoadWalletType(Optional dealer As IDealer = Nothing)
Private Function GetCSVContents(stockReinstateList As List(Of Reinstate), stockProvisionList As List(Of IStockProvision), Optional iStartIndex As Integer = 0, Optional iEndIndex As Integer = 0) As String

reload/web/DEV/NET/Applications/BackOffice/Web/UserControls/MessageBox.vb:273; .../WebForms/DealerEdit.aspx.vb:1902; .../WebForms/ReportStockAllocation.aspx.vb:277

Optional parameters must come after every required parameter, and every Optional parameter must specify a default value (= "", = Nothing, = 0) — there's no way to mark a parameter optional without also giving it a fallback. A caller can omit any trailing optional argument and the default fills in automatically.

When to reach for Optional vs. a genuine method overload Optional parameters are the right tool when omitting an argument means "use this one sensible default" — id defaulting to an empty string, a start index defaulting to 0. Reach for Overloads instead (below) when the different call shapes represent genuinely different behavior, not just a default value for the same behavior — e.g. one overload that looks up a record by ID vs. one that takes the record object directly, rather than the same lookup with a parameter defaulted.

ByRef — the same keyword you'd ask about in code review

ByRef passes a variable by reference instead of by value — the callee can reassign it and the caller sees the new value after the call returns. It's VB's version of C#'s ref/out, and it's the historical VB default before VB.NET made ByVal the default (unlike VB6, where ByRef was implicit if you wrote nothing):

Sub Increment(ByRef x As Integer)
    x = x + 1
End Sub

Dim n As Integer = 5
Increment(n)
Console.WriteLine(n)   ' 6 — the caller's variable was mutated

The main real use is a "hand back more than one value" pattern — a Function returns one value directly, but a Sub (or a Function that also needs a second output) can use one or more ByRef parameters to hand back additional results. Prefer a genuine Function return value when there's only one thing to hand back — a ByRef parameter existing purely to fake a return value on a Sub is a sign it should be a Function instead.

Overloads — VB requires the keyword; C# doesn't

A real, easy-to-miss difference: C# lets you overload a method just by giving it a different parameter list, no keyword needed. VB.NET requires every overloaded version to explicitly say Overloads:

Public Overloads Function FindDealer(dealerId As String) As IDealer
    ' look up by ID
End Function

Public Overloads Function FindDealer(dealer As IDealer) As IDealer
    ' already have the object — just validate/refresh it
End Function
Miss the keyword and VB doesn't overload — it errors If one procedure with a given name specifies Overloads, every other procedure sharing that name in the same class must specify it too — VB won't silently treat a same-named, different-signature method as a normal overload the way C# does. Forgetting Overloads on a second same-named method (instead of on purpose using Shadows to hide the base one entirely) is a real compile-time error waiting to happen when porting overloaded C# methods into VB.NET by hand.

Best practice

  • If a Sub starts needing to hand information back to its caller (beyond a ByRef parameter), that's a sign it should probably be a Function instead — trying to bolt a return value onto a Sub after the fact usually means reworking every call site anyway.
  • Reach for Optional when a missing argument means "use this sensible default"; reach for Overloads when different call shapes mean genuinely different behavior, not just a different default.

Better ways

A long run of Optional parameters with defaults (four or more) is usually a sign the method is doing several configurable things at once — consider whether a small options object, or splitting into two more specifically-named methods, would communicate the caller's intent more clearly than a long positional parameter list where it's easy to lose track of which optional argument is which.

Check your understanding

You're reading a VB.NET class and see a method declared with Sub. What does that tell you?

  • It returns no value — the equivalent of a C# method declared void.
  • It's private to the class by default.
  • It can't take any parameters.

A VB.NET class already has one Public Function FindDealer(dealerId As String) As IDealer. A second method with the same name but a different parameter list is added, without the Overloads keyword on either one. What happens?

  • It compiles fine — VB.NET infers they're overloads from the different parameter lists, same as C#.
  • It's a compile error — VB.NET requires every procedure sharing a name to declare Overloads explicitly if any of them do.
  • It compiles, but the second method silently shadows the first using an implicit Shadows.
