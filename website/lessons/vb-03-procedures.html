VB.NET Fundamentals

Sub, Function & Classes

VB.NET splits what C# calls a "method" into two explicit keywords, based on whether it returns a value.

Sub vs. Function

KeywordEquivalent in C#
SubA method returning void — does something, hands nothing back.
FunctionA method with a real return type — must end with Return value.
Function CalculateFee(amount As Double) As Double
    Return amount * 0.02
End Function

Sub Main()
    Dim fee As Double = CalculateFee(100)
    Console.WriteLine(fee)
End Sub
2

Classes: Property instead of get/set, New instead of a matching-name constructor

Public Class Terminal
    Public Property TerminalId As String
    Public Property MerchantName As String
    Public Property IsOnline As Boolean

    Public Sub New(terminalId As String, merchantName As String)
        Me.TerminalId = terminalId
        Me.MerchantName = merchantName
        Me.IsOnline = True
    End Sub
End Class

Module Program
    Sub Main()
        Dim t As New Terminal("TNG-0042", "7-Eleven KL")
        Console.WriteLine(t.TerminalId & " - " & t.MerchantName & " - " & t.IsOnline)
    End Sub
End Module
TNG-0042 - 7-Eleven KL - True

Compare this to the C# version in C# Fundamentals → Classes — same three properties, same constructor logic. Public Property X As T is VB's equivalent of C#'s public T X { get; set; }; the constructor is always named New instead of repeating the class name; Me is VB's this.

Best practice

If a Sub starts needing to hand information back to its caller (beyond a ByRef parameter), that's a sign it should probably be a Function instead — trying to bolt a return value onto a Sub after the fact usually means reworking every call site anyway.

Better ways

Public Property X As T auto-properties are convenient, exactly like C#'s { get; set; } — but the same caution applies: if setting the property is really a meaningful action with rules attached (not just a raw field write), a real method (Sub Deactivate()) communicates that intent better than a property anyone can silently overwrite.

Check your understanding

You're reading a VB.NET class and see a method declared with Sub. What does that tell you?

  • It returns no value — the equivalent of a C# method declared void.
  • It's private to the class by default.
  • It can't take any parameters.
