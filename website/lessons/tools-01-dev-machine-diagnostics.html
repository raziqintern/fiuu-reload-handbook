Diagnosing Your Own Dev Machine

Not every blocker is a bug in reload's code. Some of the most time-consuming problems a new engineer hits are entirely local: a machine that isn't set up to log correctly, a deploy failure that looks like a build failure, or a hostname that simply won't resolve. Three real examples, all with a five-minute fix once you know where to look.

1. Your machine needs to be told about reload's Windows Event Log sources

reload's Windows-hosted services and applications write to a custom Windows Event Log rather than (or alongside) file-based logs, under source names following the pattern Fiuu.App.*. On a machine that has never had these sources registered, writes to them fail or silently go nowhere — which looks exactly like "logging isn't working" when actually the log source itself doesn't exist yet on that machine.

Registering it A setup script (Register-EventLogSources.ps1) registers every Fiuu.App.* source under the app's event log. It needs administrator rights to create event log sources, and it's written to self-elevate — running it as a normal user triggers a UAC prompt rather than failing outright: 
powershell -ExecutionPolicy Bypass -File "path\to\Register-EventLogSources.ps1"
Accept the UAC prompt; a second, elevated window opens and reports the registration result for each source. This is a one-time, per-machine setup step — worth running early when setting up a new dev machine, before you spend time debugging what looks like a missing-log mystery that's actually a missing-registration one.

2. "Publish failed" is not the same failure as "build failed" — read past the dialog

Visual Studio's generic error dialog ("Publish has encountered an error. Build failed.") conflates two entirely different failure domains into one unhelpful sentence. The actual answer is always further down in the Output window (View → Output, "Show output from: Build"), and the two summary lines at the bottom tell two different stories:

========== Build: 1 succeeded, 0 failed, 15 up-to-date, 0 skipped ==========
========== Publish: 0 succeeded, 1 failed, 0 skipped ==========

Compilation can succeed completely while deployment — a separate stage, Web Deploy pushing the compiled output to a remote server — fails for a completely unrelated reason. A real example from this exact dialog:

Error ERROR_DESTINATION_INVALID: Web deployment task failed.
( Could not connect to the remote computer ("ec2amaz-e2hp5a7").
Make sure that the remote computer name is correct and that you are able to connect to that computer. )
The trap Trusting the dialog's "Build failed" framing sends you looking for a syntax error or a broken reference that doesn't exist. The real problem is network reachability to a Web Deploy endpoint (port 8172) — nothing about the C#/VB.NET code is at fault. Always check which of the two summary lines (Build vs. Publish) actually says "failed" before deciding what kind of problem you're chasing.

3. A hostname that "should" resolve, and doesn't

The fix for the deploy failure above is often "use the IP address instead of the hostname" — and that fix works, but it's worth understanding why, not just applying it. A hostname like ec2amaz-e2hp5a7 is the auto-generated Windows computer name AWS EC2 assigns a new instance by default. That name typically isn't registered in any real DNS server — it only resolves via NetBIOS name broadcast on the same local network segment. If your machine is on a different subnet, behind a VPN split that doesn't relay that broadcast, or otherwise not on the same local segment as the target box, the name lookup fails silently — even though the machine itself is perfectly reachable by IP.

Confirm it's a resolution problem before reaching for an IP 
nslookup ec2amaz-e2hp5a7
Test-NetConnection -ComputerName ec2amaz-e2hp5a7 -Port 8172
If nslookup fails to resolve the name at all, that confirms the problem is name resolution, not reachability — and explains why swapping in the IP address fixes it. If you're editing a shared publish profile (checked into a repo, not just your own machine's local copy), think twice before hardcoding an IP: EC2 private IPs can change, and a teammate on a different subnet or VPN path may not reach that same IP the same way you do. A local-only profile is a safer place for that workaround than a shared one.

Best practice

When a tool's own error dialog gives you a vague, high-level summary ("build failed", "an error occurred"), find the actual underlying log or output window before acting on the summary's framing — the summary is often written to cover multiple failure domains at once, and acting on the wrong one wastes time investigating code that was never the problem. And when you fix something by replacing a symbolic reference (a hostname, a config key) with a literal value (an IP, a hardcoded path), understand why the symbolic version failed before deciding whether your fix belongs in a shared file or should stay local to your machine.

Check your understanding

Visual Studio's publish dialog says "Build failed", but the Output window's summary line reads Build: 1 succeeded, 0 failed and Publish: 0 succeeded, 1 failed. What should you actually investigate?

  • Recently changed C#/VB.NET code for a syntax or reference error.
  • The deployment target and connection (Web Deploy endpoint, hostname resolution, network reachability) — the actual failure is in the publish/deploy stage, not compilation.
  • Whether a NuGet package reference is missing.

Why does an EC2 instance's auto-generated hostname (like ec2amaz-e2hp5a7) often fail to resolve from a machine on a different subnet or VPN segment, while its IP address always works?

  • That hostname usually isn't a real DNS record — it only resolves via local-segment NetBIOS broadcast, which doesn't cross subnets or most VPN splits. An IP skips name resolution entirely.
  • The firewall blocks hostnames but allows raw IP traffic.
  • DNS servers are just slow to respond and eventually time out.
