Type Conversion: CType, DirectCast & TryCast

VB.NET has three named ways to explicitly convert a value's type, each with a different answer to "what relationship must the two types have, and what happens if the conversion turns out to be impossible at runtime." This lesson also covers Shared members and Enum, since the real example that grounds the casts needs both.

Explicit conversion is one idea, three mechanisms

Converting a value from one type to another is a single concept — but VB.NET gives you three keywords for it because they make fundamentally different trade-offs between generality, speed, and failure behavior. Per Microsoft's own CType Operator reference, which documents all three side by side:

KeywordData typesArgument relationship requiredRun-time failure
CTypeAny data typesA widening or narrowing conversion must be defined between the two typesThrows InvalidCastException
DirectCastAny data typesOne type must inherit from or implement the otherThrows InvalidCastException
TryCastReference types onlyOne type must inherit from or implement the otherReturns Nothing

DirectCast and TryCast both require a real inheritance/interface relationship between the two types — they're for "I have an Object that I know is actually a GridView," not for genuinely converting data. CType is the general-purpose one: it also handles conversions where no such relationship exists at all — String to Integer, a boxed enum value to its underlying Integer, or a class's own user-defined conversion operator.

Enums: a named set of integer constants

Before the casts, the type they're most often converting: Public Enum is VB's syntax for a small, closed set of named values backed by an integer — the same concept as C#'s enum. Two real ones:

Public Enum ErrorType
    ' ... named integer constants
End Enum

Public Enum EnumWalletType
    ' ... named integer constants, one of which is Consignment
End Enum

Module: BackOffice/Web · Files: error.aspx.vb:6; Fiuu.CEPP.Models.Interfaces (EnumWalletType)

The question this naturally raises: why not just use plain integers? Nothing stops you from writing If walletType = 3 Then instead of If walletType = EnumWalletType.Consignment Then — both compile, both run identically. The difference shows up when someone else reads the code six months later: 3 carries no information at all without cross-referencing the enum's definition, while EnumWalletType.Consignment is self-explanatory at the call site. The enum also gives the compiler something to check — assign an out-of-range plain integer and nothing complains; assign a name that isn't a member of the enum and it won't compile at all.

CType: the general-purpose conversion, real usage on a boxed enum value

Populating a dropdown from every value of an enum, filtered and sorted — real, production code:

ddlWalletType.DataSource = (From item In [Enum].GetValues(GetType(EnumWalletType))
                            Where CType(item, Integer) <> EnumWalletType.Consignment
                            Order By CType(item, Integer)
                            Select New With {.Text = item.ToString(), .Value = CType(item, Integer)})

Module: BackOffice/Web · File: WebForms/DealerCreate.aspx.vb:539-542

Why CType, specifically, is the only one of the three that works here [Enum].GetValues(...) returns a plain array of Object — each element is a boxed enum value with no compile-time type information beyond "some object." Converting a boxed value type's contents to Integer is not an inheritance/interface relationship (an Integer doesn't "inherit from" the enum, or vice versa) — it's exactly the kind of conversion DirectCast and TryCast are structurally unable to perform, per the table above. CType is the only one of the three general enough to do it.

The same keyword behaves three different ways depending on what you feed it — worth seeing side by side, since this is exactly where "creative or unexpected" results show up in practice:

' 1. A defined, safe conversion at compile time AND runtime — succeeds.
Dim a As Integer = CType("123", Integer)

' 2. A defined conversion at compile time, but this particular value can't
'    actually make the trip at runtime — compiles fine, throws when it runs.
Dim b As Integer = CType("not a number", Integer)

' 3. No conversion is defined between these two types at all —
'    this line does not compile, ever, regardless of the value.
' Dim c As Date = CType("hello", Boolean)
Case 1: a = 123
Case 2: throws System.FormatException at runtime (CType hands off to the standard
        numeric parser here, which is where this particular exception comes from)
Case 3: compile-time error — commented out above because it would stop the
        whole file from building
The wrong way to read the comparison table above It's tempting to read "CType: any data types" as "CType never fails" — case 2 above is exactly why that's wrong. CType being more general than DirectCast/TryCast means it accepts a wider range of type pairs, not that every individual value passed through it will actually convert successfully. Always ask "is this specific value valid for the target type," not just "is this pair of types allowed."

DirectCast: casting where the framework already forces a type down to Object

Two real lines, from two different real problems, both solved by DirectCast:

gvCommissions.DataSource = DirectCast(ViewState("CommDetails"), DataTable)

Module: BackOffice/Web · File: WebForms/Commission.aspx.vb:63

Dim HeaderGrid As GridView = DirectCast(sender, GridView)

Module: BackOffice/Web · File: WebForms/CommissionEdit.aspx.vb:537

The context that makes both of these necessary, not just stylistic ViewState is ASP.NET's built-in per-page dictionary for surviving a postback (see Debugging Reload → The Postback State Trap for what postbacks actually are) — its indexer is typed As Object no matter what you actually stored in it, because ViewState has to be able to hold anything, for any page, ever written. Earlier in this same method, something did ViewState("CommDetails") = someDataTable — but the compiler has no memory of that by the time this line reads it back; all it sees is Object. Likewise, a WebForms event handler's sender parameter is always typed Object in the framework's own method signature — Sub GridView1_RowCommand(sender As Object, e As GridViewCommandEventArgs) — regardless of which specific control actually raised the event. DirectCast is correct in both cases because the surrounding code is the reason the real type is known with certainty: the same class wrote the ViewState value it's now reading, and the same markup file wired up the specific control that's now arriving as sender.
The wrong scenario: when that certainty is misplaced Imagine CommissionEdit.aspx.vb had two different grids on the page, and a shared row-command handler wired to both by mistake — one a GridView, the other a DataList. DirectCast(sender, GridView) works perfectly for clicks from the first grid, and throws InvalidCastException the instant a click comes from the second — because a DataList genuinely doesn't inherit from or implement GridView, no matter how confident the code was. This is the real risk DirectCast carries: it doesn't verify your certainty, it just fails loudly the moment that certainty turns out to be wrong. That's a deliberate trade-off (see Best practice below), not a flaw — but it's the concrete failure mode to have in mind before reaching for it.

TryCast: when "the cast might fail" is the normal case, not a bug

Dim tpSAPSetting As TabPanel = TryCast(FindControlRecursive(SAPSettingTabId), AjaxControlToolkit.TabPanel)
Dim tpSAPDealerSetting As TabPanel = TryCast(FindControlRecursive(SAPDealerSettingTabId), AjaxControlToolkit.TabPanel)

If tpSAPSetting IsNot Nothing OrElse ...

Module: BackOffice/Web · File: WebForms/RestrictedPage.vb:72-75

The idiomatic pairing: TryCast + IsNot Nothing FindControlRecursive might legitimately not find a control with that ID on every page — that's not a bug to guard against defensively, it's an expected outcome depending on which page is being rendered (not every page has a SAP settings tab). TryCast returning Nothing on failure (instead of DirectCast's exception) turns "did this control exist" into a normal IsNot Nothing check, not exception handling — exactly the real pattern here, checked immediately on the next line.
The wrong scenario: TryCast has a restriction CType and DirectCast don't Per the comparison table, TryCast works on reference types only. This does not compile, for any value: 
' Integer is a value type — TryCast flatly refuses this at compile time,
' regardless of what n actually is.
Dim result = TryCast(n, Integer)
Reaching for TryCast out of habit on a value-type target is the one scenario where you're forced back to CType even when "might fail gracefully" is exactly the behavior you wanted — there's no Nothing-returning safe cast for value types in VB.NET; Integer? (see C#/.NET Deep Dives → Nullable Types, which applies to VB.NET equally) combined with a manual check is the nearest equivalent.

Beyond casting: the other real ways this codebase converts data

CType/DirectCast/TryCast answer "how do I treat this value as a different type." A separate, equally common question is "how do I turn this raw piece of data — a query-string value, a database column, a form field — into a properly-typed value in the first place." VB.NET and this codebase use several real, distinct mechanisms for that, not just one.

The C* family: VB's own dedicated conversion functions

Official documentation Microsoft's own Type Conversion Functions reference recommends these over the .NET-wide alternatives, for two concrete reasons: "These functions are compiled inline, meaning the conversion code is part of the code that evaluates the expression... which improves performance" and "you should use the Visual Basic type conversion functions in preference to the .NET Framework methods such as ToString()... the .NET Framework conversion methods do not always produce the same results as the Visual Basic functions, for example when converting Boolean to Integer."

TryParse: convert-or-tell-me, no exception involved

Official documentation Integer.TryParse, Decimal.TryParse, and their siblings exist specifically to avoid throwing. Per Microsoft's own Int32.TryParse reference: "The TryParse method is like the Parse method, except the TryParse method does not throw an exception if the conversion fails. It eliminates the need to use exception handling to test for a FormatException in the event that s is invalid and cannot be successfully parsed." 
If Not Decimal.TryParse(txtRepostAmount.Text, repostamount) Then
    ' invalid input — show a validation message and stop, no exception ever thrown
End If

This is the right tool specifically when "the input might not be a valid number" is an expected, routine possibility (user-typed text in a textbox) rather than a genuine bug — the same "expected failure, not exceptional" territory TryCast occupies for reference-type casts, just for parsing text instead.

When to write As Type explicitly, and when to let inference do it

Syntax, Types & Option Strict already covers what Option Infer does mechanically — Dim x = 5 infers Integer without an As clause. The remaining question is a judgment call: when should you write the type out anyway, even though the compiler doesn't require it?

Official documentation Microsoft's own Local Type Inference reference gives the concrete case for writing As explicitly — when the inferred type isn't the one you actually want: "If you do not want num2 in the previous example to be typed as an Integer, you can specify another type by using a declaration like Dim num3 As Object = 3 or Dim num4 As Double = 3." It also states a hard boundary where inference simply isn't available at all: "Type inference can be used only for non-static local variables; it cannot be used to determine the type of class fields, properties, or functions." and the same restriction applies to Static locals.
SituationWhat to doWhy
A class field, property, or Function return typeAlways write As TypePer the official docs above, inference is a local-variable-only mechanism — it isn't legal syntax anywhere else, regardless of style preference.
A Static local variableAlways write As TypeSame restriction — inference doesn't apply to Static locals even though they're declared inside a procedure.
The initializer's type is obvious from the line itself (a literal, a New SomeType(...), an obviously-typed method name)Either is fine; inference is common and idiomaticDim name = "Springfield" and Dim name As String = "Springfield" genuinely declare the same thing — the type is equally obvious either way.
You want a wider or different type than what the initializer alone would inferWrite As Type explicitlyDim x = 3 infers Integer — if you actually wanted Double or Object, per the official example above, you must say so with an explicit As clause; inference cannot read your intent past the literal.
The initializer is a method call whose return type isn't obvious from its name aloneWrite As Type explicitlyA reader shouldn't have to open GetProductGroups's own definition just to know what lstProductGroup holds — this is exactly why the real CommissionEdit.aspx.vb example above writes As List(Of IProductGroup) explicitly rather than relying on inference.
What if you rely on inference somewhere it silently does the wrong thing? Dim total = 0 followed later by total += someDecimalValue infers total as Integer from the literal 0 — any fractional part silently truncates on every addition, with no compiler warning, because nothing about the declaration itself looks wrong. Writing Dim total As Decimal = 0 up front avoids the whole class of bug. This is the concrete version of "you want a different type than what would be inferred" from the table above — it's easy to trigger by accident with a bare numeric literal that happens to look like the type you actually needed, but isn't.

Shared: one copy for the whole class, not one per instance

Per Microsoft's Shared reference: "Sharing a member of a class or structure makes it available to every instance, rather than non-shared, where each instance keeps its own copy." This is VB's name for what C# calls static — same concept, different keyword.

The question this naturally raises: what would it look like if it weren't shared? Side by side — same class, same field, only the Shared keyword differs, run against two separate instances: 
Class NonSharedCounter
    Public Count As Integer = 0
End Class

Class SharedCounter
    Public Shared Count As Integer = 0
End Class

Dim a As New NonSharedCounter()
Dim b As New NonSharedCounter()
a.Count += 1
a.Count += 1
b.Count += 1
Console.WriteLine("Non-shared — a: " & a.Count & ", b: " & b.Count)

SharedCounter.Count += 1
SharedCounter.Count += 1
SharedCounter.Count += 1
Console.WriteLine("Shared — every reference sees: " & SharedCounter.Count)
Non-shared — a: 2, b: 1
Shared — every reference sees: 3

Two separate NonSharedCounter objects each keep their own independent Count — incrementing a twice never touches b. There's only ever one SharedCounter.Count in memory, no matter how many (or how few — even zero) instances of the class exist; every increment, from anywhere, changes the same value everyone else sees.

Now the real, verified pattern — a Shared factory method, overloaded by parameter type:

Public Shared Function Parse(stock As IStockInfo) As IAllocationStock

Called as AllocationStock.Parse(someStock) — through the class name, never through an instance variable — which is exactly the point: no AllocationStock object needs to exist yet to call the method that builds one. This pairs naturally with the Overloads keyword from Procedures: both Parse overloads must (and do) declare Overloads since they share a name in the same class.

The wrong scenario: making a factory method non-Shared by mistake If Parse were declared without Shared, every call site would first need an existing AllocationStock instance to call it on — someExistingStock.Parse(newStock) — which makes no sense for a method whose entire job is producing the instance in the first place. This is the concrete tell for "this should probably be Shared": if calling the method requires an instance you don't actually have yet (or one that's logically unrelated to what the method returns), the method belongs on the class, not on an instance.

Best practice

  • Default to DirectCast when you already know the real type with certainty (a sender parameter you wired up yourself, a ViewState value you stored yourself) — it fails loudly and fast if that certainty was ever wrong, which is exactly what you want for a bug you'd rather catch than silently limp past.
  • Reach for TryCast the moment "the cast might legitimately not succeed" is a real, expected possibility on a reference type — pair it with IsNot Nothing, never leave the result unchecked.
  • Reach for CType only when neither of the above applies — genuinely converting between unrelated types (a boxed enum to its underlying integer, a string to a number) where no inheritance relationship could ever exist — and still expect it to be able to throw at runtime on a bad individual value, even though the type pair itself is allowed.
  • Reach for Shared when a value or method is conceptually about the whole class, not any one instance of it — a factory method with no natural "existing instance" to call it on, or a value every instance should agree on.
  • Prefer VB's own C* conversion functions over Convert.ToX/.ToString() for VB-to-VB code, and reach for TryParse the moment invalid input is a routine possibility, not a bug. Per Microsoft's own docs, the C* functions are faster (compiled inline) and more consistent with VB semantics than the .NET-wide Convert class.
  • Write As Type explicitly whenever the initializer's type isn't obvious at a glance, or you need a wider/different type than what a literal alone would infer. Rely on inference only when the type is equally obvious either way — a bare numeric literal you actually intend as Decimal/Double is the classic silent-truncation trap inference alone won't catch.

Check your understanding

Why can't DirectCast be used to convert a boxed enum value (from [Enum].GetValues(...), typed Object) to Integer?

  • Enums are a special case DirectCast never supports.
  • DirectCast requires an inheritance/implementation relationship between the source and target types, and converting a boxed value to a different value type isn't that — it needs CType's more general conversion.
  • DirectCast doesn't accept Object as a source type at all.

Dim tpSAPSetting As TabPanel = TryCast(FindControlRecursive(SAPSettingTabId), AjaxControlToolkit.TabPanel) — the control genuinely doesn't exist on this page. What happens?

  • An InvalidCastException is thrown immediately.
  • tpSAPSetting is set to Nothing — no exception — which is exactly what the following IsNot Nothing check is there to handle.
  • tpSAPSetting is set to a new, empty TabPanel automatically.

Two separate instances of a class each read and increment a Shared field. What does each instance see?

  • Each instance has its own independent copy, unaffected by the other's changes.
  • Both instances see the same single value — an increment through either instance changes what the other one reads next.
  • Only the first instance created can actually access the field; later instances get an error.

A textbox's text needs to become a Decimal, but the user might have typed something invalid. Based on the real BillPaymentVoidRepostCreate.aspx.vb pattern, what's the right tool?

  • CDec, wrapped in a Try/Catch to handle bad input.
  • Decimal.TryParse, checking its returned Boolean — no exception handling needed for what's a routine, expected input case.
  • DirectCast(txtRepostAmount.Text, Decimal)

Per Microsoft's own Type Conversion Functions reference, why does this codebase's real code prefer CInt/CStr/CBool over Convert.ToInt32/.ToString() where both would work?

  • They're compiled inline for better performance, and the .NET Framework's Convert methods don't always produce identical results to VB's own functions for the same conversion.
  • Convert.ToInt32 doesn't work when Option Strict is On.
  • The VB conversion functions only work with numeric types, never strings or booleans.

Dim total = 0 is later used as total += someDecimalValue inside a loop. What actually happens, and why?

  • Any fractional part of someDecimalValue is silently truncated on every addition, because total was inferred as Integer from the literal 0 — not the wider type the code actually needed.
  • VB.NET automatically widens total to Decimal the first time a Decimal value is added to it.
  • It throws an OverflowException the first time a fractional value is added.
