Control Flow, Loops & Select Case

Same underlying logic as the C# track's control flow lesson, but with real VB.NET-specific traps worth knowing on their own terms: And/Or don't short-circuit the way &&/|| do, and the early-exit keyword changes depending on what block you're in.

If / ElseIf / Else

Dim amount As Integer = 25

If amount <= 0 Then
    Console.WriteLine("Invalid amount")
ElseIf amount > 500 Then
    Console.WriteLine("Exceeds max reload limit")
Else
    Console.WriteLine("Amount OK: " & amount)
End If
Amount OK: 25

Notice ElseIf is one word (unlike C#'s else if, two words), and the whole block closes with End If instead of a closing brace.

Comparison and logical operators — and the short-circuit distinction that actually matters

Official documentation Microsoft's AndAlso Operator reference defines short-circuiting precisely: "A logical operation is said to be short-circuiting if the compiled code can bypass the evaluation of one expression depending on the result of another expression." Its own remarks contrast it directly with the non-short-circuit form: "In a Boolean comparison, the And operator always evaluates both expressions, which could include making procedure calls. The AndAlso Operator performs short-circuiting, which means that if expression1 is False, then expression2 is not evaluated."

Why And/Or being non-short-circuit is a real correctness risk, not just a style choice If obj IsNot Nothing And obj.IsValid Then looks reasonable but is dangerous: And evaluates both sides regardless of the first result, so if obj actually is Nothing, obj.IsValid still runs and throws a NullReferenceException — the IsNot Nothing check accomplished nothing. AndAlso would short-circuit and never evaluate the right side once the left side is False. Default to AndAlso/OrElse in new code; reach for plain And/Or only in the rare case where you specifically need both sides evaluated regardless (e.g. two independent method calls with side effects, where you genuinely want both to run).

Arithmetic operators — VB.NET has two division operators, not one

C# has a single / that behaves differently depending on the operand types (integer / integer truncates; anything with a double keeps the fraction). VB.NET instead has two distinct operators that always mean the same thing regardless of type — you pick which behavior you want by which symbol you write, not by what type happens to be involved.

Official documentation Microsoft's own \ Operator reference states the distinction directly: "The result is the integer quotient of expression1 divided by expression2, which discards any remainder and retains only the integer portion. This is known as truncation." — contrasted explicitly with its sibling: "The / Operator (Visual Basic) returns the full quotient, which retains the remainder in the fractional portion." Its own worked example: 11 \ 4, 9 \ 3, 100 \ 3, and 67 \ -3 return 2, 3, 33, and -22 respectively — the remainder is simply gone, not rounded.

Exit — leaving early, and which keyword matches which block

VB.NET's early-exit keyword changes depending on what you're inside — there's no single break/return pair covering every case:

Official documentation Microsoft's Exit Statement reference lists each form as scoped to exactly one kind of block: "Exit For Immediately exits the For loop in which it appears... Exit For can be used only inside a For...Next or For Each...Next loop." and "Exit Sub Immediately exits the Sub procedure in which it appears... In a Sub procedure, the Exit Sub statement is equivalent to the Return Statement." This is exactly why there's no single universal "leave now" keyword — each one is grammatically tied to the specific block type it can appear in, and using the wrong one for your current block is a compile error, not a runtime surprise.

Exiting a Function early from inside an If — two real, different shapes in the same codebase

Exit Function inside a Function works the same way Exit Sub does inside a Sub — it leaves immediately — but a Function has to leave something behind as its return value, and that's exactly where the two real patterns below diverge.

Private Function IsEmailFieldValid(sEmailAddress As String) As Boolean
    For Each sEmail In arrEmail
        If Not SharedFunction.validateEmail(sEmail) Then
            MessageBox.ShowErrorMessage(Message.InvalidEmailAddress)
            Return False
            Exit Function
        End If

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/DealerEdit.aspx.vb:2159-2168

Real, shipped dead code — worth recognising, not copying Return False already exits the function immediately with a value; the Exit Function on the very next line can never execute — it's unreachable, and functionally identical to deleting it. This isn't a hypothetical "what if someone wrote this" example: it's real, committed code in this exact file. The lesson isn't "this specific line is broken" (it isn't — the function still behaves correctly, since Return alone does the whole job) — it's that Return and Exit Function are two full, independent ways to leave a function, and combining them doesn't combine their effects, it just leaves one of them silently unreachable.

The second real pattern relies on Exit Function alone, with no explicit return value at all:

Private Function ValidateEditDealer() As Boolean
    ...
    If (String.IsNullOrEmpty(txtDealer.Text.Trim())) Then
        MessageBox.ShowErrorMessage(Message.DealerNameRequired)
        Exit Function
    End If

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/DealerEdit.aspx.vb:317,320-322

What value does this actually return? A bare Exit Function returns whatever the function's own implicit return value currently holds — for a Boolean function, that's its type's default, False, unless something earlier in the method explicitly set it to something else first. Here that's exactly the intent (validation failed → return False), but it works by relying on the default rather than stating it — Return False in the same spot would say the same thing more explicitly, at no cost. Prefer an explicit Return value over a bare Exit Function whenever the returned value matters to the reader, precisely because Exit Function alone hides what's actually being returned.

For loops are inclusive on both ends

For i As Integer = 1 To 3
    Console.WriteLine("Attempt " & i)
Next
Attempt 1
Attempt 2
Attempt 3
Official documentation Microsoft's For...Next Statement reference, "Technical Implementation" section, states the loop's stopping condition precisely: "The loop doesn't stop until counter has passed end. If counter is equal to end, the loop continues. The comparison that determines whether to run the block is counter <= end if step is positive." That <= — not < — is the documented reason the upper bound runs.
To is inclusive — an easy off-by-one trap For i = 1 To 3 runs for i = 1, 2, 3 — three iterations, including the upper bound. This differs from C#'s more common for (int i = 0; i < 3; i++) idiom, which deliberately excludes its upper bound. Translating a C# loop into VB.NET (or reading the reverse) is a classic place to introduce an off-by-one bug if you're not paying attention to which convention you're in.

Same loop, both conventions side by side, run to prove the count rather than just asserted:

' VB.NET: To is inclusive on both ends
Dim count As Integer = 0
For i As Integer = 0 To 3
    count += 1
Next
Console.WriteLine(count)
4
// C#: < excludes the upper bound
int count = 0;
for (int i = 0; i < 3; i++) {
    count++;
}
Console.WriteLine(count);
3

A direct, syntax-only port of For i = 0 To 3 into C#'s for (int i = 0; i <= 3; i++) is correct — but the far more common mistake is porting the number 3 unchanged into the more idiomatic i < 3 form, silently dropping one iteration. This is exactly the trap the callout above names.

Other loop shapes: Do Until/While, and For Each over your own objects

For/For Each both assume you know in advance what you're iterating over — a count, or a collection. Do While/Do Until exist for the opposite case: keep looping until some condition changes, with no predetermined number of iterations. Real, verified usage — reading a file stream in fixed-size chunks until there's nothing left to read:

Dim sourceBytes As Integer = 1
Do Until (sourceBytes <= 0)
    sourceBytes = fs.Read(buffer, 0, buffer.Length)
    strmZipOutputStream.Write(buffer, 0, sourceBytes)
Loop

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/ReportChannelPartner.aspx.vb:199-202

fs.Read(...) returns however many bytes it actually managed to read — a number nobody can know ahead of time, since it depends on how much of the file is left. That's exactly the shape Do Until fits and a counting For loop can't: the number of iterations is discovered one at a time, by the loop's own condition, not decided before the loop starts. Do While (condition) is the same construct with the test inverted — keep going while true instead of until true; pick whichever phrasing reads more naturally for the specific condition.

For Each works identically whether the collection holds a primitive type or a class this codebase defines itself — the mechanism doesn't care what T is, only that the collection is enumerable (see VB.NET Fundamentals → Syntax, Types & Option Strict for why). Three real, verified examples looping over custom objects, not primitives:

For Each data As CommissionDealerColumn In dataList
For Each product As IProduct In lstProduct
For Each configDetail As ConfigDetails In _backOfficeConfigDetails

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/Commission.aspx.vb:628; WebForms/ProductCreate.aspx.vb:414; Helpers/HelperFunction.vb:15

Each loop variable (data, product, configDetail) is a full object of that type inside the loop body — its properties and methods are all available exactly as if you'd written Dim data As CommissionDealerColumn = dataList(i) yourself, just without an index variable to manage.

Select Case — VB's switch, with real differences worth knowing

Real code from TerminalFirmwareVersionList.aspx.vb's grid command handler:

Select Case e.CommandName
    Case "Action", "Detail"
        ResetRedirect(String.Format("TerminalFirmwareVersion.aspx?id={0}&Command={1}", e.CommandArgument, e.CommandName))
    Case "EditRow"
        ResetRedirect(String.Format("TerminalFirmwareVersionEdit.aspx?id={0}", e.CommandArgument))
    Case Else
        ' no matching command — nothing to do
End Select

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb:309-313

Official documentation Microsoft's Select...Case Statement reference confirms fall-through is not just absent from this example but structurally impossible: "If testexpression matches any Case expressionlist clause, the statements following that Case statement run up to the next Case, Case Else, or End Select statement. Control then passes to the statement following End Select." There is no syntax in the language for opting back into fall-through, unlike C-style switch where it's the default you opt out of with break;. The same reference also documents the range/comparison forms used below: "Use the To keyword to specify the boundaries of a range... Use the Is keyword with a comparison operator... to specify a restriction on the match values."

Three real differences from a C-style switch: a single Case can list several values comma-separated (Case "Action", "Detail" matches either, no separate case label needed); there's no fall-through at all, ever — each Case implicitly breaks, so there's no VB equivalent of a missing break; bug; and a Case can be a range or comparison, not just an exact match:

Select Case amount
    Case Is <= 0
        Console.WriteLine("Invalid amount")
    Case 1 To 500
        Console.WriteLine("Amount OK: " & amount)
    Case Else
        Console.WriteLine("Exceeds max reload limit")
End Select
When to reach for Select Case over If/ElseIf Once you're comparing the same single value against three or more possibilities, Select Case reads more clearly than a chain of ElseIfs and makes it visually obvious every branch is testing the same thing — the grid-command example above would be far less scannable as five separate If e.CommandName = "..." Then checks. Stick with If/ElseIf when the branches test genuinely different, unrelated conditions rather than one value against several possibilities.

Best practice

  • Default to AndAlso/OrElse in new code, not And/Or. Reach for the non-short-circuit forms only when you specifically need both sides evaluated regardless of the first result — e.g. two independent method calls with side effects, where you genuinely want both to run.
  • Write out the first and last value a translated loop actually touches, not just its shape. For i = 0 To n - 1 is the correct VB.NET translation of C#'s for (int i = 0; i < n; i++) — the - 1 is the whole trick, and it's easy to drop under time pressure.
  • Reach for Select Case once you're testing one value against three or more possibilities. A chain of ElseIfs works but hides that every branch is testing the same thing; Select Case makes that structure visible at a glance.
  • Use Return value to exit a Function, not a bare Exit Function, whenever the returned value matters to the reader. A bare Exit Function returns whatever the implicit return value already holds (a type's default if nothing set it) — correct, but it hides the actual value being returned; Return False says the same thing without making the reader work it out.

Better ways

For Each sidesteps the inclusive/exclusive bound question entirely, since there's no index to get wrong — prefer it over an indexed For loop whenever you don't actually need the index itself, exactly as in C#'s foreach.
