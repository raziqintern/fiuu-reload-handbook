LINQ in VB.NET: Query Syntax, Lambdas & Anonymous Types

C# Fundamentals covered LINQ as method calls (.Where(...), .Select(...)). VB.NET has that too — but it also has a second, SQL-shaped way to write the exact same query, actually used in BackOffice. Both need one more concept first: VB's own lambda syntax.

The concept: a lambda expression is an unnamed function, written inline

Per Microsoft's Lambda Expressions reference: "A lambda expression is a function or subroutine without a name that can be used wherever a delegate is valid." You build one with the same Function/Sub keywords as a normal procedure — the difference is it has no name, and it's written as part of a larger statement instead of declared separately:

Dim increment = Function(x) x + 1
Console.WriteLine(increment(1))

Dim isEven = Function(n As Integer) n Mod 2 = 0
Console.WriteLine(isEven(4))
Console.WriteLine(isEven(5))

Real, verified usage — both are lambdas passed directly as an argument, never given a name at all:

Dim isAnyCheckedPlatformIndicator As Boolean = cblPlatformIndicator.Items.Cast(Of ListItem)().Any(Function(item) item.Selected)
Dim countries = service.GetCountries().Where(Function(c) c.Id = ddlCountry.SelectedValue)

This is the exact same shape as C#'s lambdas — different keyword, same idea C# Fundamentals' Collections & LINQ lesson used x => x.Something. VB.NET's Function(x) x.Something is the same concept — an inline, unnamed function — spelled with a keyword instead of an arrow. .Where(Function(c) c.Id = ...) and C#'s .Where(c => c.Id == ...) compile to functionally the same thing.

VB.NET's second option: query syntax — the same LINQ, written like SQL

Everything above is method syntax — chained .Where(...)/.Select(...) calls, same as C#. VB.NET also has query syntax: From/Where/Order By/Select keywords that read like a SQL statement, compiling down to the exact same method calls underneath. This isn't a simplified toy version — it's real, used in production:

ddlWalletType.DataSource = (From item In [Enum].GetValues(GetType(EnumWalletType))
                            Where CType(item, Integer) <> EnumWalletType.Consignment
                            Order By CType(item, Integer)
                            Select New With {.Text = item.ToString(), .Value = CType(item, Integer)})

Reading it clause by clause: From item In [Enum].GetValues(...) declares a range variable, item, iterating the source — the query-syntax equivalent of the lambda parameter in method syntax. Where filters, exactly like .Where(...). Order By sorts — there's no method-syntax equivalent keyword shown yet, but it corresponds to .OrderBy(...). Select defines the shape of each result.

The concept inside that Select: anonymous types

New With {.Text = item.ToString(), .Value = CType(item, Integer)} creates an object of a type that has no name anywhere in the code — VB.NET generates one on the fly, with exactly the properties listed (Text, Value), typed from whatever each expression evaluates to. This exists specifically for cases like this one: the query's result only needs to exist briefly, to bind to ddlWalletType's DataSource — defining a real, named class just to hold two properties for one local use would be pure ceremony.

When an anonymous type stops being the right tool The moment a shape needs to be passed between methods, stored, or referred to by a real type name anywhere else, that's the signal to define an actual class instead — an anonymous type's "type" only has meaning within the method (and nearby lambdas) that created it; you can't write a method signature that accepts or returns one by name.

Best practice

  • Reach for query syntax when a query has several chained operations (filter, then sort, then shape) and would read as a long, nested chain in method syntax — the SQL-like structure keeps each step on its own line, in the same order SQL developers already read intuitively. Reach for method syntax for a single operation (one .Where(...), one .Any(...)) — query syntax's From/Select ceremony isn't worth it for one clause.
  • Keep lambda bodies short — a lambda that needs several statements and local variables to express its logic is a sign the logic deserves a real, named method instead, referenced with AddressOf.

Check your understanding

In From item In [Enum].GetValues(...) Where CType(item, Integer) <> EnumWalletType.Consignment ..., what is item?

  • A pre-existing variable declared earlier with Dim.
  • A range variable, introduced by the From clause itself, that represents each element from the source collection in turn — the query-syntax equivalent of a lambda's parameter.
  • A variable created by the Where clause.

Select New With {.Text = item.ToString(), .Value = CType(item, Integer)} — what kind of object does each result actually have?

  • An instance of a real, named class the query looked up automatically.
  • An anonymous type — a compiler-generated type with exactly the properties listed (Text, Value), never given a name in the source code.
  • A Dictionary(Of String, Integer).
