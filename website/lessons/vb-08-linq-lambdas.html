VB.NET Fundamentals

LINQ in VB.NET: Query Syntax, Lambdas & Anonymous Types

C# Fundamentals covered LINQ as method calls (.Where(...), .Select(...)). VB.NET has that too — but it also has a second, SQL-shaped way to write the exact same query, actually used in BackOffice. Both need one more concept first: VB's own lambda syntax.

A lambda expression is a function with no name, written inline

Per Microsoft's Lambda Expressions reference: "A lambda expression is a function or subroutine without a name that can be used wherever a delegate is valid." Concretely, "without a name" means this — the exact same logic, written two ways:

' A normal, named function — declared on its own, called by name.
Function IncrementNamed(x As Integer) As Integer
    Return x + 1
End Function
Console.WriteLine(IncrementNamed(1))

' The same logic as a lambda — no name, declared inline as part of
' a Dim statement, and invoked through whatever variable holds it.
Dim incrementLambda = Function(x) x + 1
Console.WriteLine(incrementLambda(1))
2
2

Both produce identical results — the lambda isn't a different mechanism, it's the same kind of function with the declaration and the "name to call it by" collapsed into one inline expression. You build one with the same Function/Sub keywords as a normal procedure:

Dim isEven = Function(n As Integer) n Mod 2 = 0
Console.WriteLine(isEven(4))
Console.WriteLine(isEven(5))
True
False

Real, verified usage — both are lambdas passed directly as an argument, never given a name at all:

Dim isAnyCheckedPlatformIndicator As Boolean = cblPlatformIndicator.Items.Cast(Of ListItem)().Any(Function(item) item.Selected)
Dim countries = service.GetCountries().Where(Function(c) c.Id = ddlCountry.SelectedValue)

Module: BackOffice/Web · File: WebForms/DealerCreate.aspx.vb:98,389

The exact same shape as C#'s lambdas — different keyword, same idea C# Fundamentals' Collections & LINQ lesson used x => x.Something. VB.NET's Function(x) x.Something is the same concept — an inline, unnamed function — spelled with a keyword instead of an arrow. .Where(Function(c) c.Id = ...) and C#'s .Where(c => c.Id == ...) compile to functionally the same thing.
The wrong scenario: forcing too much into one A single-line lambda's body must be exactly one expression that produces a value — not a series of statements. This does not compile: 
' Multiple statements inside a single-line lambda — not valid syntax.
Dim invalid = Function(x) Console.WriteLine(x) : x + 1
VB.NET does have a real multi-line lambda form (Function(x) ... End Function, spanning several lines with a proper Return), but the moment a lambda needs several statements and its own local variables to express its logic, that's usually the sign the logic deserves a real, named method instead — referenced with AddressOf where a delegate is needed — rather than growing an inline lambda into something hard to read at a glance.

VB.NET's second option: query syntax, the same LINQ written like SQL

Everything above is method syntax — chained .Where(...)/.Select(...) calls, same as C#. VB.NET also has query syntax: From/Where/Order By/Select keywords that read like a SQL statement, compiling down to the exact same method calls underneath. Side by side, on a simple case, before the real production one:

Dim numbers = {10, 25, 600, 15}

' Method syntax
Dim bigMethod = numbers.Where(Function(n) n > 20).OrderBy(Function(n) n)

' Query syntax — same filter, same sort, same result
Dim bigQuery = From n In numbers
               Where n > 20
               Order By n

For Each n In bigQuery
    Console.WriteLine(n)
Next
25
600

This isn't a simplified toy version of the idea — the SQL-shaped syntax is real, used in production, for a query with more steps than the one above:

ddlWalletType.DataSource = (From item In [Enum].GetValues(GetType(EnumWalletType))
                            Where CType(item, Integer) <> EnumWalletType.Consignment
                            Order By CType(item, Integer)
                            Select New With {.Text = item.ToString(), .Value = CType(item, Integer)})

Module: BackOffice/Web · File: WebForms/DealerCreate.aspx.vb:539-542

Reading it clause by clause: From item In [Enum].GetValues(...) declares a range variable, item, iterating the source — the query-syntax equivalent of the lambda parameter in method syntax (compare to n in the simple example above, or item in .Any(Function(item) ...)). Where filters, exactly like .Where(...). Order By sorts, corresponding to .OrderBy(...). Select defines the shape of each result.

Anonymous types: what that Select clause is actually constructing

New With {.Text = item.ToString(), .Value = CType(item, Integer)} creates an object of a type that has no name anywhere in the code — VB.NET generates one on the fly, with exactly the properties listed (Text, Value), typed from whatever each expression evaluates to. This exists specifically for cases like this one: the query's result only needs to exist briefly, to bind to ddlWalletType's DataSource — defining a real, named class just to hold two properties for one local use would be pure ceremony.

The wrong scenario: when an anonymous type stops being the right tool 
Function BuildWalletOption(item As Object) As ???  ' <- there is no name to write here
    Return New With {.Text = item.ToString(), .Value = CType(item, Integer)}
End Function
The moment a shape needs to be passed between methods, stored in a field, or referred to by a real type name anywhere else, an anonymous type stops working — there's no type name that could legally fill in the ??? above, because the type was never given one. An anonymous type's "type" only has meaning within the single method (and any lambdas nested inside it) that created it. Once a shape needs to cross a method boundary like this, define an actual class instead.

Filtering one collection against another: three real idioms, and one real trap

A recurring shape in BackOffice: given a full list and a list of items to exclude, produce the remainder. This isn't a special LINQ feature — it's an application of Where you already know, plus two variants worth recognizing by name.

The dominant idiom, seen repeated across every "sync a multi-select against a saved list" page in BackOffice — filter one collection by whether each element is absent from another:

Dim addedStore = stores.Where(Function(b) Not UserStore.Contains(b)).ToList()
Dim removedStores = UserStore.Where(Function(b) Not stores.Contains(b)).ToList()

Module: BackOffice/Web · File: WebForms/UserEdit.aspx.vb:840-841 (the identical shape repeats for dealers/suppliers in the same file, and in DealerEdit.aspx.vb, CompanyEdit.aspx.vb, SupplierEdit.aspx.vb, RoleEdit.aspx.vb, ProductEdit.aspx.vb)

Read it as one sentence: "keep every b from stores where UserStore does not contain it." Not ...Contains(...) is just a boolean lambda like any other — nothing about it is exclusion-specific syntax; it's the general-purpose Where you already know, applied to a negated membership test.

A second idiom for the same-looking problem: Except computes a real set difference Microsoft's Enumerable.Except reference defines it precisely: "The set difference of two sets is defined as the members of the first set that don't appear in the second set." That's functionally the same outcome as Where(Function(x) Not other.Contains(x)) for this shape — but real, verified usage in this codebase reaches for it specifically when computing a diff between two versions of a list, not a general exclusion filter: 
lstSerialNumber = lstFullList.Except(lstStocks.Select(Function(s) s.SerialNo)).ToList()

Module: BackOffice/Web · File: WebForms/StockAllocationCreate.aspx.vb:267

Prefer Where(Function(x) Not other.Contains(x)) when the intent is "filter this list" — it reads as a filter. Reach for Except when the intent is genuinely "what's different between these two sets" — it reads as a diff. Both compile to comparable performance; the choice here is about which one tells the next reader what the code is actually for.
A third variant: chained <>, for a tiny fixed blacklist instead of a dynamic list When there are only one or two hardcoded values to exclude — not a runtime list — this codebase skips Contains entirely and just chains inequality checks: 
Where service.ServiceCode <> TerminalContentServices.WLET AndAlso
      service.ServiceCode <> TerminalContentServices.RCAL

Module: BackOffice/Web · File: WebForms/PaymentEnquiry.aspx.vb:567-568

This doesn't scale past two or three values (each new exclusion is another AndAlso clause) — the moment a third or fourth exclusion shows up, or the excluded set might change without a code change, that's the signal to switch to a real list and Where(Function(x) Not excludeList.Contains(x)) instead.

Reducing overhead: the same exclusion filter, made structurally faster

The dominant exclusion idiom above — Where(Function(b) Not otherList.Contains(b)) — has a real cost hiding in it once the lists get large: List(Of T).Contains scans the list from the start until it finds a match (or reaches the end). Run inside a Where over every element of the first list, that's a scan of the second list for every single element of the first — the total work grows with the size of both lists multiplied together, not just added.

Official documentation This is exactly the gap Dictionary(Of TKey, TValue)'s own reference (covered in Syntax, Types & Option Strict) describes — key lookup "close to O(1), because the class is implemented as a hash table." Microsoft's own HashSet<T> reference confirms the same underlying mechanism applies to membership testing specifically: "The HashSet<T> class is based on the model of mathematical sets and provides high-performance set operations similar to accessing the keys of the Dictionary<TKey,TValue>... collections." HashSet(Of T).Contains gets the same near-constant-time lookup a Dictionary key lookup gets — it just checks membership instead of retrieving an associated value.

This codebase already uses exactly this optimization — just not, currently, in the repeated exclusion-diff idiom above:

Dim disallowedServiceTypes As New HashSet(Of ServiceProviderType) From {...}
...
If disallowedServiceTypes.Contains(row.SalesCommissionMarginRates?.ServiceTypeId) Then

Module: BackOffice/Web · File: WebForms/CommissionEdit.aspx.vb:193,202 (HashSet also used for status-transition validation in StockAllocation.aspx.vb and deduplication in StockAllocationCreate.aspx.vb:344)

The same fix applied to the real exclusion pattern The repeated idiom from earlier — stores.Where(Function(b) Not UserStore.Contains(b)), and the identical shape in CompanyEdit.aspx.vb, DealerEdit.aspx.vb, SupplierEdit.aspx.vb, RoleEdit.aspx.vb, and ProductEdit.aspx.vb — all call .Contains against a plain List(Of Integer). Converting just the list being checked into a HashSet(Of Integer) first, with no other change to the logic, turns every one of those .Contains calls from a linear scan into a near-constant-time lookup: 
' Same result, same readability — one extra step before the filter runs.
Dim userStoreSet As New HashSet(Of Integer)(UserStore)
Dim addedStore = stores.Where(Function(b) Not userStoreSet.Contains(b)).ToList()
For a handful of items the difference is invisible either way — this only becomes worth doing once the lists genuinely get large (hundreds or thousands of stores/dealers/users), which is exactly the kind of change worth making the next time one of these six files is touched anyway, not necessarily a change worth making in isolation today.

Join and Group Join: combining two collections by a shared key, not filtering one

Filtering (above) asks "which elements of this one collection survive a condition." Join asks a different question: "for each element of one collection, what's the matching element of a completely different collection." Real, verified production usage — combining stores with the dealer each one belongs to:

stores = stores.Join(dealers, Function(s) s.DealerId, Function(d) d.Id,
                      Function(Store, Dealer) New With {Store, Dealer})

Module: BackOffice/Web · File: WebForms/OfflineSalesList.aspx.vb:100

Official documentation Microsoft's own Enumerable.Join reference names the SQL parallel directly: "A join refers to the operation of correlating the elements of two sources of information based on a common key... In relational database terms, the Join method implements an inner equijoin." Function(s) s.DealerId and Function(d) d.Id are the two key selectors — one per side — and Function(Store, Dealer) New With {Store, Dealer} is the result selector, building one combined anonymous object (see above) per matching pair. Only stores with a matching dealer appear in the result at all — an "inner" join, exactly like SQL's default JOIN, not a LEFT JOIN.

Query syntax has the same operation spelled differently, and this codebase uses that form even more — combining a user with their company-level role assignment, keeping every user even when no match exists (the query-syntax Group Join ... Into Group shape, not plain Join):

Group Join compUser In companyUsers On user.Id Equals compUser.UserId Into Group

Module: BackOffice/Web · File: WebForms/CompanyEdit.aspx.vb:202 (the identical shape repeats in Dealer.aspx.vb, DealerEdit.aspx.vb, ProductEdit.aspx.vb, PurchaseOrderEdit.aspx.vb, PaymentEnquiry.aspx.vb)

Into Group is what makes this a group join rather than a plain one: instead of producing one flat result row per matching pair, each user gets a Group — the (possibly empty) collection of every compUser that matched. This is the query-syntax route to what Join's inner-only behavior can't do on its own: keeping every element from the first collection even when zero matches exist on the second.

The Array/IEnumerable trap: why [Enum].GetValues(...).Where(...) doesn't compile

[Enum].GetValues(GetType(T)) returns the non-generic System.Array type — and Array only implements the non-generic IEnumerable, not IEnumerable(Of T). Where, like every LINQ method, is written against IEnumerable(Of T), so it simply isn't visible on a plain Array-typed variable — this is a real, easy compile error to hit, not a hypothetical one.

Official documentation Microsoft's Enumerable.Cast<TResult> reference names this exact bridge: "The Cast<TResult>(IEnumerable) method enables the standard query operators to be invoked on non-generic collections by supplying the necessary type information. For example, ArrayList does not implement IEnumerable<T>, but by calling Cast<TResult>(IEnumerable) on the ArrayList object, the standard query operators can then be used." The same fix applies to the non-generic Array that [Enum].GetValues returns.

Real, verified production code doing exactly this — three lines, each demonstrating a different piece of what's been covered in this lesson and the last one:

Dim arrExcludedActions As EnumAllocateAction() = {EnumAllocateAction.Provision, EnumAllocateAction.ReActivate, EnumAllocateAction.Suspend}
Dim arrAllocationActions As IEnumerable(Of EnumAllocateAction) = [Enum].GetValues(GetType(EnumAllocateAction)).Cast(Of EnumAllocateAction)()
Dim arrFilteredAllocationActions As EnumAllocateAction() = arrAllocationActions.Where(Function(iAllocationAction) Not arrExcludedActions.Contains(iAllocationAction)).ToArray()

Module: BackOffice/Web · File: WebForms/StockAllocationCreate.aspx.vb:502-504

Line by line: arrExcludedActions is a genuine array literal (vb-01's array-type rule), correctly typed EnumAllocateAction(). arrAllocationActions is the bridge — .Cast(Of EnumAllocateAction)() turns the non-generic Array into an IEnumerable(Of EnumAllocateAction), which is why it's declared As IEnumerable(Of EnumAllocateAction), not As Array. arrFilteredAllocationActions applies the exclusion idiom from above, then .ToArray() converts the result back into a real array.

The wrong way: declaring the Cast(Of T)() result As Array undoes the fix 
' Looks like a small, harmless simplification — it isn't.
Dim arrAllocationActions As Array = [Enum].GetValues(GetType(EnumAllocateAction)).Cast(Of EnumAllocateAction)()
.Cast(Of EnumAllocateAction)() returns IEnumerable(Of EnumAllocateAction), which is not a System.Array — they're unrelated types, one a lazy enumerator and the other a concrete array class. With Option Strict On this is a compile error; with Option Strict Off (BackOffice's real default — see vb-01), it compiles but throws an InvalidCastException the moment it runs. And even setting that aside, re-typing the variable As Array puts you right back where you started: .Where won't be visible on it, for the exact same reason it wasn't visible on the original [Enum].GetValues(...) call. The variable name (arr...) staying the same across the fix is itself worth noticing — this codebase's Hungarian notation is a loose, approximate convention (per Fiuu Code Conventions → Naming), not a strictly type-accurate one; the real file above keeps the arr prefix on arrAllocationActions even though its actual declared type is IEnumerable(Of T), not an array.

Best practice

  • Reach for Where(Function(x) Not excludeList.Contains(x)) for a general exclusion filter; Except specifically when computing a diff between two versions of a list. Both work for the same shape of problem, but each signals a different intent to the next reader.
  • Reach for chained <>/AndAlso only for a tiny, genuinely fixed blacklist (one or two values). Switch to a real list and Contains the moment a third exclusion appears or the set might change at runtime.
  • Bridge a non-generic Array/IEnumerable with .Cast(Of T)() before calling any LINQ method on it — and keep the resulting variable typed as IEnumerable(Of T), never As Array. Re-typing it back to Array reintroduces the exact error the cast was meant to fix.
  • Reach for query syntax when a query has several chained operations (filter, then sort, then shape) and would read as a long, nested chain in method syntax — the SQL-like structure keeps each step on its own line, in the same order SQL developers already read intuitively.
  • Reach for method syntax for a single operation (one .Where(...), one .Any(...)) — query syntax's From/Select ceremony isn't worth it for one clause.
  • Keep lambda bodies to one expression. A lambda that needs several statements and local variables to express its logic is a sign the logic deserves a real, named method instead, referenced with AddressOf.
  • Promote an anonymous type to a real class the moment it needs to leave the method it was created in — as a return type, a field, or a parameter.
  • Convert the "other" side of a Where(Function(x) Not other.Contains(x)) exclusion filter into a HashSet(Of T) once the lists involved are large enough for it to matter. The filter logic and its readability don't change at all — only the collection type the repeated .Contains calls run against, turning a linear scan into a near-constant-time lookup.
  • Reach for Join when you need one combined result per matching pair from two collections, and query-syntax Group Join ... Into Group when you need to keep every element from the first collection even without a match. Plain Join silently drops unmatched elements — exactly like a SQL inner join — which is the right behavior sometimes and a real, easy-to-miss bug other times.

Check your understanding

In From item In [Enum].GetValues(...) Where CType(item, Integer) <> EnumWalletType.Consignment ..., what is item?

  • A pre-existing variable declared earlier with Dim.
  • A range variable, introduced by the From clause itself, that represents each element from the source collection in turn — the query-syntax equivalent of a lambda's parameter.
  • A variable created by the Where clause.

Select New With {.Text = item.ToString(), .Value = CType(item, Integer)} — what kind of object does each result actually have?

  • An instance of a real, named class the query looked up automatically.
  • An anonymous type — a compiler-generated type with exactly the properties listed (Text, Value), never given a name in the source code.
  • A Dictionary(Of String, Integer).

A method needs to return the wallet-option shape (.Text/.Value) built earlier in this lesson, so a different method can use it. What has to change?

  • Nothing — write the anonymous type's generated name as the method's return type.
  • A real, named class needs to be defined with those two properties, and the method's return type changed to that class.
  • Wrap it in a Dictionary(Of String, Integer) instead.

A variable holds the result of [Enum].GetValues(GetType(EnumAllocateAction)), declared As Array. Calling .Where(...) on it fails to compile. Why?

  • Because the enum has no values defined yet.
  • Because Array only implements the non-generic IEnumerable, not IEnumerable(Of T) — Where needs the generic interface, so it isn't visible on a plain Array-typed variable.
  • Because Where only works on List(Of T), never on anything else.

Real code declares Dim arrAllocationActions As IEnumerable(Of EnumAllocateAction) = [Enum].GetValues(GetType(EnumAllocateAction)).Cast(Of EnumAllocateAction)(). A well-meaning edit changes the declared type to As Array to "match the variable's arr name." What happens?

  • It breaks — IEnumerable(Of T) and Array are unrelated types, so this is either a compile error or a runtime InvalidCastException, and .Where stops working on it again either way.
  • Nothing changes — Array and IEnumerable(Of T) are interchangeable in VB.NET.
  • VB.NET silently keeps it working because the variable name still starts with arr.

A repeated real pattern in this codebase — stores.Where(Function(b) Not UserStore.Contains(b)) — checks UserStore.Contains(b) once per element of stores, where UserStore is a plain List(Of Integer). Why does converting UserStore to a HashSet(Of Integer) first make this faster, without changing the filter's logic at all?

  • A List(Of T).Contains call scans the list linearly every time; a HashSet(Of T).Contains call uses the same near-constant-time hash-table lookup a Dictionary key lookup gets.
  • It changes how many times the Where lambda itself executes.
  • It makes the results come back in a guaranteed sorted order.

Real code joins stores to dealers with stores.Join(dealers, Function(s) s.DealerId, Function(d) d.Id, ...). A store's DealerId doesn't match any dealer in the dealers collection. What happens to that store in the result, per Microsoft's own Join documentation?

  • It's silently excluded from the result entirely — Join implements an inner join, which only includes elements that have a match on the other side.
  • It appears in the result with the dealer fields set to Nothing.
  • It throws a runtime exception, since every store is expected to have a matching dealer.
