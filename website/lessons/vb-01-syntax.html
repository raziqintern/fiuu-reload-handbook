VB.NET Fundamentals

Syntax, Types & Option Strict

Where this fits — corrected An earlier version of this track claimed reload has "zero VB.NET" because class-library is C#. That was true of class-library alone and false about reload as a whole: the entire BackOffice WebForms UI — the app most of the real bugs in the Debugging Reload track happen on — is written in VB.NET (.aspx.vb code-behind, 1,000+ files). If your work touches BackOffice at all, this track is not optional background reading — it's what the code in front of you is written in.

VB.NET and C# compile to the same underlying .NET runtime and can do almost everything the same way — but VB.NET has its own real idioms (explicit MustOverride/Overloads keywords, a Handles clause for event wiring, per-project type-safety switches) that don't map onto a single C# keyword, and this specific codebase leans on several of them. This track covers those on their own terms, not just as a C# translation exercise.

Option Strict, Option Explicit, Option Infer — three independent switches, and this codebase runs with one of them off

These three compiler options control how forgiving VB.NET is about types, and each is set independently — knowing all three exist, and which combination a given project actually uses, matters more than memorizing what each one does in isolation:

OptionWhen OnWhen Off
Option ExplicitEvery variable must be declared before use (a typo'd variable name is a compile error)An undeclared variable is silently created on first use — On is the VB.NET default project-wide
Option StrictNarrowing/implicit type conversions (e.g. Object to String, Double to Integer) must be written explicitly, and late binding (calling a member on an Object-typed variable without knowing at compile time whether it exists) is a compile errorThe compiler silently inserts narrowing conversions and allows late binding — errors that would be compile-time with Strict On instead surface as a runtime exception, or don't surface at all

Real, verified: BackOffice's own project file runs with Option Strict Off Fiuu.App.BackOffice.Web.vbproj sets <OptionExplicit>On</OptionExplicit>, <OptionStrict>Off</OptionStrict>, and <OptionInfer>On</OptionInfer> at the project level — this is the default every hand-written .aspx.vb file in BackOffice inherits unless it declares its own Option Strict On at the top (most don't). The auto-generated *.designer.vb files are the exception: they each explicitly declare Option Strict On + Option Explicit On locally, overriding the project default just for that one generated file.

Practically: in most BackOffice hand-written code, a narrowing conversion that would be a compile error in a stricter project instead either converts silently (sometimes losing data, e.g. a Double truncated into an Integer) or throws an InvalidCastException at runtime — the compiler won't catch it for you ahead of time. This is a real, structural reason bugs here can surface as a runtime type error instead of a build failure; treat any type conversion in this codebase as unverified by the compiler unless you've confirmed the specific file opts into Option Strict On.

The concept: a declaration statement can name a shared type once for a whole list

Dim's grammar isn't "one name, one type" — it's a comma-separated list of variable names, where a name that has no As clause of its own inherits the type of the next one that does. This is a general grammar rule about how the statement parses, not a special case for any particular type.

Official documentation Microsoft's Dim Statement reference, "Declaring multiple variables" section, states it exactly: "You can specify different data types for different variables by using a separate As clause for each variable you declare. Each variable takes the data type specified in the first As clause encountered after its variablename part." Its own example: Dim a, b, c As Single, x, y As Double, i As Integer — a, b, c are all Single; x, y are both Double.

Real, verified applications of this same rule in BackOffice — each is one instance of the identical grammar, just with a different shared type:

Dim iQty, iMaxQty As Integer
Dim dtStartDate, dtEndDate As DateTime
Dim sM2MServiceProviderColumnName, sM2MSIMCardSerialNoColumnName As String

Module: BackOffice/Web · Files: WebForms/OfflineSalesCreate.aspx.vb:147; WebForms/ReportStockMovementSummary.aspx.vb:193; WebForms/M2MSIMCardSerialNoBulkCreate.aspx.vb:67

Why this specific rule is worth knowing explicitly: VB6 parsed the same-looking line differently In classic VB6, Dim x, y As Integer only gave Integer to y — x silently became a Variant (VB6's untyped catch-all), with no error and no warning. VB.NET's grammar (quoted above) is what actually changed: every name now resolves to a real type via the next As clause, with no untyped fallback in the language at all. If you ever read genuinely old VB6 code (not VB.NET) side-by-side with this codebase, don't assume identical syntax means identical behavior — the grammar itself was revised, not just cleaned up stylistically.

The concept: an array is a type of its own, built from any other type

This is the root idea everything below is one instance of — it's not a String-specific quirk, it's a general rule of the VB.NET type system: for any type T, T() is a distinct type meaning "an array of T." This applies uniformly — Integer and Integer(), Boolean and Boolean(), String and String(), even a class you wrote yourself and an array of it, are all the same relationship, every time. A single T holds one value; T() holds a reference to an ordered, indexed collection of them. Learn this once as a general mechanism and you already know how it works for every type in the language — there's nothing extra to learn per-type.

Official documentation Microsoft's own Dim Statement reference states the rule directly: "To specify that a variable holds an array, follow its variablename immediately with parentheses." The dedicated Arrays in Visual Basic guide confirms the two declaration positions are fully interchangeable and shows the same construction applied across multiple types — Integer, Double, String — not as separate features, but as the one array mechanism used consistently.

Two syntax positions, same meaning — VB.NET lets the array parentheses sit on either the type or the variable name:

' Both lines declare exactly the same thing: a variable holding
' a reference to an array of Integer. Try changing the type in
' both places — Boolean, String, Double — the rule doesn't change.
Dim scoresA As Integer() = {10, 20, 30}
Dim scoresB() As Integer = {10, 20, 30}

Console.WriteLine(scoresA(1))
Console.WriteLine(scoresB(1))
Console.WriteLine(scoresA.GetType().Name)
20

The same rule, three different types — proving it's general, not String-specific

Dim flags As Boolean() = {True, False, True}      ' an array of Boolean
Dim prices As Double() = {9.9, 12.5, 3.0}          ' an array of Double
Dim names As String() = {"Alice", "Bob"}           ' an array of String

Nothing about the array mechanism changes between these three lines except which type comes before the () — that's the whole concept. Once you've internalized this, a method returning Boolean() or Double() is exactly as unsurprising as one returning String().

Real application of this rule in BackOffice 
Dim names As String() = [Enum].GetNames(GetType(Fiuu.CEPP.Models.Interfaces.EnumVoidSupportType))
Dim arrEmail As String() = Split(sEmailAddress, ";")

Module: BackOffice/Web · File: WebForms/DealerCreate.aspx.vb:512,553

[Enum].GetNames(...) and Split(...) both return String() because "a list of strings" is what they fundamentally produce — an enum's names, or a delimited value's pieces. This is the general array rule appearing in real code, not a special case of it.
What actually breaks when the distinction is missed Passing a String() where a method expects a plain String (or vice versa) is a real type mismatch — with Option Strict On, the compiler catches it. With Option Strict Off (BackOffice's real project default — see above), some of these mismatches compile anyway and either fail at runtime or silently call .ToString() on the array, producing the literal text System.String[] instead of the values you meant. Seeing "System.String[]" anywhere in output or a log is the exact signature of this — reach for String.Join(", ", arr) when you want the array's contents rendered as one string, for any array type, not just String().

A sub-concept of arrays: sizing — the number in parentheses is the highest index, not the count

This only applies once you already have an array type (above) — it's about how big one is, not whether something is an array at all. Per the same official Arrays guide: "When you use Visual Basic syntax to define the size of an array, you specify its highest index, not the total number of elements." VB.NET arrays are always zero-based, so Dim scores(9) As Integer creates 10 elements, indices 0 through 9 inclusive — this is documented, consistent behavior, not an edge case:

Dim scores(9) As Integer
Console.WriteLine("Length: " & scores.Length)
Console.WriteLine("Last valid index: " & scores.GetUpperBound(0))
Length: 10
Last valid index: 9

This generalizes exactly like the type rule above: Dim buffer(255) As Byte is a 256-byte buffer regardless of which type sits before it — the "N means N+1 elements" rule is a property of VB.NET array declaration syntax itself, not of Byte specifically. Getting this off by one when translating a size from a spec, or from C# (where new byte[256] unambiguously means 256), is a real, easy mistake in either direction.

Static — a local variable that survives past the end of its own method

This is a different axis from where a variable is visible (scope) — it's about how long it continues to exist (lifetime). By default in VB.NET, as in nearly every language, a local variable's lifetime is tied to its scope: it's created on entering its procedure and destroyed on leaving it. Static decouples the two — the variable's scope stays local to the one procedure, but its lifetime extends far beyond a single call.

Official documentation Microsoft's Dim Statement reference, "Static local variable lifetime" section, specifies exactly how long: for a procedure in a plain module, the variable is "initialized the first time the procedure is called" and "stops existing when your program stops execution." For a non-Shared procedure in a class, it lives only as long as that specific object instance does. 
Sub TrackCalls()
    Static callCount As Integer = 0
    callCount += 1
    Console.WriteLine("This method has been called " & callCount & " time(s)")
End Sub

Sub Main()
    TrackCalls()
    TrackCalls()
    TrackCalls()
End Sub
This method has been called 1 time(s)
This method has been called 2 time(s)
This method has been called 3 time(s)
The initializer only runs once — a common source of confusion callCount As Integer = 0 only executes the first time TrackCalls is ever called; on every later call, that line is skipped entirely and callCount keeps whatever value it already had. This is fundamentally different from a normal local variable, whose initializer re-runs on every single call. A Static local is effectively a private field in disguise — scoped so only this one method can see it, but living exactly as long as a field would.

Real-world use is narrow and specific: a call counter, a one-time-setup flag inside a frequently-called method, memoizing an expensive calculation across calls to the same method on the same instance. Reach for an actual class-level field instead when more than one method needs to see or share the value — Static is deliberately private to the one method it's declared in.

Try it yourself

& for string concatenation is the one habit that trips up C# developers reading VB.NET most often:

Module Program
    Sub Main()
        Dim amount As Integer = 25
        Dim feeRate As Double = 0.02
        Dim fee As Double = amount * feeRate

        Console.WriteLine("Amount: " & amount & ", Fee: " & fee)
    End Sub
End Module
Amount: 25, Fee: 0.5

Best practice

  • Match whatever casing convention the surrounding file already uses. VB.NET is case-insensitive, so amount and Amount are the same identifier to the compiler — but a file mixing both looks like two different variables to a human reader, which is exactly the confusing situation case-insensitivity can quietly create.
  • In a new BackOffice file, add Option Strict On at the top yourself if the change is substantial enough to justify it — it turns silent, potentially lossy conversions into compile errors you fix immediately instead of runtime surprises later. Don't retrofit it onto an existing large file casually: turning it on can surface a wave of pre-existing conversion warnings unrelated to your change.

Better ways

The comment marker in Fiuu Code Conventions → Comment Style's real example — // TODO: might not be correct. If you ever do this kind of port yourself, treat it as a rewrite opportunity, not a find-and-replace exercise — the two languages' idioms (exception-only control flow vs. VB's historical On Error style, for one) don't map one-to-one.

  • A single semicolon-delimited string, unchanged.
  • A reference to an array of strings — one element per semicolon-separated piece of the original text.
  • The number of semicolons found in the string.

Dim scores(9) As Integer — how many elements does this array actually have? (just the number)

A method has Static callCount As Integer = 0 as its first line, then increments callCount. It's called three times in a row. What does the third call see as the initial value of callCount, before the increment?

  • 0 — the initializer re-runs on every call, resetting it.
  • 2 — the value left over from the two previous calls, since the = 0 initializer only ran once, on the first call ever.
  • It throws an exception, since the variable was already declared on a previous call.

A BackOffice .aspx.vb file has no Option Strict declaration of its own. What governs whether risky implicit type conversions are allowed in that file?

  • VB.NET always defaults to Option Strict On regardless of project settings.
  • The project file's own <OptionStrict> setting — verified as Off for BackOffice — which every file inherits unless it overrides it locally.
  • Whether the corresponding .aspx markup file has strict typing enabled.

Why does VB.NET generally prefer & over + for joining strings, even though both compile?

  • & runs measurably faster than +.
  • + is also the numeric addition operator, so & removes any ambiguity about whether you mean addition or concatenation.
  • + only works with numbers, & only works with pre-declared string variables.
