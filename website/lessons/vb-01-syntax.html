VB.NET Fundamentals

Syntax, Types & Option Strict

Where this fits
  • The BackOffice WebForms UI — where most of the real bugs in Debugging Reload happen — is written in VB.NET (.aspx.vb, 1,000+ files).
  • If your work touches BackOffice at all, this track is what the code in front of you is written in — not optional background reading.

VB.NET and C# share the same .NET runtime and can do almost everything the same way. This track covers VB.NET's own real idioms — MustOverride/Overloads, Handles, per-project type-safety switches — on their own terms, not as a translation exercise.

Option Strict, Option Explicit, Option Infer

Three independent compiler switches. Know all three exist, and which combination a given project uses — that matters more than memorizing each one in isolation.

OptionWhen OnWhen Off
Option ExplicitEvery variable must be declared before use (typo = compile error)Undeclared variable is silently created on first use — On is the VB.NET default project-wide
Option StrictNarrowing conversions (Object→String, Double→Integer) must be explicit; late binding is a compile errorCompiler silently inserts narrowing conversions and allows late binding — errors surface at runtime, or not at all
Option InferDim x = 5 infers IntegerA variable with no As Type is typed Object
Real, verified: BackOffice runs with Option Strict Off
  • Fiuu.App.BackOffice.Web.vbproj sets <OptionExplicit>On</OptionExplicit>, <OptionStrict>Off</OptionStrict>, <OptionInfer>On</OptionInfer> at the project level.
  • Every hand-written .aspx.vb file inherits this unless it declares its own Option Strict On — most don't.
  • Exception: auto-generated *.designer.vb files each explicitly declare Option Strict On + Option Explicit On locally.

Same risky line, compiled twice — only the Option Strict setting differs:

Option Strict Off

Dim o As Object = "not a number"
Dim n As Integer = o   ' narrowing Object -> Integer, no CInt/CType written
Compiles fine. Throws System.InvalidCastException at runtime, the moment
this line actually executes — the compiler had no objection at all.
Option Strict On

Dim o As Object = "not a number"
Dim n As Integer = o   ' same line, Option Strict On this time
Does not compile: "Option Strict On disallows implicit conversions from
'Object' to 'Integer'." Caught before the code ever runs.
  • In most BackOffice code (Option Strict Off), this exact mistake compiles and ships, then fails as a runtime InvalidCastException.
  • Treat any type conversion as unverified by the compiler unless the specific file opts into Option Strict On.

Dim Statement: Declaring Multiple Variables

  • Dim's grammar is a comma-separated list of names — a name with no As clause inherits the type of the next one that has one.
  • General grammar rule, not a special case for any particular type.
Official documentation Microsoft's Dim Statement reference: "You can specify different data types for different variables by using a separate As clause for each variable you declare. Each variable takes the data type specified in the first As clause encountered after its variablename part." Example: Dim a, b, c As Single, x, y As Double, i As Integer — a, b, c are Single; x, y are Double.

Real, verified BackOffice usage — same grammar, different shared type each time:

Dim iQty, iMaxQty As Integer
Dim dtStartDate, dtEndDate As DateTime
Dim sM2MServiceProviderColumnName, sM2MSIMCardSerialNoColumnName As String

Module: BackOffice/Web · Files: WebForms/OfflineSalesCreate.aspx.vb:147; WebForms/ReportStockMovementSummary.aspx.vb:193; WebForms/M2MSIMCardSerialNoBulkCreate.aspx.vb:67

VB6 parsed this differently
  • Classic VB6: Dim x, y As Integer only gave Integer to y — x silently became Variant, no error.
  • VB.NET fixed this: every name resolves to a real type via the next As clause, no untyped fallback.
  • Don't assume identical VB6/VB.NET syntax means identical behavior — the grammar itself changed.

Arrays

  • Root rule: for any type T, T() is a distinct type meaning "an array of T." Not a String-specific quirk.
  • Applies uniformly: Integer/Integer(), Boolean/Boolean(), String/String(), even your own classes.
  • A single T holds one value; T() holds a reference to an ordered, indexed collection of them.
Official documentation Microsoft's Dim Statement reference: "To specify that a variable holds an array, follow its variablename immediately with parentheses." The Arrays in Visual Basic guide confirms both declaration positions are interchangeable, across Integer, Double, String — one mechanism, not per-type features.

Two syntax positions, same meaning:

' Both lines declare exactly the same thing: a variable holding
' a reference to an array of Integer. Try changing the type in
' both places — Boolean, String, Double — the rule doesn't change.
Dim scoresA As Integer() = {10, 20, 30}
Dim scoresB() As Integer = {10, 20, 30}

Console.WriteLine(scoresA(1))
Console.WriteLine(scoresB(1))
Console.WriteLine(scoresA.GetType().Name)

Arrays of Any Type

Dim flags As Boolean() = {True, False, True}      ' an array of Boolean
Dim prices As Double() = {9.9, 12.5, 3.0}          ' an array of Double
Dim names As String() = {"Alice", "Bob"}           ' an array of String

Nothing changes between these three lines except the type before (). A method returning Boolean() is exactly as unsurprising as one returning String().

What breaks when the distinction is missed
  • Passing String() where a plain String is expected is a real type mismatch.
  • Option Strict On: compiler catches it. Option Strict Off (BackOffice's default): some mismatches compile anyway, either failing at runtime or silently rendering System.String[] instead of the values.
  • Seeing "System.String[]" in output/logs is the exact signature of this. Fix: String.Join(", ", arr).

Array Bounds and Size

  • Per the official Arrays guide: "When you use Visual Basic syntax to define the size of an array, you specify its highest index, not the total number of elements."
  • VB.NET arrays are zero-based: Dim scores(9) As Integer creates 10 elements, indices 0–9.
Dim scores(9) As Integer
Console.WriteLine("Length: " & scores.Length)
Console.WriteLine("Last valid index: " & scores.GetUpperBound(0))
Length: 10
Last valid index: 9
  • Generalizes to every type: Dim buffer(255) As Byte is a 256-byte buffer.
  • Easy off-by-one trap when translating a size from a spec, or from C# (new byte[256] unambiguously means 256).

Static Local Variables

  • Different axis from scope (where visible) — this is about lifetime (how long it exists).
  • By default, a local variable's lifetime is tied to its scope: created on entry, destroyed on exit.
  • Static decouples the two: scope stays local, lifetime extends far beyond one call.
Official documentation Microsoft's Dim Statement reference, "Static local variable lifetime": in a plain module, the variable is "initialized the first time the procedure is called" and "stops existing when your program stops execution." In a class's non-Shared procedure, it lives only as long as that object instance. 
Sub TrackCalls()
    Static callCount As Integer = 0
    callCount += 1
    Console.WriteLine("This method has been called " & callCount & " time(s)")
End Sub

Sub Main()
    TrackCalls()
    TrackCalls()
    TrackCalls()
End Sub
This method has been called 1 time(s)
This method has been called 2 time(s)
This method has been called 3 time(s)
The initializer only runs once
  • callCount As Integer = 0 executes only on the first call ever — later calls skip it and keep the existing value.
  • A normal local's initializer re-runs every call; Static doesn't.
  • Effectively a private field in disguise — scoped to one method, but living as long as a field would.
  • Real use is narrow: a call counter, a one-time-setup flag, memoizing a per-instance calculation.
  • Reach for a real class-level field instead once more than one method needs the value.

Objects and Collections

Same declaration grammar, applied to types you define and to generic collection types. Root mechanism: New SomeType(...) calls a constructor and produces an instance.

Object Initializers

Official documentation Microsoft's own Object Initializers reference: "Object initializers provide a simple way to call the constructor of a type and then set the values of some or all properties in a single statement." Its example — Dim cust1 As New Customer With {.Name = "Toni Poe", .City = "Louisville"} — is stated as identical to constructing first, then assigning properties separately. Convenience syntax, not a different mechanism.

Dictionary(Of TKey, TValue)

  • An array/list holds things in order — get an item by position.
  • A Dictionary(Of TKey, TValue) holds things by an arbitrary key — get a value by whatever key it was stored under, regardless of insertion order.
Official documentation Microsoft's own Dictionary<TKey,TValue> reference: "provides a mapping from a set of keys to a set of values" and "Retrieving a value by using its key is very fast, close to O(1), because the Dictionary<TKey,TValue> class is implemented as a hash table." That's the reason to reach for one instead of scanning a List(Of T) — lookup stays fast regardless of size, where a list scan gets slower as it grows.

IEnumerable(Of T) and For Each

  • For Each only works on types implementing the enumerable pattern — that's why Function GetSupplierProducts(...) As IEnumerable(Of ISupplierProducts) is readable at a glance.
Official documentation Microsoft's own IEnumerable<T> reference: "IEnumerable<T> is the base interface for collections in the System.Collections.Generic namespace such as List<T>, Dictionary<TKey,TValue>, and Stack<T>... Collections that implement IEnumerable<T> can be enumerated by using the foreach statement" — VB.NET's For Each is the same mechanism, different keyword. Dictionary is one of these too — loopable with For Each, yielding key/value pairs.

Picking the wrong collection for the job
  • List(Of T) + .Contains(...) or a hand-written loop still works — not a compile error, invisible for a handful of items.
  • Real, measurable cost as the list grows: every lookup walks the list from the start.
  • Dictionary(Of TKey, TValue) keyed on the same identifier turns it near-constant-time. The fix is picking the right collection, not "faster code."
' Same lookup, two collection types — watch what each one is actually good at.
Dim namesList As New List(Of String) From {"TNG", "BILL_PAYMENT", "TICKET"}
Dim namesDict As New Dictionary(Of String, Integer) From {
    {"TNG", 1}, {"BILL_PAYMENT", 2}, {"TICKET", 3}
}

' List: good for "is this value present" / "give me each one in order"
Console.WriteLine(namesList.Contains("TICKET"))
For Each n In namesList
    Console.Write(n & " ")
Next
Console.WriteLine()

' Dictionary: good for "given this key, what's the value" — no scanning

Try it yourself

& for string concatenation is the one habit that trips up C# developers reading VB.NET most often:

Module Program
    Sub Main()
        Dim amount As Integer = 25
        Dim feeRate As Double = 0.02
        Dim fee As Double = amount * feeRate

        Console.WriteLine("Amount: " & amount & ", Fee: " & fee)
    End Sub
End Module
Amount: 25, Fee: 0.5

Best practice

  • Match the surrounding file's casing convention. VB.NET is case-insensitive, so a file mixing amount/Amount looks like two variables to a human reader.
  • Opt new BackOffice files into Option Strict On when the change justifies it. Don't retrofit it onto an existing large file casually — it can surface a wave of pre-existing warnings.
  • Use String.Join to render an array, never string concatenation. String.Join(", ", someArray) is the correct, general-purpose fix for any array type.
  • Reach for Dictionary(Of TKey, TValue) for "find the value for this key," and List(Of T) for "give me every item, in order." A list plus a linear scan for a key lookup is a real, measurable cost once the collection isn't tiny.

Check your understanding

Dim iQty, iMaxQty As Integer — a real line from OfflineSalesCreate.aspx.vb. What type is iQty?

  • Object, since it has no As clause of its own.
  • Integer — VB.NET gives every name in the list the type named at the end, unlike VB6.
  • This doesn't compile — VB.NET requires a separate Dim for each variable.

Dim arrEmail As String() = Split(sEmailAddress, ";") — a real line from DealerCreate.aspx.vb. What does arrEmail actually hold?

  • A single semicolon-delimited string, unchanged.
  • A reference to an array of strings — one element per semicolon-separated piece of the original text.
  • The number of semicolons found in the string.

Dim scores(9) As Integer — how many elements does this array actually have? (just the number)

A method has Static callCount As Integer = 0 as its first line, then increments callCount. It's called three times in a row. What does the third call see as the initial value of callCount, before the increment?

  • 0 — the initializer re-runs on every call, resetting it.
  • 2 — the value left over from the two previous calls, since the = 0 initializer only ran once, on the first call ever.
  • It throws an exception, since the variable was already declared on a previous call.

A BackOffice .aspx.vb file has no Option Strict declaration of its own. What governs whether risky implicit type conversions are allowed in that file?

  • VB.NET always defaults to Option Strict On regardless of project settings.
  • The project file's own <OptionStrict> setting — verified as Off for BackOffice — which every file inherits unless it overrides it locally.
  • Whether the corresponding .aspx markup file has strict typing enabled.

Why does VB.NET generally prefer & over + for joining strings, even though both compile?

  • & runs measurably faster than +.
  • + is also the numeric addition operator, so & removes any ambiguity about whether you mean addition or concatenation.
  • + only works with numbers, & only works with pre-declared string variables.

A method needs to look up a cancellation reason by serial number, potentially across thousands of stock items. Based on the real StockAllocationCreate.aspx.vb code above, which collection type fits, and why?

  • A List(Of String), since it can hold any number of strings.
  • A Dictionary(Of String, String), since the operation is "given this serial number, what's its reason" — a key lookup, not a sequential scan.
  • A fixed-size String() array, since the number of stock items is known in advance.

Dim x As New RazerAccount and Dim y As New PrepayNationGetBalanceRequest With {.CorrelationId = "..."} — both real lines from RazerAccountBalance.aspx.vb. What's actually different between them, per Microsoft's own Object Initializers documentation?

  • Nothing structural — both call New to construct an instance; the With {} form just also sets one property as part of the same statement, equivalent to setting it in a separate line afterward.
  • One is a custom class and the other is a built-in .NET framework type.
  • With {} means the variable is actually an array, not a single object.
