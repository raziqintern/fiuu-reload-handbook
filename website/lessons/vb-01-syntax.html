VB.NET Fundamentals

Syntax, Types & Option Strict

Where this fits — corrected An earlier version of this track claimed reload has "zero VB.NET" because class-library is C#. That was true of class-library alone and false about reload as a whole: the entire BackOffice WebForms UI — the app most of the real bugs in the Debugging Reload track happen on — is written in VB.NET (.aspx.vb code-behind, 1,000+ files). If your work touches BackOffice at all, this track is not optional background reading — it's what the code in front of you is written in.

VB.NET and C# compile to the same underlying .NET runtime and can do almost everything the same way — but VB.NET has its own real idioms (explicit MustOverride/Overloads keywords, a Handles clause for event wiring, per-project type-safety switches) that don't map onto a single C# keyword, and this specific codebase leans on several of them. This track covers those on their own terms, not just as a C# translation exercise.

Option Strict, Option Explicit, Option Infer — three independent switches, and this codebase runs with one of them off

These three compiler options control how forgiving VB.NET is about types, and each is set independently — knowing all three exist, and which combination a given project actually uses, matters more than memorizing what each one does in isolation:

OptionWhen OnWhen Off
Option ExplicitEvery variable must be declared before use (a typo'd variable name is a compile error)An undeclared variable is silently created on first use — On is the VB.NET default project-wide
Option StrictNarrowing/implicit type conversions (e.g. Object to String, Double to Integer) must be written explicitly, and late binding (calling a member on an Object-typed variable without knowing at compile time whether it exists) is a compile errorThe compiler silently inserts narrowing conversions and allows late binding — errors that would be compile-time with Strict On instead surface as a runtime exception, or don't surface at all
Option InferDim x = 5 infers x As Integer without needing As Integer written outA variable declared without As Type is typed Object instead of inferred
Real, verified: BackOffice's own project file runs with Option Strict Off Fiuu.App.BackOffice.Web.vbproj sets <OptionExplicit>On</OptionExplicit>, <OptionStrict>Off</OptionStrict>, and <OptionInfer>On</OptionInfer> at the project level — this is the default every hand-written .aspx.vb file in BackOffice inherits unless it declares its own Option Strict On at the top (most don't). The auto-generated *.designer.vb files are the exception: they each explicitly declare Option Strict On + Option Explicit On locally, overriding the project default just for that one generated file.

Practically: in most BackOffice hand-written code, a narrowing conversion that would be a compile error in a stricter project instead either converts silently (sometimes losing data, e.g. a Double truncated into an Integer) or throws an InvalidCastException at runtime — the compiler won't catch it for you ahead of time. This is a real, structural reason bugs here can surface as a runtime type error instead of a build failure; treat any type conversion in this codebase as unverified by the compiler unless you've confirmed the specific file opts into Option Strict On.

Declaring several variables in one Dim — and the VB6 trap this fixed

VB.NET lets one Dim declare several variables of the same type, comma-separated, with the type named once at the end. Real, verified examples:

Dim iQty, iMaxQty As Integer
Dim dtStartDate, dtEndDate As DateTime
Dim sM2MServiceProviderColumnName, sM2MSIMCardSerialNoColumnName As String

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/OfflineSalesCreate.aspx.vb:147; ReportStockMovementSummary.aspx.vb:193; M2MSIMCardSerialNoBulkCreate.aspx.vb:67

In Dim iQty, iMaxQty As Integer, both iQty and iMaxQty are Integer — the type after the last name in the list applies to every name before it that doesn't have its own As clause. You can also mix explicit types in one statement: Dim x As Long, i, j, k As Integer, s As String declares x as Long, i/j/k as Integer, and s as String — each name takes the type from the next As clause that actually follows it.

Why this is worth knowing explicitly: VB6 did something dangerously different In classic VB6, Dim x, y As Integer only gave Integer to y — x silently became a Variant (VB6's untyped catch-all), with no error and no warning. VB.NET fixed this specific footgun: every name in a comma-separated Dim gets a real, specific type, never an untyped fallback. If you ever read genuinely old VB6 code (not VB.NET) side-by-side with this codebase, don't assume the same line means the same thing in both — this is one of the sharpest behavioral differences between the two, not just a syntax tweak.

String vs. String() — a single value vs. an array of them

String and String() are as different as int and int[] in C# — one is a single value, the other is a collection of them — but VB.NET's syntax makes the two easy to visually confuse, especially since the array parentheses can legally go on either the type or the variable name. Real, verified examples, both forms:

Dim names As String() = [Enum].GetNames(GetType(Fiuu.CEPP.Models.Interfaces.EnumVoidSupportType))
Dim arrEmail As String() = Split(sEmailAddress, ";")

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/DealerCreate.aspx.vb:512,553

Dim names As String() and the equivalent-but-less-common Dim names() As String declare exactly the same thing: a variable holding a reference to an array of strings, not a string itself. Split(...) and [Enum].GetNames(...) both return String(), never a plain String — this is precisely why splitting a semicolon-delimited email list needs an array-typed variable to catch the result.

What actually goes wrong when this gets confused Passing a String() where a method expects a plain String (or vice versa) is a real, catchable type mismatch — with Option Strict On, it's a compile error. With Option Strict Off (BackOffice's actual project default — see above), some of these mismatches can still compile and fail at runtime instead, or silently call .ToString() on the array (producing the unhelpful literal text System.String[] rather than the joined values you probably meant). If you ever see the literal string "System.String[]" show up somewhere in output or a log, that's the exact signature of a String() being stringified instead of joined — reach for String.Join(", ", arr) when you actually want the array's contents as one string.

Array bounds: the number in the parentheses is the highest index, not the size

A classic, still-relevant VB.NET trap: Dim scores(9) As Integer does not create an array of size 9 — the number in parentheses is the array's upper bound (the highest valid index), and VB.NET arrays are always zero-based. Dim scores(9) As Integer creates 10 elements, indices 0 through 9 inclusive:

Dim scores(9) As Integer
Console.WriteLine("Length: " & scores.Length)
Console.WriteLine("Last valid index: " & scores.GetUpperBound(0))
Length: 10
Last valid index: 9

Reading this correctly matters most when a size looks deliberately chosen — Dim buffer(255) As Byte is a 256-byte buffer, not 255, and getting that off by one when translating a size requirement from a spec or from C# (where new byte[256] unambiguously means 256) is a real, easy mistake in either direction.

Static — a local variable that survives past the end of its own method

A local variable normally stops existing the moment its method returns. Static is VB.NET's keyword for the opposite: a local variable declared Static keeps its value between separate calls to the same method, for the lifetime of the containing object (or, inside a Shared method, for the lifetime of the whole application — there's only one copy, not one per object instance):

Sub TrackCalls()
    Static callCount As Integer = 0
    callCount += 1
    Console.WriteLine("This method has been called " & callCount & " time(s)")
End Sub

Sub Main()
    TrackCalls()
    TrackCalls()
    TrackCalls()
End Sub
This method has been called 1 time(s)
This method has been called 2 time(s)
This method has been called 3 time(s)
The initializer only runs once — a common source of confusion callCount As Integer = 0 only executes the first time TrackCalls is ever called; on every later call, that line is skipped entirely and callCount keeps whatever value it already had. This is fundamentally different from a normal local variable, whose initializer re-runs on every single call. A Static local is effectively a private field in disguise — scoped so only this one method can see it, but living exactly as long as a field would.

Real-world use is narrow and specific: a call counter, a one-time-setup flag inside a frequently-called method, memoizing an expensive calculation across calls to the same method on the same instance. Reach for an actual class-level field instead when more than one method needs to see or share the value — Static is deliberately private to the one method it's declared in.

Try it yourself

& for string concatenation is the one habit that trips up C# developers reading VB.NET most often:

Module Program
    Sub Main()
        Dim amount As Integer = 25
        Dim feeRate As Double = 0.02
        Dim fee As Double = amount * feeRate

        Console.WriteLine("Amount: " & amount & ", Fee: " & fee)
    End Sub
End Module
Amount: 25, Fee: 0.5

Best practice

  • Match whatever casing convention the surrounding file already uses. VB.NET is case-insensitive, so amount and Amount are the same identifier to the compiler — but a file mixing both looks like two different variables to a human reader, which is exactly the confusing situation case-insensitivity can quietly create.
  • In a new BackOffice file, add Option Strict On at the top yourself if the change is substantial enough to justify it — it turns silent, potentially lossy conversions into compile errors you fix immediately instead of runtime surprises later. Don't retrofit it onto an existing large file casually: turning it on can surface a wave of pre-existing conversion warnings unrelated to your change.

Better ways

The comment marker in Fiuu Code Conventions → Comment Style's real example — // TODO: might not be correct. Was : Exit For — is a tell for code mechanically ported from VB.NET to C# without a careful rewrite. If you ever do this kind of port yourself, treat it as a rewrite opportunity, not a find-and-replace exercise — the two languages' idioms (exception-only control flow vs. VB's historical On Error style, for one) don't map one-to-one.

Dim iQty, iMaxQty As Integer — a real line from OfflineSalesCreate.aspx.vb. What type is iQty?

  • Object, since it has no As clause of its own.
  • Integer — VB.NET gives every name in the list the type named at the end, unlike VB6.
  • This doesn't compile — VB.NET requires a separate Dim for each variable.

Dim arrEmail As String() = Split(sEmailAddress, ";") — a real line from DealerCreate.aspx.vb. What does arrEmail actually hold?

  • A single semicolon-delimited string, unchanged.
  • A reference to an array of strings — one element per semicolon-separated piece of the original text.
  • The number of semicolons found in the string.

Dim scores(9) As Integer — how many elements does this array actually have? (just the number)

A method has Static callCount As Integer = 0 as its first line, then increments callCount. It's called three times in a row. What does the third call see as the initial value of callCount, before the increment?

  • 0 — the initializer re-runs on every call, resetting it.
  • 2 — the value left over from the two previous calls, since the = 0 initializer only ran once, on the first call ever.
  • It throws an exception, since the variable was already declared on a previous call.

A BackOffice .aspx.vb file has no Option Strict declaration of its own. What governs whether risky implicit type conversions are allowed in that file?

  • VB.NET always defaults to Option Strict On regardless of project settings.
  • The project file's own <OptionStrict> setting — verified as Off for BackOffice — which every file inherits unless it overrides it locally.
  • Whether the corresponding .aspx markup file has strict typing enabled.

Why does VB.NET generally prefer & over + for joining strings, even though both compile?

  • & runs measurably faster than +.
  • + is also the numeric addition operator, so & removes any ambiguity about whether you mean addition or concatenation.
  • + only works with numbers, & only works with pre-declared string variables.
