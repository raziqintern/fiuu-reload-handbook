WebForms Postback & ViewState Pitfalls

reload's BackOffice web app is ASP.NET WebForms — a model where three mechanisms (ViewState, UpdatePanel async postbacks, and a "magic" global function name) cause bugs that look nothing like their actual cause. All three real examples below come from the same page: TerminalFirmwareVersionList.aspx.

Pitfall 1 — a control's Visible survives postbacks whether you want it to or not

Protected Sub Page_Load(ByVal sender As Object, ByVal e As System.EventArgs) Handles Me.Load
    Try
        If Not IsPostBack Then
            ...
            If (Service.AccessRightControl(ModuleName.TerminalFirmwareVersion, WebEnumAccessRights.Print)) Then
                btnExcel.Visible = True
                ScriptManager.GetCurrent(Me).RegisterPostBackControl(upReport.FindControl("btnExcel"))
            Else
                btnExcel.Visible = False
            End If
            ...
        End If
    Catch ex As Exception
        Logger.WriteErrorToEventLogs(ex)
    End Try
End Sub

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb:31-58

btnExcel.Visible is decided exactly once, guarded by If Not IsPostBack — the very first time the page loads. Every subsequent postback on this page (clicking Search, clicking Reset) never touches it again. That's not an oversight to "fix" reflexively: in WebForms, a control's server-side properties — Visible included — are persisted in ViewState and survive across postbacks automatically. Once set, it stays set until something explicitly changes it, exactly the way a page author would want for a value that only depends on the user's access rights, which don't change mid-session.

Official documentation Microsoft's own ASP.NET View State Overview confirms this is deliberate framework behavior, not something specific to this page: "View state is the method that the ASP.NET page framework uses to preserve page and control values between round trips... View state is used automatically by the ASP.NET page framework to persist information that must be preserved between postbacks. This information includes any non-default values of controls." Visible is exactly this kind of non-default control value — once set to True outside the framework's own default, ViewState is what keeps it True across every later postback with zero code re-running that line.
The trap this pattern sets for the next change The moment someone makes btnExcel's visibility depend on something that can change across postbacks — like whether the last search returned results — ViewState persistence stops being free and becomes a liability. If a results-found search sets btnExcel.Visible = True and a later no-results search doesn't explicitly set it back to False, the button stays visible on an empty grid, because nothing told it otherwise. This exact scenario was the subject of a real review discussion on MR !1906: a reviewer asked "is resetting both controls' visibility at the top of the method necessary?" — and the honest answer was yes, once visibility depends on per-search state rather than a value that's fixed for the whole session.

Best practice for pitfall 1

  • When a control's visibility depends only on something session-wide and unchanging (access rights, a feature flag), set it once and leave it — don't add defensive resets "just in case." ViewState is doing exactly what it's supposed to for this case.
  • When visibility depends on something that varies per postback (search results, validation state), reset it to a safe default at the top of the handler and only opt it back to visible where the conditions are actually met. Don't rely on remembering to add an explicit False to every branch that doesn't grant it, including ones added later.

Pitfall 2 — a function literally named pageLoad is a framework hook, not just a name you picked

ASP.NET AJAX (Sys.Application, the framework behind UpdatePanel) automatically calls a global JavaScript function named exactly pageLoad(sender, args) — if one exists anywhere on the page — after the initial page load, and again after every single async partial postback completes. It's not an event you subscribe to; it's a magic name the framework looks for.

Why this made a search spinner stick, on a real page in this codebase While cleaning up an unrelated jQuery UI autocomplete block that was copy-pasted onto this page from elsewhere, a leftover was left behind: 
function pageLoad(sender, args) {
    loadUIComponents();   // loadUIComponents was deleted along with the autocomplete cleanup — this now throws ReferenceError
}
Because pageLoad runs after every async postback — including clicking Search, which goes through an UpdatePanel on this page — the resulting uncaught ReferenceError fired inside the same framework completion path responsible for hiding the UpdateProgress spinner. The visible symptom had nothing to do with search logic at all: the loader just never went away.

The fix wasn't in the VB.NET code-behind — it was deleting the now-orphaned pageLoad function once nothing on the page needed it. If you ever add or remove a script block on a WebForms page that uses UpdatePanel, grep the page for a literal function named pageLoad before you assume your change is purely additive — a stray one can silently break every async postback on the page, not just the feature you touched.

Pitfall 3 — a file download from inside an UpdatePanel needs to opt out of the async pipeline

<asp:Button runat="server" ID="btnExcel" OnClick="btnExcel_OnClick" Text="Export to Excel" OnClientClick="ShowProgress()" Visible="False" />
<asp:UpdatePanel runat="server" ID="upReport">
    ...
</asp:UpdatePanel>

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx:102-103

btnExcel triggers btnExcel_OnClick, which writes a raw CSV file straight to Response with a content-disposition: attachment header. That only works correctly as a full postback. Since btnExcel sits inside (or near) an UpdatePanel, the framework's default is to route its click through the async pipeline instead — which expects a small, specially-formatted partial-page delta back, not a raw file. Get this wrong and the browser throws exactly this client-side error:

Sys.WebForms.PageRequestManagerParserErrorException:
The message received from the server could not be parsed.

That's the textbook signature of a full-postback-shaped response (your CSV) arriving through a client that's expecting an async-postback-shaped one. The line that prevents it is easy to miss precisely because it's a one-line opt-out, not a visible structural difference in the markup:

If (Service.AccessRightControl(ModuleName.TerminalFirmwareVersion, WebEnumAccessRights.Print)) Then
    btnExcel.Visible = True
    ScriptManager.GetCurrent(Me).RegisterPostBackControl(upReport.FindControl("btnExcel"))
End If

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb:44-46

RegisterPostBackControl tells the framework "treat clicks on this specific control as a full postback, regardless of what panel it's sitting in" — required for any file download triggered from inside an UpdatePanel-heavy page. If you add a new export/download button to a page like this one and copy the surrounding panel structure but miss this line, the button will look identical in the markup and still throw this exact parser exception the first time someone clicks it.

A smaller trap hiding in the same button: two statements, one onclick

OnClientClick="ShowProgress()" on a WebForms button gets rendered client-side as roughly onclick="ShowProgress(); __doPostBack(...)" — two JavaScript statements, in sequence. If ShowProgress() throws an uncaught exception (for example, because a dependency it calls — like jQuery itself — was never loaded on this page), the browser aborts the rest of that inline handler right there. __doPostBack(...), the part that actually submits the postback and runs your server-side click handler, **never runs at all** — no request goes out, nothing happens, and it looks exactly like "the button stopped working," when the server-side code was never reached in the first place.

The general lesson across all three pitfalls WebForms hides a lot of client/server plumbing behind a small surface area — a property that "just persists," a function name that "just happens" to get called, an attribute that "just" runs some script before a postback. When a bug's symptom doesn't match the code you're staring at, ask whether you're looking at the framework's plumbing instead of your own logic: stale ViewState, a magic-named global function, or a postback silently never reaching the server at all.

Best practice

  • Before adding a script block to a WebForms page that already uses UpdatePanel, check for an existing global pageLoad function — don't silently shadow or half-delete one. It's a magic framework hook, not just a name you happened to pick.
  • Confirm any new file-download button calls RegisterPostBackControl, and verify any script referenced by OnClientClick has its dependencies (jQuery, etc.) actually loaded on that specific page. Copying a script block from a sibling page doesn't copy the <script src> tags it silently depends on.

Check your understanding

A WebForms page's search spinner (UpdateProgress) gets stuck showing after every search, but only after a recent, seemingly-unrelated cleanup of some old autocomplete script. What should you check first?

  • Re-read the VB.NET search handler for a newly introduced logic bug.
  • Grep the page for a global function literally named pageLoad — ASP.NET AJAX calls it automatically after every async postback, and a leftover reference to deleted code there can break the framework's own UI cleanup.
  • Clear the browser cache — this is almost always a stale-asset problem.

A new "Export to PDF" button is added inside an existing UpdatePanel-heavy WebForms page, copying the structure of a working "Export to Excel" button on a sibling page — except ScriptManager.GetCurrent(Me).RegisterPostBackControl(...) for the new button. What happens when a user clicks it?

  • The server throws an unhandled exception because the button isn't registered.
  • Nothing — RegisterPostBackControl is a performance optimization only, the download still works either way.
