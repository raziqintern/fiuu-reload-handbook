Classes, Objects & Interfaces

This is the lesson that matters most before you open real reload code — the whole codebase is organised around exactly these three ideas.

A class with properties and a constructor

public class Terminal
{
    public string TerminalId { get; set; }
    public string MerchantName { get; set; }
    public bool IsOnline { get; set; }

    public Terminal(string terminalId, string merchantName)
    {
        TerminalId = terminalId;
        MerchantName = merchantName;
        IsOnline = true;
    }
}

class Program
{
    static void Main()
    {
        Terminal t = new Terminal("TNG-0042", "7-Eleven KL");
        Console.WriteLine(t.TerminalId + " - " + t.MerchantName + " - " + t.IsOnline);
    }
}
TNG-0042 - 7-Eleven KL - True

A class is a blueprint; new Terminal(...) creates an object (an instance) from it. { get; set; } is a shorthand C# property — a field with an automatic getter/setter, far more common in real code than writing a private field plus manual getter/setter methods by hand.

Interfaces: a contract, separate from the implementation

An interface declares what a class can do, without saying how. This matters because it lets code depend on the contract instead of a specific class — you can swap the implementation later without touching every place that uses it.

public interface ITerminalService
{
    bool Login(string terminalId);
}

public class TerminalService : ITerminalService
{
    private string _lastError;

    public bool Login(string terminalId)
    {
        if (string.IsNullOrEmpty(terminalId))
        {
            _lastError = "Terminal ID required";
            return false;
        }
        Console.WriteLine("Logging in terminal: " + terminalId);
        return true;
    }
}

class Program
{
    static void Main()
    {
        ITerminalService service = new TerminalService();
        bool ok = service.Login("TNG-0042");
        Console.WriteLine("Login result: " + ok);
    }
}
Logging in terminal: TNG-0042
Login result: True
This is not a hypothetical example ITerminalService and TerminalService are real types in reload's class-library (Reloads/TNG/Services/TerminalService.cs). The I-prefix-on-interfaces convention shown here is followed with zero exceptions across the entire sampled codebase — see Fiuu C# Conventions → Naming for the full picture, including where other naming conventions in this codebase are not so consistent.

Best practice

  • Give every class a constructor that leaves it in a valid state — Terminal's constructor sets IsOnline = true so there's never a moment where a Terminal object exists half-initialized.
  • Depend on the interface (ITerminalService), not the concrete class, in any code that calls a Service — it's what makes the implementation swappable later, and it's the real, consistent pattern in reload's own code.

Better ways

Auto-properties ({ get; set; }) are convenient but let any caller freely overwrite a value that maybe shouldn't be freely overwritable — t.IsOnline = false from anywhere, any time. A more deliberate design exposes a method (t.GoOffline()) instead of a public setter when the change is really a meaningful action with its own rules, not just a raw field write — the same encapsulation idea from Software Design → OOP Pillars.

Check your understanding

Why declare ITerminalService service = new TerminalService(); instead of just TerminalService service = new TerminalService();?

  • It's required for the code to compile.
  • The rest of the code only depends on the interface's contract, not the specific class — the implementation can be swapped later.
  • It hides the class's public methods from other files.
