Trees & Hierarchies

A tree is what you get when a hierarchy has exactly one parent per item — and reload's real domain has a genuine one, not a contrived teaching example.

The shape: one root, no cycles, each node has children

A tree is a node with a value and a list of child nodes, each of which is itself a tree — the same recursive shape you just spent a whole lesson on. There's exactly one root (no parent), and no node can be its own ancestor.

This isn't a contrived example — it's CEPP's actual structure You'll trace this in full later, in the Architecture Map track: CEPP, reload's master-data hub, organizes its org hierarchy as Company → Dealers → Stores → Terminals — a real, four-level tree. Every terminal belongs to exactly one store, every store to exactly one dealer, every dealer to exactly one company. That's a tree, not a graph, specifically because there's no scenario where a terminal belongs to two stores at once.

Example: counting terminals with a recursive traversal

public class OrgNode
{
    public string Name;
    public List<OrgNode> Children = new List<OrgNode>();
}

static int CountTerminals(OrgNode node)
{
    if (node.Children.Count == 0)
        return node.Name.StartsWith("Terminal") ? 1 : 0;

    int total = 0;
    foreach (var child in node.Children)
    {
        total += CountTerminals(child);
    }
    return total;
}

static void Main()
{
    var store = new OrgNode { Name = "Store A" };
    store.Children.Add(new OrgNode { Name = "Terminal-01" });
    store.Children.Add(new OrgNode { Name = "Terminal-02" });

    var dealer = new OrgNode { Name = "Dealer X" };
    dealer.Children.Add(store);

    var company = new OrgNode { Name = "Company" };
    company.Children.Add(dealer);

    Console.WriteLine(CountTerminals(company));
}

Notice this is the exact same shape as Recursion's base-case/recursive-case pattern: a leaf node (no children) is the base case; a branch node recurses into each child and combines the results. Trees and recursion are a natural pair because a tree is, by definition, recursively structured — a tree is a node plus a list of smaller trees.

What if the structure isn't actually a tree? A cycle turns the base case into an infinite loop The recursive traversal above has no explicit "have I visited this node before" check — it relies entirely on there being no way back up to an ancestor, which is the actual definition of a tree, not just a convenient assumption. If a bug (or bad data — a store's parent dealer ID accidentally pointing back down to one of its own stores) ever created a cycle, CountTerminals would recurse into that cycle forever, with no leaf node ever reached to stop it — exactly the missing-base-case failure from Recursion, and just as uncatchable once it throws StackOverflowException. This is precisely why the "no node can be its own ancestor" rule matters in practice, not just in the definition.

A special case you've already met: the binary search tree

A binary tree is a tree where every node has at most two children. A binary search tree keeps them ordered (left child smaller, right child larger) — which means Binary Search's halve-the-remaining-space idea is really just walking down one of these, left or right, at each step.

Best practice

  • Use a recursive traversal by default. It's the most natural fit for a tree's own recursive definition, and it's usually the most readable option.
  • Watch traversal depth on a tree that could be unexpectedly deep. A hierarchy with no practical limit on nesting risks the same call-stack exhaustion from Recursion.
  • If the data's tree-ness is enforced by convention rather than the database schema, don't assume it can never become a cycle. A bad write elsewhere in the system is all it takes to turn a recursive traversal into an unrecoverable crash.

Better ways

For a tree that might be very deep or very wide, an iterative traversal using an explicit Stack<T> (depth-first) or Queue<T> (breadth-first) — from Stacks, Queues & Dictionaries — avoids the call stack's fixed depth limit entirely, at the cost of slightly more code than the recursive version above.

Why is CEPP's Company → Dealers → Stores → Terminals structure a tree rather than some other shape?

  • Because every terminal, store, and dealer has exactly one parent — no item belongs to two parents at once.
  • Because it only ever has at most two children per node.
  • Because the terminals are stored in sorted order.

Bad data accidentally makes a store's parent dealer ID point back down to one of that dealer's own stores, creating a cycle. What happens when CountTerminals (the recursive traversal above) is run on this structure?

  • It correctly detects the cycle and stops at the base case.
  • It recurses forever along the cycle, since there's no leaf node to stop it — eventually crashing with an uncatchable StackOverflowException.
  • The .NET runtime automatically detects the cycle and throws a clear, catchable error.
