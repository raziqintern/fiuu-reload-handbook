HTML Basics

Page Structure & Tags

HTML isn't going to be your day job at Fiuu — but reload_portal and web_app render HTML, and when something looks wrong in a browser, you need to read the markup fast. This lesson is the minimum you need to do that.

The skeleton every page has

Every HTML page has the same four wrapper tags. Nothing renders outside <body>:

<!doctype html>
<html>
<head>
  <title>My Page</title>
</head>
<body>
  <h1>Hello, Fiuu</h1>
</body>
</html>
  • <!doctype html> — tells the browser "this is modern HTML", always the first line.
  • <head> — metadata: page title, linked stylesheets, scripts. Nothing in here is visible on the page itself.
  • <body> — everything the user actually sees.
Official documentation MDN's Doctype glossary entry explains exactly what that first line is protecting you from: "Its sole purpose is to prevent a browser from switching into so-called 'quirks mode' when rendering a document; that is, the <!doctype html> doctype ensures that the browser makes a best-effort attempt at following the relevant specifications, rather than using a different rendering mode that is incompatible with some specifications."
Real, verified: not every page in this codebase uses the modern doctype TerminalFirmwareVersionList.aspx's markup starts with <!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN" "http://www.w3.org/TR/xhtml1/DTD/xhtml1-transitional.dtd"> instead of the modern one-line <!doctype html> — a real relic of when this WebForms UI was first built, well before HTML5 existed. It still renders in every modern browser (old doctypes are still recognized), but it's a concrete sign of the page's age, and one more reason old and new markup in this codebase can look and behave slightly differently.

Tags nest — and the nesting is the structure

A tag opens with <tag> and closes with </tag>. What's between them is its content, and tags can contain other tags. Indentation in the examples exists purely to make that nesting readable to you — the browser doesn't care about whitespace.

TagMeaning
<h1>…<h6>Headings, biggest to smallest. A page should have exactly one <h1>.
<p>A paragraph of text.
<div>A generic block-level container — no meaning of its own, used to group things for layout/styling.
<span>Same idea as <div> but inline (doesn't force a line break) — used to style a piece of text mid-sentence.
<a href="...">A link.
<img src="...">An image. Self-closing — no separate closing tag.
Official documentation MDN's <div> reference states the "no meaning of its own" rule as a recommendation, not just a description: "The <div> element should be used only when no other semantic element (such as <article> or <nav>) is appropriate." Its usage notes go further: "As a 'pure' container, the <div> element does not inherently represent anything. Instead, it's used to group content so it can be easily styled..." — a <div> is what's left after every meaningful tag has been ruled out, not a default first choice.
Why this matters for debugging When a merchant reports "the reload page looks broken", your first move is often browser DevTools → Elements tab, reading exactly this kind of nested structure to see which tag is missing, misplaced, or mis-styled — not reading C# first.

Best practice

  • Exactly one <h1> per page. It's the page's title, not a size setting. Use <h2>/<h3> for subsections, and don't skip a level just because a smaller size looks better (use CSS for that).
  • Indent nested tags consistently. It costs nothing and it's the difference between spotting a missing closing tag in two seconds versus two minutes.
  • Reach for a semantic tag before a <div>, per MDN's own recommendation. Only fall back to <div> once you've genuinely ruled out <header>/<nav>/<main>/<article>/<footer> as not fitting.

Better ways

A page built entirely from <div>s (a "div soup") works, but tells a screen reader or search engine nothing about what each part is. Real semantic tags — <header>, <nav>, <main>, <footer>, <article> — are just <div> with a meaning attached, and cost nothing extra to use. You'll see this distinction matter more once you're reading a real rendered page's DevTools tree.

A merchant says a page "looks broken" in their browser. What's the fastest first step?

  • Pull up the reload_portal C# source and start reading controllers.
  • Open browser DevTools and inspect the rendered HTML/console for errors.
  • Ask them to restart their browser and try again.

A page's markup is missing <!doctype html> entirely. What actually happens in the browser?

  • Nothing renders at all — the page fails to load.
  • The browser switches into "quirks mode," a legacy rendering mode that doesn't follow modern specifications the way standards mode does.
  • The server rejects the page and returns an error instead.
