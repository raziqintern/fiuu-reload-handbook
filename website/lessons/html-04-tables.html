Tables & Reading Real Markup

BackOffice-style admin screens lean heavily on tables for transaction lists, terminal lists, and reports. Last stop before you're ready to open real DevTools on a real page.

Table anatomy

<!doctype html>
<html>
<body>
  <table border="1">
    <tr>
      <th>Trans No</th>
      <th>Terminal</th>
      <th>Amount</th>
      <th>Status</th>
    </tr>
    <tr>
      <td>TXN-1001</td>
      <td>TNG-0042</td>
      <td>RM 10.00</td>
      <td>Success</td>
    </tr>
    <tr>
      <td>TXN-1002</td>
      <td>TNG-0042</td>
      <td>RM 25.50</td>
      <td>Pending</td>
    </tr>
  </table>
</body>
</html>

<tr> is a row, <th> a header cell, <td> a data cell. That's genuinely the whole vocabulary — everything else in a real admin table (sorting, pagination, row highlighting) is CSS and JavaScript layered on top of this same three-tag skeleton.

Reading real markup: a practical checklist

When you open DevTools on an actual reload page and it looks like an unreadable wall of nested <div>s, work outside-in:

  1. Find the element that's visually wrong (right-click it → Inspect).
  2. Look at its immediate parent and siblings — is it where you'd expect in the structure?
  3. Check the Styles panel next to Elements — a crossed-out CSS rule tells you something else is overriding it.
  4. Check the Console tab for JavaScript errors — a thrown error often stops later script from running at all, which explains "half the page works."

Best practice

Official documentation MDN's HTML table basics guide is direct about why the older "layout tables" habit is a real accessibility problem, not just an aesthetic one: "Layout tables reduce accessibility for visually impaired users: screen readers... interpret the tags that exist in an HTML page and read out the contents to the user. Because tables are not the right tool for layout... the screen readers' output will be confusing to their users."
  • Use <table> only for genuinely tabular data — rows and columns of related values, like the transaction list above — never as a general-purpose layout tool for positioning unrelated page elements. Use CSS for layout instead.

Better ways

A large real table (hundreds or thousands of transaction rows) rendered all at once will make a browser tab sluggish. Real admin screens handle this with server-side pagination or a "virtualized" list that only renders the rows currently in view — worth knowing the term for when you eventually need to explain why a report page is slow.

Real, verified: pagination on a real BackOffice grid <mol:GridView runat="server" AllowPaging="True" AllowSorting="True" ID="gvTerminalFirmwareVersion" ... PageSize="100" ...> — this WebForms grid control renders down to a real <table>, but AllowPaging="True" with PageSize="100" means only 100 rows are ever actually rendered into the page at once, no matter how many thousands of rows the underlying query returns. That's the server-side pagination technique in production, not a theoretical example.

Check your understanding

Why does MDN's own guidance specifically warn against using <table> for page layout instead of CSS?

  • Because tables don't render correctly in modern browsers.
  • Because a screen reader announces table structure as if it were meaningful data, which is confusing when the table was only ever meant for visual positioning.
  • Because search engines penalize pages that use <table> for layout.

A real BackOffice grid sets AllowPaging="True" and PageSize="100" on a table backed by a query that could return tens of thousands of rows. What does this actually prevent?

  • It prevents the underlying SQL query from ever returning more than 100 rows.
  • It prevents the browser from ever having to render more than 100 <tr> rows into the page at once, no matter how large the full result set is.
  • It prevents the user from sorting the table by more than one column.
