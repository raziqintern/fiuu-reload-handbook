DOM, Events & the Console

The last JS lesson: how JavaScript actually touches the page you learned about in HTML Basics, and how to debug it when it goes wrong.

The DOM is the HTML, as JavaScript sees it

The Document Object Model is the live, in-memory tree of every tag on the page. JavaScript reads and changes it with methods like document.querySelector.

<!doctype html>
<html>
<body>
  <h1 id="status">Terminal: checking...</h1>
  <button id="refresh-btn">Refresh Status</button>

  <script>
    const heading = document.querySelector("#status");
    const button = document.querySelector("#refresh-btn");

    button.addEventListener("click", () => {
      heading.textContent = "Terminal: Online ✓";
      heading.style.color = "green";
    });
  </script>
</body>
</html>

Click Run ▸, then click the "Refresh Status" button inside the result panel — that's addEventListener reacting to a real click, and .textContent/.style editing the DOM live, exactly like a real reload_portal page would when a status updates without a full page reload.

The browser console is your debugger

Everything you've been reading in the "Console" output boxes on this site is exactly what you'll see in real browser DevTools (F12 → Console tab) on any real page. The habits:

  • Read errors top to bottom, oldest first — the first error is often the real cause; later ones can just be fallout.
  • console.log liberally while debugging — print a variable right before the line that misbehaves to confirm what it actually contains, not what you assume it contains.
  • Check the Network tab when data looks wrong — see the actual request/response before assuming the JavaScript logic is at fault.
"Cannot read properties of undefined" This is the single most common JS runtime error you'll encounter. It means you tried to access a property (.something) on a value that turned out to be undefined — almost always because an API call hasn't returned yet, a field name was typo'd, or an array was empty when you expected an item.

Try it yourself: reproduce that exact error

const terminal = undefined; // pretend an API call hasn't returned yet

console.log("About to read a property...");
console.log(terminal.merchantName); // this line throws

Best practice

  • When something breaks, read the Console tab's first error before any that follow — a single root-cause error thrown early often stops later script from running, producing a cascade of confusing follow-on errors that all trace back to the first one.
  • Reach for console.table(someArray) instead of console.log when inspecting an array of objects (like an API response) — it renders as an actual readable table instead of a wall of nested braces.

Better ways

Sprinkling console.log everywhere and re-running is the fastest first move, but real browser DevTools also have a proper step-through debugger: click a line number in the Sources tab to set a breakpoint, reload, and the browser pauses execution right there, letting you inspect every variable's live value without editing the code at all. Worth learning once you're debugging something console.log alone can't pin down.

Check your understanding

You see "Cannot read properties of undefined (reading 'merchantName')" in the console. What's the most likely cause?

  • A missing semicolon somewhere in the file.
  • Something you expected to already be an object (like API response data) was actually undefined at that point.
  • The internet connection dropped.
