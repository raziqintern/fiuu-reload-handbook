Assemblies & DLLs

The last theory lesson, and the one that explains a genuinely unusual real pattern you'll run into in reload's own repository layout.

The vocabulary

TermMeaning
AssemblyThe .NET unit of compiled code, versioning, and deployment — the output of compiling one project. Contains IL (Intermediate Language) code plus metadata describing every type inside it.
DLLDynamic-Link Library — a compiled assembly meant to be referenced by other programs, not run directly (as opposed to an .exe, which is a runnable assembly).

When you add a project reference in Visual Studio, you're telling your project "at build time, compile against this assembly's public types, and at runtime, load this DLL to actually execute them."

Official documentation Microsoft's Assemblies in .NET reference lists what an assembly actually bounds, not just contains: "The type boundary. Every type's identity includes the name of the assembly in which it resides. A type called MyType that's loaded in the scope of one assembly isn't the same as a type called MyType that's loaded in the scope of another assembly." It also confirms the versioning claim directly: "The version boundary. The assembly is the smallest versionable unit in the common language runtime. All types and resources in the same assembly are versioned as a unit."
What if two different-but-same-named DLLs both exist? The type identity, not just the name, decides Per the type-boundary rule above, a class named Fiuu.Logging.LogManager compiled into one build of Fiuu.Logging.dll is not the same type, as far as the runtime is concerned, as a class with the exact same name and namespace compiled into a different build of that same-named DLL. If a consuming app somehow ends up with two different versions of Fiuu.Logging.dll loaded at once (a real, if unusual, possibility), passing an object created against one version into code expecting the other can fail with a genuinely confusing "cannot convert type X to type X" error — the two Xs only look identical in the error message; they're bound to two different assemblies underneath.

Two ways to consume someone else's code

  • Project reference (source): your build compiles the other project's source directly alongside yours. Change the source, rebuild, see the change immediately.
  • Binary reference (a prebuilt DLL): you reference an already-compiled .dll file directly. You don't have (or need) its source to build against it — but you also can't see or step into its implementation without a separate copy of the source, and it won't reflect any source change until someone rebuilds and re-drops a new DLL.
reload's class-library does something genuinely unusual here Traced in full later in Architecture Map → reload: Topology & Modules — the short version: several modules (Fiuu.CEPP, Fiuu.Logging, Fiuu.Lookup, Fiuu.MasterFramework, Fiuu.Provider, and others) exist as prebuilt .dll files committed directly into the class-library repository's root — not built from source inside that repo. Their actual source lives elsewhere (in Components/*, a different part of the monorepo). How the built DLL gets from that source into class-library's root was never confirmed in this handbook's research — no visible build-and-publish pipeline step does it automatically, so the most likely explanation is a developer building locally and manually committing the resulting DLL.
Why this is worth knowing before you go looking for "the source" If you're debugging behavior that seems to come from Fiuu.Logging.dll referenced this way, editing the Components/Logging source and rebuilding that project will not change what class-library's consumers actually run — they're bound to whatever DLL is physically sitting in class-library's repo root until someone manually rebuilds and re-commits it there. This is exactly the kind of "looks like one codebase, is actually two things kept in sync by hand" trap worth checking for before you conclude a fix didn't work.

Best practice

  • When you're not sure whether you're looking at the real, current source of a referenced type, check how it's referenced. A <ProjectReference> in the .csproj means you're building against live source; a <Reference> with a HintPath pointing at a .dll means you're not, and the actual behavior is frozen at whenever that DLL was last built.
  • Never assume two same-named types from two different assembly builds are interchangeable. The runtime scopes type identity to the assembly it came from — a mismatch here produces a confusing error where the type name in the message looks correct but the object still won't cast.

Check your understanding

You edit the source in Components/Logging and rebuild that project, expecting a bug fix to show up in an app that consumes Fiuu.Logging.dll from class-library's repo root. Why might the bug still be there?

  • The Components project probably failed to compile.
  • The app likely references the prebuilt DLL committed in class-library's root, which isn't automatically regenerated from the Components source you just changed.
  • .NET caches the old assembly in memory until the whole machine restarts.

Two different builds of Fiuu.Logging.dll both define a class named Fiuu.Logging.LogManager. An object created against one build is passed to code expecting the type from the other build. What happens?

  • It works fine — the class name and namespace match, so the runtime treats them as the same type.
  • It can fail with a confusing type-mismatch error — the runtime treats them as genuinely different types, even though their name and namespace are identical.
  • The runtime automatically picks whichever version was loaded more recently.
