Security Basics

Reload is a payment platform — security here isn't abstract. This lesson covers the handful of concepts worth understanding before you touch anything that handles money or credentials.

SQL injection: see it happen, live, against this site's own practice database

Imagine a search feature built by directly pasting user input into a SQL string, like "SELECT * FROM Terminals WHERE MerchantName = '" + userInput + "'". Now imagine a user (or attacker) types ' OR '1'='1 into that search box instead of a real merchant name:

-- This is what the query string above actually becomes once
-- ' OR '1'='1  is substituted in as "userInput":
SELECT * FROM Terminals WHERE MerchantName = '' OR '1'='1';

Run it. You get every row in the table, not zero rows — because '1'='1' is always true, the attacker's input turned a "find one specific merchant" query into "return everything," entirely through the text of the query itself. This is SQL injection: user input being interpreted as code instead of as data.

A common misconception, corrected "We use stored procedures, so we're safe from SQL injection" is not quite true. A stored procedure that itself builds a dynamic SQL string by concatenating a parameter (EXEC('SELECT * FROM Terminals WHERE MerchantName = ''' + @Name + '''')) is exactly as vulnerable as the raw query above. The actual defense is parameterization — passing the value as a typed parameter that's never interpreted as SQL syntax, regardless of whether it's wrapped in a stored procedure or not.
This is genuinely how reload defends against it Recall from Fiuu C# Conventions → Data Access: every parameter reload sends to a stored procedure goes through ParameterCollection.Add("@Name", DbType.String, value) — the value is bound as typed data, never concatenated into query text. Combined with "no inline dynamic SQL, no string-built SELECT/UPDATE statements... anywhere," this is a real, consistently-applied defense — not just "we use stored procedures so we're fine."

Secrets: never in source code, never fully trust logs

You've already seen reload's real secrets story in Configuration & Secrets: credentials live in AWS Secrets Manager, not hardcoded in source. The general principle behind that: a secret committed to source control is compromised the moment it's pushed, even if you delete it in a later commit — Git history keeps it. And recall Logging's warning that reload logs full request/response payloads unredacted — a secret or account number passed through a logged call is now sitting in a log file too, a second place it can leak from.

Least privilege

Give code (and people) only the access they actually need, not the broadest access that happens to be convenient. A background job that only ever reads from REPORTSUMMARY shouldn't run with a database credential that also has write access to CEPP — if that job is ever compromised or has a bug, the blast radius is limited to what it actually needed.

Check your understanding

A teammate says "this stored procedure is safe from SQL injection because it's a stored procedure." Based on what you just saw, what's the accurate correction?

  • That's correct — stored procedures are always immune to SQL injection.
  • Only if the procedure itself uses parameterized values rather than concatenating input into a dynamic SQL string — the defense is parameterization, not the stored procedure wrapper itself.
  • It depends on which programming language calls the stored procedure.
