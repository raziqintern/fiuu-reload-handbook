Heaps & Priority Queues

A Queue processes things in the order they arrived. Sometimes that's wrong — you need to process the most urgent thing next, regardless of when it showed up.

The problem a plain queue can't solve

Imagine a retry queue for failed transactions, where some failures are far more urgent than others (a payment stuck mid-flight vs. a low-priority report regeneration). A Queue<T> would retry them in arrival order, ignoring urgency entirely. A priority queue is exactly this: a queue where each item has a priority, and Dequeue() always returns the highest-priority item currently waiting, not the oldest one.

Example: .NET's real, built-in PriorityQueue

using System.Collections.Generic;

var retryQueue = new PriorityQueue<string, int>();
retryQueue.Enqueue("TXN-1001", 3); // priority 3 = least urgent
retryQueue.Enqueue("TXN-1002", 1); // priority 1 = most urgent
retryQueue.Enqueue("TXN-1003", 2);

while (retryQueue.Count > 0)
{
    Console.WriteLine(retryQueue.Dequeue());
}
TXN-1002
TXN-1003
TXN-1001

Notice TXN-1001 was enqueued first but comes out last — arrival order is completely irrelevant here. Only the priority number matters, and by default, lower numbers come out first (a "min-heap" — see below for why that's the name).

What's actually inside a priority queue: a heap

A heap is a tree (usually binary, like Trees & Hierarchies) with one extra rule: every parent's value is <= both its children's values (a min-heap — the smallest value is always the root; a max-heap flips the comparison). That single rule is enough to guarantee the smallest item is always instantly available at the root, while insert and remove only need to fix up one path through the tree — O(log n) each, not a full re-sort of everything.

OperationCostWhy
Peek at the top priority itemO(1)It's always sitting at the root — no searching needed.
Insert a new itemO(log n)Add it, then swap it upward until the heap rule holds again.
Remove the top itemO(log n)Move the last item to the root, then swap it downward until the rule holds again.
Official documentation Microsoft's own PriorityQueue<TElement,TPriority> reference confirms the default ordering directly: "Represents a collection of items that have a value and a priority. On dequeue, the item with the lowest priority value is removed." It's specifically documented as "an array-backed, quaternary min-heap" — quaternary meaning each node has up to four children, not the two a "textbook" binary heap has, though the same core min-heap rule and O(log n) behavior still apply.
What if two items share the exact same priority? No FIFO guarantee The same reference states this plainly: "Note that the type does not guarantee first-in-first-out semantics for elements of equal priority." If TXN-1001 and TXN-1004 are both enqueued with priority 2, don't assume the one enqueued first comes out first — PriorityQueue<T,P> makes no promise about their relative order at all. If tie-breaking by arrival order genuinely matters, encode it explicitly — e.g. a compound priority combining urgency and a sequence number — rather than relying on undocumented behavior.
You don't need to hand-write one System.Collections.Generic.PriorityQueue<TElement, TPriority> (available since .NET 6) is a real, correct, built-in heap — exactly like List<T>/Dictionary<TKey,TValue> from earlier lessons, there's essentially never a reason to hand-roll this data structure in real code.

Best practice

  • Reach for a priority queue specifically when "process the most urgent thing next" is a real requirement. Not as a fancier-sounding substitute for a plain queue when arrival order was actually fine.
  • Be explicit about what "priority 1" means in your own code (most urgent, as in the example above, or least urgent). PriorityQueue<T,P> defaults to smallest-value-first, which surprises anyone assuming "higher number = higher priority" without checking.
  • Never rely on arrival order as a tie-breaker for equal-priority items. It's explicitly undocumented/unguaranteed behavior — encode any real tie-breaking rule into the priority value itself.

Better ways

If you need max-value-first behavior instead of the default min-first, don't invert your priority numbers everywhere as a workaround — PriorityQueue accepts a custom IComparer<T> in its constructor, letting you flip the ordering once, in one place, instead of remembering to negate every priority value at every call site.

Check your understanding

Why is peeking at the highest-priority item in a heap O(1), when peeking at the smallest item in an unsorted array would be O(n)?

  • The heap's defining rule guarantees the smallest (or largest) value is always sitting at the root — no search needed.
  • A heap keeps every element fully sorted at all times.
  • It uses the same hashing mechanism as a Dictionary.

Two transactions, TXN-1001 and TXN-1004, are enqueued into a PriorityQueue<string,int> with the exact same priority value, TXN-1001 first. Which one does Dequeue() return first?

  • Always TXN-1001, since it was enqueued first.
  • It's not guaranteed — either could come out first, and the order between equal-priority items isn't documented or promised.
  • It throws an exception, since two items can't share the same priority.
