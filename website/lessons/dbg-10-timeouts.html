Timeouts: Whose Problem Is It

A real ticket investigation: a payment flow was timing out against a slow stored procedure, and the proposed fix was sqlCommand.CommandTimeout = 0. That number deserves more scrutiny than it usually gets — walked through here with the actual test technique used to prove it.

The fact that changes how you think about this: CommandTimeout is enforced by the client, not the server

SQL Server has no idea your SqlCommand gave up When SqlCommand.CommandTimeout elapses, ADO.NET on the .NET side gives up waiting and throws a SqlException (Number == -2, "Execution Timeout Expired"). The query itself keeps running on SQL Server, completely unaware the caller walked away. This is why "did SQL run past the timeout" isn't something you can check in SQL Server or SSMS — there's no CommandTimeout concept there at all. It's purely a fact about how long the calling .NET code was willing to wait.

Why CommandTimeout = 0 is not "a generous timeout"

0 doesn't mean "wait a long time." It means no timeout — wait as long as the server takes, with no upper bound at all. For a call sitting in the synchronous path of a live payment request (a real customer's HTTP call blocked on it), that's a specific, considered trade-off, not a safe default:

  • A genuinely bounded slow query (the kind the ticket was actually about) now succeeds instead of timing out — which is the intended fix.
  • But a different failure mode — a real deadlock, a blocking chain, a connection that never resolves — now has no way to fail. The request just holds its thread and connection open indefinitely, and so does every other request queued behind it if this happens repeatedly.

The ticket's own suggested fix was a bounded increase (40 seconds, against an SP that normally finishes well under 30). Reaching for 0 instead trades a slow-but-recoverable failure for a scenario with no recovery path at all.

The testing technique: isolate the mechanism before testing through the full stack

Rather than proving this by driving the whole flow through Postman against a live SIT database and waiting out a real 30-second stored procedure, the mechanism was proven in a throwaway console harness first:

// Minimal, isolated: no business logic, no real stored procedure — just the mechanism.
var cmd = new SqlCommand("WAITFOR DELAY '00:00:05'", connection);
cmd.CommandTimeout = 2;   // shorter than the delay — should time out

try
{
    cmd.ExecuteNonQuery();
    Console.WriteLine("No timeout — unexpected");
}
catch (SqlException ex) when (ex.Number == -2)
{
    Console.WriteLine("Confirmed: timed out as expected");
}
Confirmed: timed out as expected

Three cases prove the whole mechanism cheaply: CommandTimeout shorter than the delay (throws, Number == -2), longer than the delay (succeeds, takes exactly as long as the delay), and CommandTimeout = 0 against the same delay (succeeds, waits the full delay, no exception regardless of how long it took). None of this needs the real stored procedure, the real database, or the real payment flow — proving the mechanism in isolation first, then trusting it applies to the real call site, is faster and removes noise (auth, business logic branches, real network latency) that has nothing to do with the question being tested.

A test scaffold left behind can look like the real bug During this investigation, the stored procedure under test was found to contain a hardcoded WAITFOR DELAY '00:00:01:01' with a malformed time literal (a colon instead of a period before the milliseconds segment) — not present in the procedure's own change history. Before treating a slow query as "the bug," check whether you're actually looking at test scaffolding someone left in a shared script, not the procedure's real, deployed behavior. Confirm who added it and why before drawing conclusions from it.

A related trap: don't let a green HTTP response stand in for a correct one

While validating this fix through Postman, an early test "went through" — HTTP 200 — and was treated as confirmation the fix worked. It wasn't: with CommandTimeout = 0, the call was never going to time out no matter what, so a 200 proved nothing about whether the changed code path had even executed. Worse, this codebase's own response contract makes HTTP status doubly unreliable as a signal on its own — a respCode field inside a 200 body still distinguishes success ("00") from a specific failure reason (every other value). A request can complete, return 200, and still represent a failed transaction. Never treat "the HTTP call went through" as equivalent to "the operation succeeded" — check the actual assertion the test needs, not just that a response arrived.

Best practice

When a synchronous, request-blocking database call needs a longer timeout: pick a bounded number justified by the query's normal running time plus margin, not 0. Prove the timeout mechanism itself in an isolated harness (a bare SqlCommand and WAITFOR DELAY) before wiring the real fix into business logic — it's faster to test and it separates "does the timeout mechanism work at all" from "does this specific call site use it correctly." And before calling any test a pass, confirm it actually exercised the failing condition — a request that "went through" isn't confirmation of anything if the change you made couldn't possibly have caused it to fail either way.

Check your understanding

Why can't you check "did the SQL query exceed its CommandTimeout" from inside SQL Server Management Studio?

  • CommandTimeout is enforced entirely on the .NET client side — SQL Server has no awareness of it and keeps running the query regardless.
  • SSMS doesn't display query execution duration.
  • CommandTimeout only applies when a stored procedure uses OPTION (RECOMPILE).

A colleague proposes fixing a payment-flow SQL timeout by setting CommandTimeout = 0. What's the strongest objection?

  • It will throw an exception immediately since 0 isn't a valid CommandTimeout value.
  • It removes any upper bound at all, so a genuine hang (deadlock, blocking chain) — not just a predictably slow query — can never fail gracefully; the request and its connection are held open indefinitely.
  • It makes every call to the database slower, even when nothing is wrong.
