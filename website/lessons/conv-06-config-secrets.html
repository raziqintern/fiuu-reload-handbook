Configuration & Secrets

Mechanisms only — no literal config values, connection strings, keys, or secrets appear anywhere in this lesson, matching the source handbook's own policy. Full source: conventions/configuration-and-secrets.md.

At least four distinct mechanisms coexist, layered by module and by how old the code is:

1. Classic appSettings

DirFileLogs = ConfigurationManager.AppSettings["dirFileLogs"] ?? string.Empty;

reload/class-library/Reloads/Game/Helpers/LogHelper.cs:20

The oldest, most universal mechanism — simple non-secret settings read via ConfigurationManager.AppSettings["Key"], resolved from whatever host application's config file is actually loaded.

2. A database-backed config table

Business/environment configuration is pulled from a CONFIGURATION database via a stored procedure, mapped into a generic KeyName/KeyValue model — this shape is reimplemented independently in more than one module rather than shared.

3. AWS Secrets Manager, gated by a big switch, cached in-process

Actual credentials (partner usernames/API keys) come from AWS Secrets Manager, never from appSettings. Which secret labels to expect is decided by a large switch on EventAppName ("which partner/app am I"), then every label resolves to a real value on first use and gets cached for the process lifetime.

Mechanism 2 bootstraps mechanism 3 The AWS access key/secret used to authenticate to Secrets Manager is itself pulled from the database-backed config table (mechanism 2), not from appSettings or an environment variable. If Secrets Manager calls start failing, the database-backed config is a real place to check first, not an unrelated system.

4. Plain-text connection-string files on local disk

private static string[] CONNECTION_DIRECTORIES = new string[] {
        "d:\\db",
        "c:\\db"
    };

reload/class-library/Database/Helpers/DBConnectionHelper.cs:12-15

Fiuu.Database's connection strings aren't read from a config file's <connectionStrings> section at all — they're read from a flat text file named after the database alias (e.g. d:\db\LOGGING.txt), searched across a hardcoded list of local directories, read as raw text, and cached in a static field.

The most fragile mechanism in the codebase This assumes a specific drive letter/folder exists on whatever machine runs the app, stores a connection string (which may itself embed a SQL login/password) unencrypted on local disk, and throws FileNotFoundException with no fallback if the file is missing. If you ever see a startup failure mentioning a missing file at d:\db\... or c:\db\..., this is the mechanism responsible.

A migration in progress: .NET Framework vs. .NET 8

public static string GetAppSetting(string sConfigKey)
{
    if (Environment.Version.Major >= 8)
    {
        //TO CATER FOR .NET VERSION 8 ONLY
        string sAppSettingsFilePath = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "appsettings.json");
        string json = File.ReadAllText(sAppSettingsFilePath);
        JObject jObject = JObject.Parse(json);
        return jObject[sConfigKey]?.ToString() ?? string.Empty;
    }
    else
    {
        return ConfigurationManager.AppSettings[sConfigKey] ?? string.Empty;
    }
}

This branches on the running CLR's major version rather than using a proper Microsoft.Extensions.Configuration abstraction — a clear, deliberate signal the codebase is being ported off classic .NET Framework toward modern .NET incrementally, module by module.

Check your understanding

A partner's API integration suddenly starts failing to authenticate. You suspect the credential from AWS Secrets Manager is stale. What's worth checking first, based on how these mechanisms actually chain together?

  • The AWS Secrets Manager console directly, since that's the final source of truth.
  • The CONFIGURATION database-backed values, since they supply the AWS credentials Secrets Manager itself is authenticated with.
  • The plain-text connection-string files under d:\db.
