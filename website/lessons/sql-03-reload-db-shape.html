SQL & reload_db

How reload_db Is Organised

From here on this track stops being generic SQL and starts being specifically about reload_db. This lesson is a summary of architecture/reload_db/00-overview.md — read that doc for the full module-by-module detail.

One SQL Server instance, ~20 separate databases

reload_db isn't one database with lots of tables — it's 20 real, actively-patched databases on one instance, one per business domain, each with its own `MAINT/` patch-script folder:

DatabaseRole
CEPPMaster data & back-office hub — org hierarchy, users/roles, product catalog, shared lookups. The most cross-referenced database in the whole estate; nearly everything else references it.
TRANSACTIONCore transaction staging + EOD/EOS reconciliation. Every terminal or API reload/payment request lands here first, with one integration schema per external provider.
TNG, INCOMM, BILL_PAYMENT, RESTORIFY, TICKET, PREPAIDProvider-specific integrations — each owns its own accounts/wallets/cards/campaign data for that partner.
REPORTSUMMARY → DataWarehouseDownstream settlement/billing aggregation, then a reporting star-schema fed daily.
EINVOICE, SAPMalaysia e-Invoicing and SAP Business One integration — both genuinely undocumented in the original team vault until this repo's own tracing found them.
RMS_OFFLINEThe consumer-facing self-service "Reload Offline" web app — its own largely-independent user base.

The data flow, in one sentence: a reload/payment request lands in TRANSACTION, gets routed to a provider-specific database, settlement rows land in REPORTSUMMARY, which feeds DataWarehouse — and almost every database along the way reads shared master data out of CEPP.

Why "one database per domain" matters when debugging If a merchant's reload succeeded in TRANSACTION but never showed up in a settlement report, the bug is very likely a hop between two of these databases (e.g. TRANSACTION → REPORTSUMMARY), not inside either one alone. Knowing the map above tells you where to look next instead of re-reading the same stored procedure five times.

Inside a MAINT folder: organised by object type

Every database's folder under reload_db/MAINT/<Name>/ has the same shape — subfolders by type of SQL object, not by feature:

reload_db/MAINT/TRANSACTION/
  Table/
  StoredProcedure/
  Function/
  Index/
  Type/
  Schema/
  Data/

One consequence worth internalising: a single business change ("add a column, and a stored proc to use it") lands as two separate files in two separate folders, tied together only by a shared ticket number in the filename. There's no single commit or PR-diff view that shows you "everything this ticket changed" the way you might expect from an application codebase.

Best practice

Before touching an unfamiliar table, check which database it actually lives in and what else references it — a change that looks locally correct in TRANSACTION can have downstream effects in REPORTSUMMARY or DataWarehouse that aren't visible from that one table alone.

Better ways

When a fix genuinely needs to touch both a table and a related stored procedure, note the shared ticket number in both filenames even though MAINT's folder structure keeps them physically apart (see Stored Procs, MAINT & NOLOCK) — it's the only thing that lets a future reader reconstruct "everything this change touched" later.

A reload transaction exists in TRANSACTION but is missing from a settlement report. Based on the data flow above, where's the most likely place to start looking?

  • Somewhere in the TRANSACTION -> provider DB -> REPORTSUMMARY hop.
  • Inside EINVOICE, since it's the newest addition to the estate.
