Threading, Locks & Race Conditions

Async/await (previous lesson) is about not blocking a thread. This lesson is about what happens when multiple threads genuinely run at the same time and touch the same data.

What a race condition actually is

Imagine two threads both run counter++ on a shared variable. That one line is really three steps: read the current value, add one, write it back. If both threads read the same starting value before either writes back, one increment is silently lost — the final count is wrong, and which run loses an increment (or whether it happens at all) is unpredictable. This is a race condition: correctness depends on timing that isn't guaranteed.

Why this can't be usefully "predicted and revealed" Unlike every other example on this site, a genuine race condition's wrong output isn't one fixed, reproducible value — it depends on real thread scheduling, which varies run to run. The honest teaching move here is to show you the fix's deterministic behavior below, not to fake a specific "wrong number" as if it were guaranteed.

Example: lock / SyncLock serializes access to a critical section

static readonly object _lockObj = new object();
static int counter = 0;

static void SafeIncrementBatch()
{
    for (int i = 0; i < 1000; i++)
    {
        lock (_lockObj)
        {
            counter++; // only one thread at a time can be inside here
        }
    }
}

static void Main()
{
    // Called sequentially here just to show correct, deterministic behavior —
    // the real value of `lock` is when multiple threads call this concurrently.
    SafeIncrementBatch();
    SafeIncrementBatch();
    Console.WriteLine(counter);
}
2000
Dim lockObj As New Object()
Dim counter As Integer = 0

Sub SafeIncrementBatch()
    For i As Integer = 0 To 999
        SyncLock lockObj
            counter += 1 ' only one thread at a time can be inside here
        End SyncLock
    Next
End Sub

Sub Main()
    ' Called sequentially here just to show correct, deterministic behavior —
    ' the real value of SyncLock is when multiple threads call this concurrently.
    SafeIncrementBatch()
    SafeIncrementBatch()
    Console.WriteLine(counter)
End Sub
2000

lock (C#) / SyncLock (VB.NET) guarantees only one thread can be inside the block touching counter at a time — any other thread that arrives has to wait its turn. That's what makes concurrent increments safe instead of racy.

Official documentation Microsoft's lock statement reference defines exactly what it guarantees: "Any other thread is blocked from acquiring the lock and waits until the lock is released. The lock statement ensures that at most only one thread executes its body at any moment in time." It also names something worth knowing before combining this with the previous lesson: "You can't use the await expression in the body of a lock statement." A lock and an await don't mix in the same block — awaiting can hand the thread to a different piece of work entirely, which defeats the whole point of holding an exclusive lock.
What if you lock on the wrong kind of object? Deadlock risk, not a syntax error The same reference's own guidelines section warns specifically against three common choices: "avoid using the following instances as lock objects: this, as callers might also lock this. Type instances, as they might be obtained by the typeof operator or reflection. string instances, including string literals, as they might be interned." All three compile without complaint — the real risk is that some other, completely unrelated piece of code might independently lock the exact same object (this, a shared Type, or an interned string with the same text), creating lock contention or a deadlock that has nothing to do with the logic you're protecting. A dedicated, private object created solely to be a lock — exactly like _lockObj/lockObj above — sidesteps this entirely, because nothing else in the program could possibly be locking on it.

The real cost of a lock: it can turn a small slowdown into a queue

This is exactly what happened in a real reload incident This is issue #2592, which gets a full worked-example treatment later in Debugging Reload → Worked Example — the short version here: every TNG reload transaction opened a certificate file and RSA-decrypted a session key from scratch, twice, and never released the handle — a resource leak. That alone would just get progressively slower. What made it a multi-hour queue instead of a mild slowdown: this all happened inside a per-account lock. As the leak made each lookup slightly slower, every other transaction for that same account had to wait behind it — the lock, which exists to keep things safe, was also what let a small per-request slowdown compound into a serialized backlog.

The lesson isn't "don't use locks" — the increment example above needed one. It's that a lock makes whatever's inside it a serialization point: anything slow inside a lock doesn't just cost that one caller, it costs every other thread waiting for the same lock.

Best practice

  • Keep the code inside a lock/SyncLock block as short and fast as possible. Nothing that does I/O, calls a network API, or opens a file/certificate should live inside one.
  • If you're debugging a "gets slower over time, especially under load, and a restart temporarily fixes it" report, check for exactly this shape. A resource leak sitting inside a lock.
  • Lock only on a dedicated, private object created solely for that purpose. Never on this, a Type instance, or a string — per Microsoft's own guidance, any of those could be locked by unrelated code elsewhere, causing contention or deadlock that has nothing to do with the resource you're actually protecting.
