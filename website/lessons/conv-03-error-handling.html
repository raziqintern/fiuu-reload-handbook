Error Handling

You learned in C# Fundamentals that catching Exception broadly is a code smell. Reload's real code does it constantly — on purpose. Full source: conventions/error-handling.md.

The dominant pattern: catch, log, return a sentinel — don't rethrow

public long AddGameSalesTransaction(GameSalesTransaction gameSalesTransaction)
{
    long iId = -1;
    ...
    try
    {
        ...
        iId = result.GetParameterValue<Int64>("@Id");
    }
    catch (Exception ex)
    {
        LogHelper.Error("AddGameSalesTransaction", gameSalesTransaction != null ? gameSalesTransaction.ReferenceId : null, "Unhandled exception.", ex);
    }
    return iId;   // caller cannot tell "-1 because of an exception" from "-1 because that's a real id"
}

reload/class-library/Reloads/Game/Providers/GameProvider.cs:15-46

Read that comment twice This is the pattern's real cost, called out in the source doc itself: the caller of AddGameSalesTransaction gets back -1 whether something threw an exception, or whether -1 is a legitimately meaningful value. The exception detail exists only in the log. If you're debugging "why did this transaction silently not save", the log — not the C# call site — is where the real answer lives.

This shape (wrap the whole method, catch Exception, log, return a safe default or an error-code DTO) is consistent across TNG, Game, Astro, and InComm. It's the de facto house style, even though nobody wrote it down anywhere.

The one narrower exception: known SQL constraint violations

Where duplicate-key detection matters for correctness — an idempotency check on a retryable network call — the code catches the specific SqlException, checks the error number, and rethrows everything else:

catch (Exception ex)
{
    if (ex is SqlException sqlEx && (sqlEx.Number == 2627 || sqlEx.Number == 2601))
    {
        auth.TransStatus = TransStatus.DuplicateTransNo;
        auth.ResponseMessage = "Trans No has been used.";
        return false;
    }
    throw;
}

reload/class-library/Reloads/TNG/Providers/TerminalProvider.cs:109-124

This is the one place in the sampled codebase where "catch broadly, but rethrow anything you didn't specifically expect" is done correctly. Worth knowing the two magic numbers: 2601 and 2627 are both SQL Server unique-constraint-violation error numbers.

Even here, consistency slips Those same two numbers also exist as a named enum elsewhere (SqlExceptionNumber.ViolationOfUniqueKeyConstraint = 2601) — but TerminalProvider doesn't use it, and re-inlines the raw numbers instead. Two ways of expressing the same check coexist in the same module. If you're adding a similar check, prefer the named enum — but don't be surprised to find the magic-number version elsewhere.

Logging code must never itself throw

LoggerDic[sKey].Log(sLogMessage);
...
catch
{
    // Logging must never take down a transaction.
}

reload/class-library/Reloads/Game/Helpers/LogHelper.cs:66-71

This is the one blanket empty catch in the sampled codebase that's clearly intentional, not incidental — and it's commented as such. The reasoning: a failure in logging infrastructure should never be allowed to crash or corrupt a real transaction in progress.

Best practice — for working inside this specific codebase

  • When adding a new catch block, check whether the caller already logs the same exception — if so, don't add a second log call here too (the double-exception-logging complaint from Debugging Reload → Reading the Logs First).
  • Prefer the named SqlExceptionNumber enum over re-inlining raw error numbers like 2601/2627 when you're the one writing the check — even though existing code sometimes does the opposite.

Better ways

The catch-log-return-sentinel pattern is a real, working house style, not a mistake to "fix" wholesale — but if you're adding a new code path (not modifying an existing one), consider whether a proper result type distinguishing "genuinely not found" from "an exception happened" would serve the caller better than an overloaded -1. That's a design choice to make deliberately, not a blanket rule to apply retroactively.

Check your understanding

You call a reload Provider method and it returns -1. Based on the dominant error-handling pattern, what does that tell you?

  • Definitely an unhandled exception occurred.
  • Definitely a legitimate result value, not an error.
  • It's ambiguous — you have to check the log to know whether -1 is a real value or a swallowed exception.

Why does the SQL-constraint-violation catch block check the specific error number (2601/2627) before deciding what to do, instead of just catching and handling any SqlException the same way?

  • Because a duplicate-key violation is expected and recoverable, but any other SQL error is not — and shouldn't be silently swallowed.
  • Checking the number is faster than catching the whole exception type.
  • SqlException doesn't support catching by type in C#.
