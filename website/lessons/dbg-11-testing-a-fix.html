Worked Example: Designing Test Cases for a Fix

A real merged change, MR !1916, added a new Bill Payment biller category (MBMBKW38) and loosened one validation rule while tightening another. Tracing the actual diff into a test matrix — rather than just clicking the happy path once — is what this lesson walks through.

Step 1 — read the diff for what it actually changed, not what the title implies

The MR's title suggests "add a new biller." The real diff was narrower and more interesting: four files, all validation-only, no new UI. Two independent rule changes, on the same field-length check:

If String.IsNullOrEmpty(sAccountNo) OrElse ((sBillerCode = "MBMBK" AndAlso (sAccountNo.Length < 6 OrElse sAccountNo.Length > 10)) OrElse
    (sBillerCode = "MBMBCT" AndAlso (sAccountNo.Length < 12 OrElse sAccountNo.Length > 14)) OrElse
    (sBillerCode = "MBMBSG" AndAlso (sAccountNo.Length < 11 OrElse sAccountNo.Length > 14)) OrElse
    (sBillerCode = "MBMBBR" AndAlso Not sAccountNo.Length = 13)) Then

reload/web/DEV/NET/Applications/Reloads/TerminalServer/Console/MessageHandlers/MessageHandlerBase.vb:205-208

The MBMBKW38 length branch that used to sit in this same OrElse chain (a fixed 12-character check on the payer identifier) is gone — removed, not added to. In its place, a new, unrelated rule appeared on a completely different field, in a different handler:

ElseIf terminalContentProduct.ServiceProviderProductCode = "MBMBKW38" AndAlso Not System.Text.RegularExpressions.Regex.IsMatch(If(sAccountNo2, String.Empty), "^\d{9}$") Then
    task.Status = TerminalMessageManager.EnumMessageStatus.InvalidReferenceNo

reload/web/DEV/NET/Applications/Reloads/TerminalServer/Console/MessageHandlers/BillPaymentAccountInquiryHandler.vb:1385-1386

So the real change is: PayerIc (account1) is now unrestricted in length/format for this one biller, and IncomeCode (account2) must now be exactly 9 digits — a brand-new constraint that didn't exist before. Two different fields, two opposite directions (one loosened, one tightened). A test plan built from the title alone ("added MBMBKW38") would miss that this is really two separate rule changes layered on one category.

Step 2 — build a boundary-value matrix, not one happy-path click

For the loosened field (PayerIc), the useful test isn't "does a valid value still work" — it's proving the old boundary still works and values outside it now also work, without silently breaking the field's other guard (empty-string rejection, untouched by this diff):

#account1 (PayerIc)Why this valueExpected
1aA1234567 (8-char, passport-style)The case the MR exists forAccepted
1b123456789012 (12 digits — the old fixed length)Confirms the previously-required length still works, not just that other lengths now also doAccepted
1c1234567 (7 digits, below the old boundary)Would have failed before; must pass nowAccepted
1d(empty string)A separate, untouched guard earlier in the same handler — must still rejectRejected (InvalidAccountNo)

Row 1d is the one that isn't in the MR's own checklist, but it's exactly the kind of case worth adding: it proves the fix didn't accidentally widen scope beyond what it intended to change. "Length restriction removed" and "no restriction at all, including on emptiness" are different claims, and only one of them is what the diff actually does.

The same discipline for the tightened field For IncomeCode (now must be exactly 9 digits), the matrix is the mirror image: 9 digits exactly (accept), 8 and 10 digits (reject, one on each side of the boundary — confirms it's not an off-by-one), and confirm the rejection maps to the right response code (InvalidReferenceNo), not a generic failure that would also fire for an unrelated reason.

Step 3 — a real result that looked like a new bug, but wasn't

Running the regression pass across the four existing MBMB categories (MBMBK, MBMBCT, MBMBSG, MBMBBR — all untouched by this diff, but now sitting one line away from the removed branch), one test came back Invalid Amount for MBMBCT. The instinct is to assume the account-number diff broke something nearby. It didn't — checking the biller's own config turned up a completely unrelated, pre-existing constraint:

"PaymentMaxAmt": 10000.00, "PaymentMinAmt": 1.00

The test's amount value happened to sit outside MBMBCT's own configured min/max range — a constraint that has nothing to do with the account-number length logic under test. Before attributing a failing test to the change you're verifying, confirm the failure is actually reachable from that change — a different, pre-existing rule triggering on an incidentally-chosen input value is not a regression.

Step 4 — regression coverage means proving what didn't move, not just what did

The MR's own checklist asked for one happy-path Initiate→Confirm per existing biller. Since the actual code edit was a deletion from a shared OrElse chain — the exact kind of edit where an off-by-one can silently shift a neighboring condition — the more complete version adds one boundary-failure case per untouched biller too (one length just past each biller's own valid range), specifically because this fix's edit sat directly inside the chain those checks live in. A checklist written before the diff exists can't know which lines are riskiest to touch; reading the actual diff can.

Best practice

When testing a fix: read the diff first to find every field it actually touches (not just the one the title mentions), build a boundary-value matrix around each one (the old boundary, just inside the new range, just outside it, and any separate untouched guard nearby), and before blaming a failing result on your change, check whether a completely different, pre-existing rule could explain it. Regression tests on sibling code paths should specifically target whatever's structurally closest to the actual edit (a shared conditional chain, a shared helper) — that's where an unintended side effect is most likely to hide.

Check your understanding

A test of an untouched, sibling biller category returns "Invalid Amount" during regression testing of an account-number validation fix. What's the right next step?

  • Assume the account-number fix has a side effect on amount validation and start reading that diff again.
  • Check whether the failing field (amount) is actually governed by the code you changed, or by a separate, pre-existing rule the test happened to trip.
  • Just change the test's amount value and move on without investigating why it failed.

Why does testing the exact old boundary value (12 digits, the previously-required length) still matter, once a length restriction has been removed entirely?

  • It confirms the fix genuinely widened the accepted range instead of accidentally shifting or breaking the one value that used to be the only valid one.
  • It's only relevant for display formatting, not validation logic.
  • It measures whether the new, unrestricted code path runs faster than the old one.
