Error Handling: Try/Catch, When & Is Nothing

The core Try/Catch/Finally structure is identical to C#'s — same .NET exception types underneath, VB.NET's block-keyword syntax on top. Two real VB-specific tools sit on top of that: a When filter on a Catch, and the Is/IsNot operators every null check in this codebase actually uses.

Function Divide(a As Double, b As Double) As Double
    If b = 0 Then
        Throw New DivideByZeroException("Cannot divide by zero")
    End If
    Return a / b
End Function

Sub Main()
    Try
        Dim result As Double = Divide(10, 0)
        Console.WriteLine(result)
    Catch ex As DivideByZeroException
        Console.WriteLine("Error: " & ex.Message)
    End Try
    Console.WriteLine("Program continues")
End Sub

Program continues

Finally still always runs

Try
    Console.WriteLine("Attempting reload...")
    Throw New Exception("Gateway timeout")
Catch ex As Exception
    Console.WriteLine("Caught: " & ex.Message)
Finally
    Console.WriteLine("Cleanup: closing connection")
End Try

Caught: Gateway timeout

Because it's the same .NET runtime DivideByZeroException, Exception, and every other exception type here are the exact same .NET Base Class Library types C# uses — VB.NET and C# share one runtime and one set of framework types. This is the whole reason the two languages are basically a syntax skin over the same underlying platform.

Catch ... When — a filter, not just a type match

Catch can add a When condition, so the catch block only runs if both the exception type and the condition match — otherwise VB.NET keeps looking for a different matching Catch, or the exception propagates up if none matches:

Try
    CallExternalApi()
Catch ex As WebException When TypeOf ex.Response Is HttpWebResponse AndAlso CType(ex.Response, HttpWebResponse).StatusCode = HttpStatusCode.NotFound
    Console.WriteLine("Endpoint not found — check the URL")
Catch ex As WebException
    Console.WriteLine("Some other network failure: " & ex.Message)
End Try
Official documentation Microsoft's Try...Catch...Finally statement reference is specific about the filter's evaluation order: "A When clause is applied only after checking the type of the exception." Its own worked example proves what happens when a When condition is False even though the type matched — VB.NET keeps examining later Catch clauses rather than stopping: given Catch e As OverflowException When i = 5 (type doesn't match the thrown exception) then Catch e As ArgumentException When i = 4 (type matches, but i = 4 is False) then a final type-less Catch When i = 5, throwing an ArgumentException with i = 5 actually prints "Third handler" — the second Catch matched the type but failed its filter, so control moved on rather than raising an error or re-throwing.
When to reach for a When filter vs. checking inside the Catch A When filter is worth it specifically when you have multiple Catch blocks for the same exception type, each wanting different handling depending on some detail of the exception (a status code, an error number). If there's only one Catch for that type, an If inside the block is equally clear and doesn't need the extra syntax — reach for When once you'd otherwise need nested Ifs inside a single catch block just to re-dispatch on the same condition a When filter could express in the Catch line itself.

Is Nothing / IsNot Nothing — not just style, a real distinction

Real, verified code from this exact codebase, showing both the recommended form and the older, more awkward one still present in production:

If lstTerminalModel Is Nothing Then ...
If lstTerminalModel IsNot Nothing And lstTerminalModel.Count > 0 Then ...

IsNot exists specifically so you don't have to write the second, more awkward form — Not x Is Nothing and x IsNot Nothing mean exactly the same thing, but IsNot reads directly instead of needing a mental double-negative. Both forms are real, currently-shipping code in this codebase — a reminder that "the codebase does X" isn't always uniform, and reading the older form correctly matters as much as writing the newer one.

Official documentation Microsoft's Is operator reference defines the comparison precisely: "The Is operator determines if two object references refer to the same object. However, it does not perform value comparisons." That second sentence is the entire reason it exists as a separate operator from = — a value-comparison operator and a reference-identity operator answer genuinely different questions, and only one of them is safe against being silently redefined by an overloaded =.
Why Is/IsNot exist at all instead of just using = and <> Is and IsNot are specifically for reference comparison — "do these two variables point at the same object" — and only work on reference types. Using = for this can give incorrect or unintended results because = can be intercepted by an overloaded equality operator that compares by value instead of by reference identity; Is/IsNot always compare identity, with no possibility of being overridden to mean something else. This is exactly why checking for Nothing specifically should always be Is Nothing/IsNot Nothing, never = Nothing.

Best practice

  • Use modern Try/Catch/Finally in all new code. If you ever encounter VB6-era On Error Goto style error handling in genuinely old code, know that it's a different, older model entirely (a jump target, not structured exception handling) and don't try to mix the two styles in the same procedure.
  • Always use Is Nothing/IsNot Nothing for null checks, never = Nothing. Treat any = Nothing you find in existing code as worth a second look, not necessarily as broken, but as a pattern not to copy forward.
  • Order Catch blocks from most specific to least specific, and always finish with a catch-all if you have one. Once a Catch As Exception (or a bare Catch) appears, every Catch after it is unreachable — the documentation is explicit that control can never reach a later clause.

Better ways

Just as in C#, catch the most specific exception type you actually expect (DivideByZeroException above), not a blanket Catch ex As Exception that would also hide a genuine bug you'd rather see fail loudly and get fixed. See Debugging Reload → The Response That Was Never Real for a real production incident caused by exactly this — a broad catch swallowed the real failure and let the caller trust an object that was never actually valid.

Check your understanding

Why do VB.NET and C# use the exact same exception types (Exception, DivideByZeroException, etc.)?

  • It's a naming convention both language communities happened to agree on.
  • Both languages compile to the same .NET runtime and share the same underlying framework class library.
  • VB.NET code gets translated into C# before compiling.

Why prefer x IsNot Nothing over x = Nothing to check whether an object reference is null?

  • Is/IsNot always compare reference identity directly, while = can be overloaded to compare by value instead, giving incorrect results for a null check.
  • x = Nothing doesn't compile for reference types in VB.NET.
  • IsNot runs faster at runtime than the equivalent = comparison.

An ArgumentException is thrown into a block with Catch e As OverflowException When i = 5 first, then Catch e As ArgumentException When i = 4 (with i actually equal to 5), then a final Catch When i = 5. Which handler runs?

  • The first handler — its When i = 5 condition is true.
  • The second handler — its exception type matches what was thrown.
  • The third handler — a type mismatch or a failed When filter both just move on to the next Catch, and this is the first one that both matches and passes its filter.
