reload_db: Topology & Modules

You covered the SQL-level conventions of reload_db in the SQL track. This lesson zooms out to the whole-estate picture. Full source: architecture/reload_db/00-overview.md.

reload_db is a change-management repo, not a deployable app

reload_db is its own independent git repository, separate from reload. It contains no application code — just MAINT/<DatabaseName>/ folders of hand-written SQL patch scripts, one folder per database, plus a couple of console tools used to apply those scripts against a live database.

One SQL Server instance, 20 real databases

Recapping from the SQL track: reload_db is 20 separate, actively-patched databases on one instance, not one database with many tables. The full list and roles are in SQL & reload_db → How reload_db Is Organised — worth re-checking that table any time you're trying to figure out which database owns a piece of data you're chasing.

How the application side actually connects

No connection strings live in any web.config/app.config anywhere in the reload repo. Two separate, unrelated mechanisms exist instead:

WhatMechanism
SQL Server connection stringsRead from a flat text file named <alias>.txt (e.g. LOGGING.txt) in a hardcoded local directory (d:\db\ or c:\db\) — see Conventions → Configuration & Secrets.
Partner/integration credentialsAWS Secrets Manager, gated by an app-identity switch, cached in-process — a completely separate mechanism from the SQL connection strings above.

Only three connection-string aliases were confirmed directly in application code: RMS_Offline, LOGGING, and Notification — corresponding to three of the 20 databases. How the other 17 databases' connections are resolved wasn't traced in this pass; treat it as an open question rather than assuming the same three-alias mechanism covers everything.

The estate is still being actively corrected

Two whole databases were missing from the team's own documentation The original internal vault claimed "16 separate databases." Tracing the live MAINT/ folders directly found at least 20 — the vault's 16 plus EINVOICE and SAP, both genuine, actively-patched databases with zero mentions anywhere in the team's existing 260KB schema vault. This is a useful reminder: even "official" internal documentation here can lag behind what's actually running in production — cross-check against the live MAINT/ scripts, not just whatever doc you find first.

  • In a plain text file named LOGGING.txt in a hardcoded local directory (d:\db or c:\db) on the deployed machine.
