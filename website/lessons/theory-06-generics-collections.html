Generics & Collections Internals

You've used List<T> and Dictionary<TKey,TValue> since Algorithms & Data Structures. This lesson is why the <T> exists and what's actually happening inside them.

The problem generics solve

Without generics, you'd either write a separate IntList, StringList, TerminalList... for every type (massive duplication), or write one list that stores object (losing type safety, and — per Boxing & Unboxing — boxing every value type you put in it). Generics let you write the logic once, parameterized by a type, with full compile-time type safety and no boxing.

Example: one generic method, two types, no duplication

static T Max<T>(T a, T b) where T : IComparable<T>
{
    return a.CompareTo(b) > 0 ? a : b;
}

static void Main()
{
    Console.WriteLine(Max(10, 25));
    Console.WriteLine(Max("apple", "banana"));
}
25
banana
Function Max(Of T As IComparable(Of T))(a As T, b As T) As T
    If a.CompareTo(b) > 0 Then
        Return a
    Else
        Return b
    End If
End Function

Sub Main()
    Console.WriteLine(Max(10, 25))
    Console.WriteLine(Max("apple", "banana"))
End Sub
25
banana

where T : IComparable<T> is a generic constraint — it tells the compiler "only allow types that can actually be compared," so a.CompareTo(b) is guaranteed to exist. Without it, the compiler couldn't verify CompareTo is callable on an arbitrary T. The same one method body works for int and string here, and would work for any other comparable type — no copy-pasted overload needed.

Official documentation Microsoft's Constraints on type parameters reference explains exactly why the constraint is required here, not optional: "Without any constraints, the type argument could be any type. The compiler can only assume the members of System.Object." CompareTo isn't a member of System.Object — without where T : IComparable<T>, the compiler has no way to know a.CompareTo(b) is even callable, so it simply refuses to compile the method body at all.

What's actually inside List<T> and Dictionary<TKey,TValue>

TypeInternal structureWhy it matters
List<T>A plain array that automatically resizes (typically doubling) when it runs out of roomAdding to the end is usually O(1), but occasionally O(n) when a resize happens — inserting in the middle is always O(n) (everything after has to shift).
Dictionary<TKey,TValue>A hash table — each key is run through a hash function to compute roughly where it livesThis is why lookups are close to O(1) — see Big O Notation and Stacks, Queues & Dictionaries.
Official documentation Microsoft's Dictionary<TKey,TValue> reference states the rule as a hard requirement, not a suggestion: "As long as an object is used as a key in the Dictionary<TKey,TValue>, it must not change in any way that affects its hash value."
A hash table needs a good, stable key Dictionary's O(1) lookup depends on the key type having a correct GetHashCode()/Equals() pair. Using a mutable object as a dictionary key, then changing a field that affects its hash code after inserting it, can make that entry unfindable — the dictionary is still looking in the bucket for the old hash. Strings (as reload's real Dictionary<string,string> secrets cache uses) are immutable, which sidesteps this entirely — one more reason immutable keys are the safe default.

Best practice

  • Default to List<T> and Dictionary<TKey,TValue> for almost everything. Reach for a different collection only when you specifically need its distinguishing behavior — Stack<T>/Queue<T> for strict LIFO/FIFO order, HashSet<T> when you only care about unique membership, not order or key-value pairing.
  • Never use a mutable object as a dictionary key unless you can guarantee its hash-relevant fields never change while it's a key. Prefer an immutable type (a string, a record, a value type) as the safe default.

Check your understanding

Why does where T : IComparable<T> need to be on the generic Max<T> method above?

  • Without it, the compiler can't guarantee an arbitrary type T actually supports .CompareTo(...).
  • It controls how much memory the method is allowed to allocate.
  • It makes the method run faster at runtime.

A mutable class is used as a Dictionary<TKey,TValue> key. After inserting it, one of its fields that GetHashCode() depends on is changed. What happens when the code later tries to look up that same key?

  • The lookup can fail to find the entry — the dictionary is still looking in the bucket for the key's original hash code, not its current one.
  • The dictionary automatically re-indexes the entry to its new hash bucket.
  • It throws an exception the moment the key's field is changed.
