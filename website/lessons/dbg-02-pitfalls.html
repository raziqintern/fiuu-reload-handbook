Known Patterns & Pitfalls

A curated set of recurring smells, framed descriptively, not as indictments — this is what you'd expect from a production fintech codebase extended by many hands over many years without a documented standard. Full source: conventions/known-patterns-and-pitfalls.md.

A real, broken exception that shipped to production

public TNGEODException()
{
    new TNGEODException(terminalId, businessDate, messageNo);   // constructs and discards a second instance
}

public TNGEODException(int terminalId, DateTime businessDate, string messageNo)
{
    this.terminalId = terminalId;
    this.businessDate = businessDate;
    this.messageNo = messageNo;
}

public override string Message
{
    get { return base.Message; }   // never surfaces terminalId/businessDate/messageNo
}

reload/class-library/Reloads/TNG/Exceptions/TNGEODException.cs:14-33

What's actually wrong with the parameterless constructor above?

  • It won't compile — you can't call new inside a constructor.
  • It constructs and discards a second, separate instance instead of chaining to the parameterized constructor with : this(...) — this object's fields are never actually set.
  • terminalId is used before it's declared.

Nothing in the sampled code appears to construct this exception via the parameterless constructor — probably why the bug was never noticed. Treat this as a real signal: custom exception types in this codebase are not uniformly battle-tested just because they exist and compile.

Spot the bug: an unguarded dropdown reset

This exact bug shipped as issue #2190 ("Exception 43"): selecting a supplier in a dropdown, then changing it back to a placeholder option, then saving.

The save throws Conversion from string "" to type 'Integer' is not valid. Based on what you now know about dropdown-driven forms, what's the root cause?

  • The placeholder option's empty-string value flows straight into a strict Integer conversion with no guard against it.
  • The database column doesn't allow NULL and something tried to insert NULL.
  • The dropdown's options failed to load over the network.

The fix in this codebase is always the same shape: guard against the placeholder/default option explicitly, not just against blank text input — a dropdown's "nothing selected" state is a distinct case from an empty string.

Spot the bug: cents vs. ringgit

This exact bug shipped as issue #2346: JomPay topup confirmation emails showed amounts 100x too large.

// amount arrives from the partner API in cents, as an integer
int amountInCents = 3000000;

// bug: formatted directly as if it were already ringgit
Console.WriteLine("MYR " + amountInCents.ToString("N2"));
MYR 3,000,000.00

The intended amount was RM 30,000.00 — 100x smaller. The fix was pure format-conversion: divide by 100 before formatting, since the partner's API contract sends cents, not ringgit. The same ticket also found the confirmation email was sent before the balance update, so the displayed "new balance" was the pre-topup balance — two separate bugs discovered in the same investigation.

The general lesson, not just this one bug Whenever a value crosses a partner boundary (amount, date, timestamp), check the unit/format the partner expects or sends — not what's convenient internally. Cents-vs-ringgit and date-only-vs-datetime are both real, previously-shipped bugs in this exact codebase, not hypothetical warnings.

Spot the bug: a swallowed exception hides a resource leak

A "Resend Email" action was silently failing to record its audit entry, every single time, in a way that looked at first like a stale one-off lock. The real cause was structural, in the email-sending code itself:

try
{
    var mail = new Mail();
    ...
    mail.AttachmentPath = AttachmentPath;   // opens a file handle on the zip attachment
    ...
    mail.Send();      // if this throws (e.g. no reachable SMTP server)...
    mail.Dispose();   // ...this NEVER runs — no try/finally, no using
}
catch (Exception ex)
{
    Logger.WriteErrorToEventLogs(ex);   // swallows the exception, hides the real failure
}

reload/web/DEV/NET/Components/CEPP/Services/ReportService.cs — SendEmailReportWithCC

Why the failure shows up somewhere else entirely When mail.Send() throws, mail.Dispose() is skipped, so the file handle on the zip attachment leaks. The exception itself is swallowed and logged — so nothing appears to fail at the point of the actual bug. But a later, unrelated-looking line — File.Delete(sZipFilename), cleaning up the same zip — then fails because the file is still locked, and that exception propagates and aborts the calling method before it ever reaches the audit-log write. The visible symptom (a missing audit row) is two method calls and one swallowed exception away from its actual cause.

The general shape to recognise: a try/catch with no matching finally/using around something that opens a resource, combined with a catch that logs and swallows rather than re-throwing. Either half alone is often fine; together, they let a leak in one method surface as a mysterious failure in a completely different one.

Spot the bug: an implicitly-Nothing function crashes every caller

Issue #2461: searching a BackOffice list with any status other than "All"/"Approved" threw Object variable or With block variable not set. The cause was a filter function, typed to return Object, that fell off the end of its own method on the empty-result path instead of explicitly returning an empty collection:

If lstTerminalFirmwareVersion.Count <= iMaxRow Then   ' crashes here — .Count on Nothing

reload/web/DEV/NET/Applications/CEPP/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb — fixed in MR !1906

Any status filter that legitimately matched zero rows left the underlying function implicitly returning Nothing — never explicitly, never documented, just a fall-through. Every caller that assumed a real (if empty) collection came back crashed instead.

This isn't a one-off — it's the single largest cluster of open crash tickets A pass across this project's open "[Issue] Exception N" crash-report series found 18 tickets from the same automated crash-reporting mechanism. 8 of the 18 shared this exact shape: Object reference not set/Object variable or With block variable not set, traced back to a method that returns Nothing instead of an empty collection on some path. That's nearly half of all open crash reports in this one recognisable pattern — worth actively searching for (any Object- or interface-typed method with a return path that isn't an explicit Return New List(Of ...)/empty result), not just fixing reactively one ticket at a time.

Spot the bug: two enums, one shared name

A BackOffice payment-enquiry feature reads a "service type" value on both a list page and its detail page, using what looks like the same identifier passed straight through a query string.

Investigation turned up two separate enums in the codebase, both representing "which service type is this," both fed by variables named almost identically (iServiceTypeId). EnumPOSAPIServiceType defines GiftCard = 3; a second, unrelated enum, ServiceProviderType, defines TopUp = 3 — same numeric value, different meaning. The two enums aren't mixed together anywhere today. What's the actual risk?

  • Nothing breaks yet only by accident — a local variable currently shadows the class-level property that would otherwise mix the two enums, but that's fragile, not a real safeguard, against a future refactor.
  • The compiler already prevents this from ever causing a bug, since the two enum types are distinct.
  • It's purely a style issue — since the enum names are different, there's no functional risk.
Why this kind of collision hides for years Several values happened to match in both enums (BillPayment, Razer_Cash, Ticket, CarbonOffset all share the same number in both) — which is almost certainly why nobody noticed the other three that don't. When two enums represent "the same kind of thing" from two different eras of the codebase, check whether their values actually agree member-by-member before assuming a property or variable name that matches one also safely matches the other.

Known pattern: the record exists, but the UI shows nothing

A real, repeated investigation shape: a product/record is confirmed present and correct in the database, yet a BackOffice search page returns nothing for it — no error, just an empty result.

Two confirmed causes, same symptom In one investigation, a product's ProductGroup had gone InActive — and the search page's own dropdown only ever loads Active groups (Where productGroup.Status = EnumStatus.Active), so the group itself was never selectable, regardless of what products sat under it. In another, a product's linked ServiceProvider had a CountryId that didn't match the logged-in user's own country — a stored procedure filter (WHERE @iCountryId = 0 OR SP.CountryId = @iCountryId) silently excluded it before the C# code ever saw it. Neither case was a data bug; both were a silent scoping filter applied one layer above the record you're looking at.

The lesson generalizes: before concluding "the record is missing or corrupted," check every dropdown and filter between the record and the search results for a silent Status/Active/CountryId condition — this codebase applies that kind of scoping constantly, and it produces exactly the same "empty result" symptom as genuinely missing or bad data.

Spot the bug: a validation that fires almost every time, including on valid input

Submitted for review on MR !1910, meant to reject a blank or non-numeric quantity field:

If Not String.IsNullOrWhiteSpace(txtQuantity.Text.Trim()) Or Not IsNumeric(txtQuantity.Text.Trim()) Then
    MessageBox.ShowErrorMessage("Quantity must be a numeric")
    Return False
End If

' Trace it by hand for txtQuantity.Text = "5" — a perfectly valid quantity:
IsNullOrWhiteSpace("5")  = False  -->  Not False           = True
IsNumeric("5")           = True   -->  Not True            = False
                                        True Or False       = True   <- condition fires!
"Quantity must be a numeric" shown, even though 5 is a valid number.

Apply De Morgan's law to see why this was never going to work as written: Not A Or Not B is logically identical to Not (A And B). Since a blank string and a valid number can never both be true of the same input at once, A And B (blank and numeric, simultaneously) is essentially never true — which means Not (A And B) is essentially always true, and the error fires almost unconditionally, valid input included. The author needed the fields combined with And, not Or: reject only when the text is blank or non-numeric, i.e. String.IsNullOrWhiteSpace(...) OrElse Not IsNumeric(...) — no Not in front of the whitespace check at all.

The general lesson Whenever a boolean condition mixes Not with Or/And across more than one variable, don't eyeball it — trace it by hand for at least one case each of "should pass" and "should fail," the same way you'd trace any other suspicious conditional. This exact shape of mistake is easy to get wrong by inspection alone, which is exactly why it reached a merge request instead of being caught while writing it.

Best practice

Treat every pattern on this page as a checklist item when reviewing a diff in an unfamiliar part of this codebase, not just trivia — a dropdown reset to its placeholder, a value crossing a partner boundary, an unused function about to be deleted. Recognising the shape is what turns "this looks fine to me" into "wait, isn't this the same thing that broke in #2190?"

A report scheduler was changed to remove its row limit, "since we want all the data now." What should a reviewer flag, based on real review history?

  • An unbounded query risks holding the database under load — match the default limit convention used by sibling reports instead.
  • The report's column headers probably need updating too.
  • Nothing — more data is always better for a report.
