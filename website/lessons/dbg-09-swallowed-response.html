Debugging Reload

Worked Example: The Response That Was Never Real

A real production incident from reload's offline-payment integration (issue #2546): a NullReferenceException whose stack trace pointed at the wrong method entirely — because the real point of failure had already caught and hidden its own exception before the crash ever happened.

The symptom, as it was reported

A NullReferenceException with a suspiciously short stack trace Production logs showed a crash inside MolPayOfflinePaymentService.ApiCall_PaymentPreCreate(), with OfflineService.PreCreatePayment as its only caller above it. The method that actually makes the outbound HTTP call — RequestWebApi() — never appears in the trace at all, even though it's the method sitting directly between them in the source.

Step 1 — a method missing from its own crash is a clue, not a mystery

The instinct is to assume the stack trace is incomplete or that the file has drifted since the crash. Both are worth a five-second check (git log --since=<date> -- <file> — in this case, no commits since the incident, so the code hadn't moved). But there's a more common explanation, and it's the right one here: a method can be the true site of failure and still never appear in the trace, if it catches its own exception and never rethrows. From the caller's point of view, a swallowed exception looks exactly like a normal return — just possibly with a broken result inside it.

Step 2 — the actual code, and the gap between two try scopes

protected HttpResponseMessage RequestWebApi(string method, string url, Dictionary<string, string> param)
{
    HttpResponseMessage responseMessage = new HttpResponseMessage();   // line 70 — default StatusCode is 200 OK, Content is null
    ...
    try
    {
        ...
        HttpWebRequest request = (HttpWebRequest)WebRequest.Create(url);
        request.ContentLength = byteArray.Length;
        Stream stm = request.GetRequestStream();                       // line 89 — OUTSIDE the inner try below
        stm.Write(byteArray, 0, byteArray.Length);

        HttpWebResponse response;
        try
        {
            response = (HttpWebResponse)request.GetResponse();          // line 97 — the ONLY call wrapped by the safety net
        }
        catch (WebException e)
        {
            response = (HttpWebResponse)e.Response;                     // builds a graceful "M1" stub response below
        }

        if (response == null)
        {
            responseMessage.Content = new StringContent("{\"statusCode\": \"M1\"}", ...);
            throw new Exception("Failed to get response from HttpRequest.");
        }
        responseMessage = new HttpResponseMessage(response.StatusCode); // real success path
        responseMessage.Content = new StringContent(...);
    }
    catch (Exception ex)                                                // line 115 — logs, does NOT rethrow
    {
        LogHelper.Write(string.Format("... [System Error: {0}]", ex.Message), userId);
    }

    return responseMessage;   // whatever it was left as when the try block gave up
}

reload/web/DEV/NET/Components/CEPP/Payment/OfflinePayment/Fiuu.Reloads.OfflinePayment/Services/MolPayOfflinePaymentService.cs:68-121

The method has exactly one safety net — the inner try/catch (WebException e) around GetResponse() — and it exists specifically to hand back a usable stub response ({"statusCode": "M1"}) if the HTTP call itself fails. But request.ContentLength = byteArray.Length is set before this, and for a POST with a real body, HttpWebRequest actually opens the TCP connection at GetRequestStream() — line 89 — not later at GetResponse(). That line sits outside the inner try. A connection failure there (exactly what production hit: "Unable to connect to the remote server") skips the safety net entirely, falls straight into the broad outer catch (Exception ex), gets logged, and is never rethrown.

Official documentation Microsoft's own HttpWebRequest.GetRequestStream reference lists WebException among the exceptions this specific method can throw — "An error occurred while processing the request" — confirming this isn't a method that only ever succeeds or fails silently: a connection failure genuinely surfaces as an exception right here, at the point the two nested try scopes in this code don't agree on who's responsible for catching it.
What that means for responseMessage Nothing between line 89 and the outer catch ever ran. responseMessage is returned exactly as constructed at line 70: a brand-new HttpResponseMessage() whose default StatusCode is 200 OK and whose Content was never assigned — null. Not the "M1" stub. Not a real response. A blank object that looks, from the outside, like a legitimate empty success.

reload/web/DEV/NET/Components/CEPP/Payment/OfflinePayment/Fiuu.Reloads.OfflinePayment/Services/MolPayOfflinePaymentService.cs:46-54

ApiCall_PaymentPreCreate checks StatusCode != OK to detect failure — a completely reasonable check, except the untouched default object is also OK. So it falls into the success branch and dereferences .Content, which is null. That's line 54, exactly where the exception log points — and it's a perfectly true report. It's just not where the actual bug lives.

The generalizable pattern

A broad catch-and-swallow is dangerous specifically when its method returns a value the caller treats as authoritative catch (Exception ex) { Log(...); } with no rethrow doesn't just hide an error — it lets execution continue as if nothing happened, handing the caller whatever partial state existed at the moment of failure. If that return value is later checked with an incomplete signal (here, "is StatusCode not OK?" — but a never-set default is also "OK"), the caller can't distinguish real success from silently absorbed failure. When a stack trace's crash point sits right after a call to a method with this shape, treat the returned object as suspect before trusting the line the trace points to.

Debugging technique worth stealing

Reproducing this required getting a real TCP connection failure to happen specifically during GetRequestStream() rather than GetResponse() — timing-dependent and awkward to force live (hosts-file redirects, firewall rules, a real unreachable host). The actual, faster path: force the exact object state directly in the debugger — set a breakpoint where RequestWebApi() returns, and override responseMessage in the Immediate window to a brand-new, completely untouched HttpResponseMessage(). That's a faithful stand-in for the real failure, not a shortcut around it, because it reproduces the exact object state the real code path produces — and it's available without touching a shared dev box's network config at all.

One more discipline this incident surfaced: when testing a hypothesis, change one variable at a time and confirm the other precondition is still true. A test that set ContentLength = 0 and got "no exception, request went through" proved nothing about the ContentLength > 0 theory — the connection wasn't actually broken during that particular run, so of course it succeeded. Two changed conditions, one observed result, is not a test of either one alone.

Best practice

  • Whenever you write a method with an outer catch-and-log-and-swallow around a whole method body, ask whether this method's return value gets checked for success by the caller. If so, make sure every exit path — including the one your outer catch falls through to — leaves that return value in a state the caller's check can correctly classify as failure. A default-constructed object is rarely a safe stand-in for "this failed."
  • When testing a hypothesis about a failure condition, change exactly one variable at a time and confirm the other precondition still holds. A test that changes two things and observes one result proves nothing about either variable alone — reproduce the exact failure condition, don't approximate it.

Check your understanding

Why does the exception in this incident get logged at line 54 of ApiCall_PaymentPreCreate, instead of inside RequestWebApi where the real connection failure happened?

  • The file changed after the incident, so the line numbers no longer match.
  • RequestWebApi already caught and swallowed the real exception without rethrowing — the NullReferenceException at line 54 is a second, separate exception, caused by the caller trusting the untouched object it got back.
  • responseMessage itself is null, and the null-check on line 48 has a bug.

What made the debugger-forced repro ("manually set responseMessage to a fresh HttpResponseMessage()") a faithful reproduction of the bug rather than a cheat?

  • It reproduces the exact object state that a real connection failure at GetRequestStream() would leave behind — same shape, same missing Content, same default StatusCode.
  • It works because it actually breaks the real network connection to the sandbox host.
  • It's unrelated to the actual fix, just a way to trigger some exception for the log.
