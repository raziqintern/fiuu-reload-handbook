Joins & Filtering

Real questions almost never live in one table. "Show me every transaction, with the merchant name attached" needs a join.

INNER JOIN: rows that match in both tables

SELECT
  ta.TransNo,
  ta.Amount,
  t.MerchantName
FROM TerminalActivities ta
INNER JOIN Terminals t ON ta.TerminalId = t.TerminalId;

Read it as: "for every row in TerminalActivities, find the matching row in Terminals where the TerminalId is equal, and pull columns from both." ta and t are aliases — short names so you don't have to spell out the full table name on every column.

Official documentation Microsoft's FROM clause plus JOIN reference defines INNER precisely: "Specifies all matching pairs of rows are returned. Discards unmatched rows from both tables." That "discards" is the whole reason a row with no match on either side simply never appears — it's documented behavior, not an incidental side effect.

LEFT JOIN: keep rows even without a match

SELECT
  t.MerchantName,
  ta.TransNo
FROM Terminals t
LEFT JOIN TerminalActivities ta ON ta.TerminalId = t.TerminalId
WHERE t.TerminalId = 3;

Terminal 3 ("Old Kiosk") has no activity rows. An INNER JOIN would have dropped it from the results entirely; LEFT JOIN keeps it and fills the missing activity columns with NULL. Use LEFT JOIN whenever "no matching rows" is itself a meaningful answer, not an error.

Official documentation The same reference states LEFT [OUTER]'s behavior in the same precise terms: "Specifies that all rows from the left table not meeting the join condition are included in the result set, and output columns from the other table are set to NULL in addition to all rows returned by the inner join." Every row an INNER JOIN would have kept is still there — LEFT JOIN only adds back the ones that INNER would have discarded.
A real incident: data existed, but an INNER JOIN two layers deep was silently dropping it A BackOffice list page showed "No result found" for every status filter, even though the underlying table clearly had matching rows. The trail went two layers deep: the stored procedure itself already filtered by country (correctly), and then a second, page-level LINQ query re-filtered the results with its own Join against a GetUsers() call — which turned out to run INNER JOIN Departments ON Departments.Id = Users.DepartmentId internally. Any user with a NULL or orphaned DepartmentId silently disappeared from that "all users" list — and every record they had ever created vanished from the page along with them, regardless of what status filter was applied. Nothing in the page's own filters was wrong; an unrelated INNER JOIN three calls away was the actual cause.

The lesson generalises beyond this one page: when a query or a page shows fewer rows than the data supports, don't stop at the first WHERE clause you find — a chain of joins across a service layer can each independently be "correct" in isolation and still silently exclude real rows in combination. An INNER JOIN anywhere in that chain is a candidate for accidental data loss, not just the one in the query you're currently looking at.

Filtering and ordering

SELECT TransNo, Amount
FROM TerminalActivities
WHERE Amount > 10
ORDER BY Amount DESC;

SELECT ta.TransNo, ta.Amount, t.MerchantName
FROM TerminalActivities ta

Best practice

  • Always alias your tables in a join (ta, t above) and qualify every column with its alias. Once a query joins three or four tables, an unqualified column name becomes genuinely ambiguous to a reader (and sometimes to the database itself).
  • Default to INNER JOIN and only reach for LEFT JOIN when you've deliberately decided "no match" is a valid, meaningful result you want to keep. An accidental LEFT JOIN can quietly let bad/incomplete data through a report that should have excluded it.
  • When a query returns fewer rows than expected, check every INNER JOIN in the chain, not just the outermost query. As the real incident above shows, a service-layer join two calls removed can silently be the actual cause.

Better ways

A query that joins many tables and applies several filters can get hard to read as one long statement. Splitting it with a Common Table Expression (WITH RecentActivity AS (...) SELECT ... FROM RecentActivity ...) names each intermediate step, which is often far more debuggable than one deeply nested query — worth reaching for once a query stops fitting comfortably on one screen.

Check your understanding

You need a report that lists every terminal, including ones with zero transactions ever. Which join do you use?

  • INNER JOIN, filtered by transaction count.
  • LEFT JOIN from Terminals to TerminalActivities.
  • A plain SELECT * FROM TerminalActivities with no join.

In the real incident described above, the page's own SQL and its own WHERE filters were correct. What actually caused users with a NULL/orphaned DepartmentId to silently disappear from the list?

  • The stored procedure's own country filter was wrong.
  • A separate, page-level GetUsers() call three layers away ran its own INNER JOIN against Departments, which discarded any user without a matching department — completely unrelated to the page's own visible filters.
  • The status filter dropdown on the page was broken.
