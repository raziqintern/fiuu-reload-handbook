Finding Every Affected Function Before You Change Anything

Before touching a shared method, table, or control's behavior: who else calls it? In most codebases that's a quick "find usages" in the IDE. In this one, the architecture itself makes that question harder than it looks — and getting it wrong is how a one-line fix breaks a page nobody was testing.

Why "find usages" alone isn't enough here

This codebase has a three-tier shared-library situation, verified in the Architecture Map track Shared code lives in three different places that overlap incompletely: reload/web/DEV/NET/Components/* (source, inside the reload repo), reload/class-library (a separate submodule — plus prebuilt .dll files committed at its own root), and reload/web/Libraries/NET/* (an older, per-version vendored DLL drop, still referenced by some apps in parallel). An IDE's "find usages" only sees source it can index — a consumer that references a prebuilt .dll from tier 3 instead of the tier-2 source won't show up in a source-level search at all. "App X depends on module Y" needs a specific ProjectReference/HintPath citation, not a guess by module name.

Technique 1 — grep the exact symbol, then grep its neighbors

Start with the literal name (a method, a class, a stored procedure, a table), but don't stop at the first hit. Real example: fixing the CSV-escaping anti-pattern (see Fiuu Code Conventions → CSV Export Escaping) meant finding every caller of the existing ToCSVDisplayString helper before deciding whether it was safe to change its behavior. Grepping the exact name across the whole repo — not just the one file the bug report pointed at — surfaced four separate BackOffice report pages already calling it, each one a page that would be affected by any change to what the helper does, not just the page the original ticket was about.

Grep wider than the symbol name itself For a shared helper, also grep for the class/namespace it lives in — a caller might use an alias, a `using`/`Imports` that makes the call look different at the call site than the definition does. For a database object, grep both the raw table/column name and the fully-qualified [Schema].[Table] form used in cross-database queries — this codebase's shared reference data (CEPP) gets referenced that way from other databases constantly.

Technique 2 — for a database object, check the schema vault's own known gaps first

Before concluding "nothing else touches this table," check architecture/reload_db/vault-drift-notes.md — the team's own schema vault was found to be missing two entire live databases (EINVOICE, SAP) and six TRANSACTION provider schemas entirely. A tool or doc that's silent about a table doesn't mean nothing references it; it can mean the tool never saw it. For anything touching those specific areas, go straight to the live MAINT/<Module>/ scripts instead of trusting the vault's silence.

Technique 3 — indirect call sites: config-driven dispatch and postback wiring

A direct grep misses anything reached through a layer of indirection. Two patterns specific to this codebase are worth checking explicitly:

  • The EventAppName switch pattern (see Configuration & Secrets) — a large switch statement decides which AWS Secrets Manager labels apply based on which app is running. Changing behavior gated by one label can silently affect every app whose EventAppName resolves to that branch, not just the one you're testing against.
  • Shared controls inside an UpdatePanel — per the WebForms Postback & ViewState Pitfalls lesson, a control's visible behavior can differ depending on whether it sits inside or outside an async-postback boundary on a given page. The same shared control embedded on two different pages can behave differently under this codebase's postback wiring even though the control's own code never changed — check the postback structure of every page a shared control appears on, not just its own definition.

Technique 4 — before resetting or aligning a shared reference, check ancestry, not dates

This applies to more than code: a shared submodule commit, a deployment tag, any pointer more than one team's work flows through. See Git Archaeology for the full worked example — "looks newer" and "is actually a descendant of what's currently live" are different claims, and confusing them is how a well-intentioned reset quietly reverts someone else's already-shipped fix.

Best practice

  • For a shared method: grep the exact name across the whole repo (not just the app you're changing), then check each caller's own project file for how it actually references the module (source vs. prebuilt DLL) before assuming a source-level search caught everyone.
  • For a database object: check the handbook's known vault gaps before trusting a schema tool's silence, and grep both the bare name and the fully-qualified cross-database form.
  • For a shared UI control or config-gated behavior: check every page/app it appears on individually — this codebase has enough small-per-page differences (postback wiring, which EventAppName branch applies) that "it's the same control everywhere" is not a safe assumption.
  • Write down what you checked and what you found nothing in, not just what you found — "grepped X, no other callers" is useful information for the next person (including future you), even when the answer is "nothing else uses this."

Check your understanding

An IDE's "find usages" on a class-library method shows zero callers. What should you check before concluding it's safe to change its behavior?

  • Trust it — an IDE search covers every possible caller in any .NET codebase.
  • Whether any consuming app references this module via a prebuilt DLL rather than the source project — that consumer wouldn't appear in a source-level search at all.
  • Whether the method has an XML documentation comment, since undocumented methods don't show up in searches.

You're about to change a table that the schema vault shows no other references to. What's the right next step, specifically in this codebase?

  • Proceed — if the vault shows nothing, nothing else references it.
  • Check vault-drift-notes.md for known gaps, and if the table falls in or near an already-flagged gap, verify directly against the live MAINT/ scripts instead of trusting the vault's silence.
  • Regenerate the entire schema vault from scratch before making any change.
