Debugging Reload

Worked Example: Tracing a Bug

A real incident from reload's history (issue #2592), walked through the way you'd actually work it — not the tidy after-the-fact summary. Source: gitlab-analysis/reload-tribal-knowledge.md §2.6.

The symptom, as it was reported

"TNG reload transactions are getting slow" Transaction time crept up from normal to as long as two hours to complete. The pattern that makes this bug class recognisable: it gets slowly worse over hours, and a service restart fixes it — for a while, before it creeps back up again.

Step 1 — resist the obvious wrong hypotheses

"Getting slow over time, restart fixes it" points strongly at a resource leak, not a logic bug — the code's output was correct the whole time, only its speed degraded. A few hypotheses that would waste time here:

  • "The database is slow" — would show up as slow queries across many unrelated operations, not specifically TNG reload transactions creeping up in isolation.
  • "There's a bug in the reload logic" — a logic bug doesn't explain why a restart temporarily fixes it. Logic doesn't degrade with uptime.
  • "Traffic increased" — would show a step change correlated with a known traffic event, not a slow, restart-resettable creep.

Step 2 — what "restart fixes it" actually tells you

If restarting the process resets the problem, whatever is degrading must live in process memory or OS-level handles — not the database, not the network, not a config value (those would survive a restart unchanged). This narrows the search dramatically before a single line of code is read.

Step 3 — find what's opened per-transaction and never released

The actual root cause: every single reload transaction opened a .pfx certificate file from disk and RSA-decrypted a session key from scratch, twice per reload — and never released the handle afterward.

Why this specifically causes a slow multi-hour creep, not an instant crash Windows serializes access to crypto key material. As unreleased handles piled up over hours, each new lookup got slower, competing for the same serialized resource. And because this all happened inside a per-account lock, the slowdown queued behind itself — one slow transaction blocks the next one for the same account, compounding the delay instead of just adding to it.

Step 4 — the fix, and the generalizable lesson

The fix itself is almost anticlimactic once the cause is found: release the certificate/key handle after each use instead of leaking it. The lesson that outlives this specific ticket:

The pattern to recognise next time "Things get slow over time, and a restart fixes it" is the signature of a per-request resource leak (a file handle, a crypto key, a connection, a lock) that never gets released — especially dangerous when it sits inside a per-account or per-resource lock, because the lock turns a small per-request slowdown into a compounding queue. When you see this shape, go looking for something opened inside a hot path with no matching Dispose()/release — not for a logic bug in the transaction itself.

Best practice

When a symptom description arrives ("it's slow," "the amount is wrong," "duplicate records appeared"), resist jumping straight to the code — spend the first few minutes narrowing which shape of bug it is (resource leak, unit/format mismatch, race condition, unbounded query) before opening a single file. The shape tells you where to look; guessing at code first usually means reading the wrong file first.

Try applying it: which pattern does each symptom match?

A merchant's topup confirmation email shows an amount 100x larger than what was actually charged. Which pitfall from this track does this match?

  • The per-request resource leak pattern (like the TNG certificate issue above).
  • A partner unit/format mismatch — the amount arrived in cents and wasn't converted before display.
  • The double-exception-logging anti-pattern.

Two independent code paths (a webhook callback and a browser redirect) both try to mark the same payment as complete, and duplicate transaction records appear. Which category of fix does the tribal-knowledge doc point to?

  • Release the unreleased resource that's causing a slowdown.
  • Make exactly one of the two signals authoritative, or add a dedupe/idempotency key — don't let whichever arrives first just win.
  • Add a retry loop so both paths keep trying until one succeeds.
