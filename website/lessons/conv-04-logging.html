Fiuu C# Conventions

Logging

Since the previous lesson showed the log is often the only place an exception's detail survives, knowing how logging actually works here is directly a debugging skill. Full source: conventions/logging.md.

No single logging mechanism

Two shared framework primitives exist underneath everything (both compiled dependencies, no source in this repo): Fiuu.MasterFramework.Utilities.Logger (rolling file logger + Windows Event Log) and Fiuu.Logging.LogManager (a structured logger). Instead of one shared façade over these, at least three modules each define their own static LogHelper wrapping them differently — different constructors, different method surfaces (Write/Error/Trace/Warn in one, just Write in another).

You cannot copy logging code between modules Because each module's LogHelper has a different method surface, code that logs correctly in TNG will not compile (or will compile but call the wrong thing) if pasted into AWSCore. Always check which LogHelper the file you're editing actually imports before writing a log call.

The one genuine house convention: bracketed request/response logging

LogHelper.Write(string.Format("[{0}] >>> [Key: {1}] {2}", config.AmdocsPaymentUrl, billPayment.BankClientRefId, request.ToJson()));
string response = HttpHelper.HttpPost(config.AmdocsPaymentUrl, request.ToJson(), MIMEType.TEXT_JSON, config.HttpRequestTimeout);
LogHelper.Write(string.Format("[{0}] <<< [Key: {1}] {2}", config.AmdocsPaymentUrl, billPayment.BankClientRefId, response));

Outbound HTTP/API calls are logged with a >>> (outgoing) / <<< (incoming) bracket convention, tagged with a correlation key (usually the business reference id). This recurs across unrelated modules written by different people — it's the closest thing to a real de facto logging standard in this codebase, and it's the pattern most worth following if you're adding a new outbound integration.

This logs full payloads, unredacted Full request/response bodies get logged as JSON, including for payment/account-verification calls — and nothing in the sampled code redacts sensitive fields before logging. Be aware of this both when reading logs (they may contain account numbers/amounts) and when adding new logging (don't assume redaction happens for you; it doesn't, by default, anywhere in this codebase).

Practical debugging habit: search for the correlation key

Given the [Key: ...] convention above, the fastest way to trace one specific transaction through the logs is to search for its reference id as the correlation key — not to read logs chronologically. This is the direct log-side analogue of the JS/browser habit from earlier: search for the specific thing that's wrong, don't scroll from the top.

Best practice — for working inside this specific codebase

  • When adding a new outbound integration, follow the real >>>/<<< bracket-and-correlation-key convention — it's the closest thing to a genuine house standard, and it's what makes a future incident traceable by search.
  • Check which LogHelper the file you're editing already imports before writing a log call — don't assume a method signature from a different module's helper will compile or behave the same way.

Better ways

If you're ever in a position to influence it, consolidating the three module-specific LogHelpers onto one shared façade (already flagged as tech debt in this codebase's own tracked backlog — see gitlab-analysis/reload-tribal-knowledge.md §4) would remove an entire class of "this code compiles in one module but not another" friction. Not a change to make casually inside an unrelated bug fix, though — it's exactly the kind of cross-cutting change that deserves its own dedicated, reviewed effort.
