Software Design & Best Practices

Design Patterns reload Actually Uses

A "design pattern" is just a named, reusable solution to a recurring design problem. You've already read the code for two real ones on this site — this lesson gives them their formal names, so you can recognise them elsewhere and talk about them precisely in a code review.

Service Locator

The problem it solves: a class needs a dependency, but you don't want to hand-wire every single dependency through a constructor, especially for dependencies that are expensive to create and might never actually be needed.

private IAccountService _accountCompo;
private IAccountService AccountCompo
{
    get { return _accountCompo ?? (_accountCompo = EngineContext.Current.Resolve()); }
}

reload/class-library/Reloads/TNG/Services/TerminalService.cs:35-39

Instead of receiving IAccountService as a constructor parameter (the more modern Dependency Injection approach you'll see recommended almost everywhere today), TerminalService asks a central registry (EngineContext.Current) for it, lazily, the first time it's actually used. This is the Service Locator pattern — a real, working, if somewhat dated, alternative to constructor injection. You saw this first in Fiuu C# Conventions → Layering; the callout there is worth re-reading now that you know the pattern's name: don't "fix" it to constructor injection unless that's the actual scope of your change.

Template Method

The problem it solves: several related operations share the same overall sequence of steps, but a couple of the steps need to vary per case.

protected override ContractResponse RetrieveExistingGiftCardResend(ContractRequest request, int actionType) { ... }
protected override InCommTransaction FormatContractToModel(ContractRequest appReq, string processingCode, string messageTypeIdentifier) { ... }
protected override int ValidateParameters(ContractRequest appReq) { ... }

reload/class-library/Secure/Incomm/Services/FastPinSaleService.cs:70-90

An abstract base class (InCommServiceBase) defines the overall algorithm's shape once, with specific steps (ValidateParameters, FormatContractToModel, ...) left as overridable hooks. Concrete classes like FastPinSaleService override just those steps — this is the Template Method pattern. It's notably more structured than the flat, no-inheritance style most other reload modules (TNG, Game) use for the same kind of variability — a real, deliberate design choice specific to InComm's ISO 8583 protocol handling, not a codebase-wide standard.

Repository / Provider pattern

The problem it solves: keep data-access code (how you talk to a database) separate from business logic (what you do with the data), so each can change independently.

Every *Provider class in reload (Fiuu C# Conventions → Data Access) is this pattern by another name — industry-standard terminology usually calls it a Repository, though reload's own naming convention calls it a Provider. Same idea: one class per aggregate, whose only job is translating between the domain model and the database, with a stored-procedure call underneath.

Why naming the pattern is useful, practically "This should use the Repository pattern" is a much faster, more precise code-review comment than re-explaining "you should separate data access from business logic" from scratch every time. Learning the vocabulary is a communication tool, not just trivia.
