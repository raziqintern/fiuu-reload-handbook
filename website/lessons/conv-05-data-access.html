Fiuu C# Conventions

Data Access

Three distinct ways of calling the database coexist in class-library — but one rule is universal across all of them. Full source: conventions/data-access.md.

The one universal rule: stored-procedure-only

No exceptions found, across every module sampled No inline dynamic SQL, no string-built SELECT/UPDATE statements, no LINQ-to-SQL or Entity Framework entity mapping, anywhere. Every single read or write goes through a named stored procedure. This is worth internalizing before you go looking for "the query" behind a bug — it's in reload_db's StoredProcedure/ folder, never inline in the C#.

Pattern 1 (most common): SqlAccessor + ParameterCollection

public bool Insert(TerminalActivity activity)
{
    var param = new ParameterCollection();
    param.Add("@TerminalId", DbType.AnsiStringFixedLength, 8, activity.TerminalId);
    ...
    SqlAccessor.ExecuteProcedure(ReturnType.NonQuery, Fiuu.Provider.Database.TNG.Alias,
                                 Fiuu.Provider.Database.TNG.StoredProcedures.TerminalActivities_Ins, param);
    return true;
}

A custom framework wrapper around ADO.NET: build a ParameterCollection, call SqlAccessor.ExecuteProcedure(...), get back a SqlResult. Mapping a database row back into a C# model is always done by hand, field by field, via a shared Conversion.DBNullTo* helper family — never a generic/reflection-based mapper:

private static Account GetAccountModel(DataRow dr)
{
    return new Account
    {
        Id = Conversion.DBNullToInt32(dr["Id"]),
        Name = Conversion.DBNullToString(dr["Name"]),
        Status = (Status)Conversion.DBNullToInt32(dr["MStatusId"]),
        ...
    };
}

Notice MStatusId (the M-prefix column from Naming) is cast to a friendly Status enum right here — this is exactly where that mapping happens.

Pattern 2 and 3: raw Dapper, two different shapes

The Fiuu.Database project skips SqlAccessor entirely and uses Dapper directly against a SqlConnection opened per call — either through a generic BaseProvider<T> (Pattern 2), or, in the Notification module, a singleton with one hand-named method per stored procedure (Pattern 3). Pattern 3's Dapper usage (connection.Query<Messages>(...) directly against the domain model) is actually the lightest-weight and closest to how a modern Dapper repository is normally written — ironically the oldest-feeling module (Notification) has the most modern-looking data access code.

No transactions spanning multiple Provider calls

Atomicity is the stored procedure's job, not C#'s There is no example anywhere in class-library of composing multiple writes into one ADO.NET transaction across Provider calls. If an operation needs "insert this, then update that" to happen atomically, that atomicity is expected to live inside a single stored procedure doing everything server-side — not orchestrated by a C# unit-of-work. If you're tempted to add a TransactionScope around two Provider calls to fix a consistency bug, that would be a new pattern for this codebase, not an existing one — think carefully, and check whether the real fix belongs in the stored procedure instead.

Best practice — for working inside this specific codebase

  • Never write inline dynamic SQL or a string-built query, even for a "quick" one-off — it's the one universal, zero-exception rule across every module and every data-access pattern sampled here.
  • When adding a new Provider, pick whichever of the three coexisting patterns (SqlAccessor, BaseProvider<T>, or a Dapper singleton) the sibling Provider in the same module/database already uses — there's no single "correct" one to introduce fresh.

Better ways

If you're the one adding a brand-new module with no existing sibling Provider to match, Pattern 3's plain Dapper usage (typed Query<T> directly against the domain model) is the lightest-weight and closest to how a modern Dapper-based data-access layer is normally written — arguably the best of the three to default to when nothing existing constrains the choice.
