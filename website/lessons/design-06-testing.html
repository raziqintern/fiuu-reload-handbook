Testing Fundamentals

A unit test is just code that checks other code's behavior automatically, so a human doesn't have to manually re-verify it every time something nearby changes.

The shape of a test: Arrange, Act, Assert

Almost every unit test follows the same three-part structure: set up the inputs (Arrange), call the code you're testing (Act), and check the result is what you expected (Assert). You don't need a real testing framework to see this in action — here it is hand-rolled, testing the exact same validation function from C# Fundamentals → Methods & Parameters:

static string ValidateReload(double amount, string method)
{
    if (amount <= 0) return "Amount must be positive";
    if (amount > 500) return "Exceeds max reload limit";
    if (string.IsNullOrEmpty(method)) return "Payment method required";
    return "OK";
}

static void AssertEqual(string actual, string expected, string testName)
{
    bool pass = actual == expected;
    Console.WriteLine((pass ? "PASS" : "FAIL") + ": " + testName);
}

static void Main()
{
    // Arrange + Act + Assert, three times over
    AssertEqual(ValidateReload(50, "tng"), "OK", "valid reload should pass");
    AssertEqual(ValidateReload(-5, "tng"), "Amount must be positive", "negative amount should fail");
    AssertEqual(ValidateReload(50, null), "Payment method required", "missing method should fail");
}
PASS: valid reload should pass
PASS: negative amount should fail
PASS: missing method should fail
Function ValidateReload(amount As Double, method As String) As String
    If amount <= 0 Then Return "Amount must be positive"
    If amount > 500 Then Return "Exceeds max reload limit"
    If String.IsNullOrEmpty(method) Then Return "Payment method required"
    Return "OK"
End Function

Sub AssertEqual(actual As String, expected As String, testName As String)
    Dim pass As Boolean = (actual = expected)
    Console.WriteLine((If(pass, "PASS", "FAIL")) & ": " & testName)
End Sub

Sub Main()
    ' Arrange + Act + Assert, three times over
    AssertEqual(ValidateReload(50, "tng"), "OK", "valid reload should pass")
    AssertEqual(ValidateReload(-5, "tng"), "Amount must be positive", "negative amount should fail")
    AssertEqual(ValidateReload(50, Nothing), "Payment method required", "missing method should fail")
End Sub

PASS: negative amount should fail
PASS: missing method should fail

You've now seen this exact validation logic implemented across three languages on this site — JavaScript, C#, VB.NET — and this is the first time you've seen it verified automatically instead of by eyeballing the output.

Official documentation Microsoft's Best practices for writing unit tests defines the pattern in the same three parts used above: "Arrange your objects, create, and configure them as necessary. Act on an object. Assert that something is as expected." The same reference also names a real, specific naming convention worth matching: "The name of your test should consist of three parts: Name of the method being tested, Scenario under which the method is being tested, Expected behavior when the scenario is invoked" — for example Add_SingleNumber_ReturnsSameNumber, not Test_Single. The plain-string test names above ("negative amount should fail") capture the same idea informally; a real framework's method-name convention makes it precise and searchable.

Why untested code is a real, tracked risk — not a theoretical concern

A real example from reload itself CardNumberValidator.IsValid encodes a blacklist bitmap lookup scheme with several magic numbers and no visible unit tests anywhere in the sampled codebase (Debugging Reload → Known Patterns & Pitfalls). The documented guidance is explicit: treat changes to this class as high-risk specifically because there's no test suite to catch a regression — you're relying entirely on manual review and production behavior to notice a mistake.

What tests actually buy you

  • Confidence to change code. A good test suite tells you within seconds whether a refactor broke something, instead of waiting for a bug report.
  • Executable documentation. A test named "negative amount should fail" tells a future reader what the function is supposed to do, in a way that can't silently go stale the way a comment can.
  • A place to reproduce a bug before fixing it. Writing a failing test that reproduces a reported bug, then fixing the code until it passes, proves the fix actually addresses the reported behavior — not just "seems fine now."
What if not: multiple Act steps in one test? Microsoft's own reference names a concrete cost of this: "Multiple Act tasks need to be individually asserted, and you can't guarantee that all Assert tasks execute. In most unit testing frameworks, after an Assert task fails in a unit test, all subsequent tests are automatically considered as failing." If one test calls ValidateReload three times with three different inputs and asserts after each, a failure on the first call can hide whether the second and third would have passed at all — the recommended fix is a separate test (or a parameterized one) per scenario, so a single failure tells you exactly which case broke.

Best practice

  • Use a real test framework in real code (xUnit/NUnit/MSTest for C#/VB.NET) rather than hand-rolled asserts like the example above. They give you test discovery, isolated failures, and readable reports for free. The AssertEqual helper here exists purely to show the underlying idea without any tooling in the way.
  • Name each test with the method, the scenario, and the expected behavior. ValidateReload_NegativeAmount_ReturnsError tells a future reader what broke without opening the test body at all.
  • Give each test exactly one Act step. A failure should point unambiguously at one specific scenario, not leave you guessing which of several calls actually failed.

Check your understanding

Why does the lack of unit tests on CardNumberValidator specifically raise the risk of changing it, compared to a similarly complex but well-tested class?

  • Without tests, the class runs slower in production.
  • A regression introduced by a change has no automated way to be caught before it reaches production or manual review misses it.
  • The class becomes impossible to mark as public.

A single test calls ValidateReload three times with three different inputs, asserting after each call. The first assertion fails. What does Microsoft's own testing guidance say happens to the other two assertions?

  • They still run and report independently, so you can see all three results.
  • In most frameworks, the test stops at the first failed assertion — you can't tell from the result whether the other two would have passed or failed too.
  • The test runner crashes entirely and no results are reported at all.
