Exceptions & Try/Catch

When something goes wrong mid-transaction — a timeout, bad input, a gateway rejection — C# doesn't return a special "error" value. It throws, unwinding the call stack until something catches it.

throw, try, catch

static double Divide(double a, double b)
{
    if (b == 0)
        throw new DivideByZeroException("Cannot divide by zero");
    return a / b;
}

static void Main()
{
    try
    {
        double result = Divide(10, 0);
        Console.WriteLine(result);
    }
    catch (DivideByZeroException ex)
    {
        Console.WriteLine("Error: " + ex.Message);
    }
    Console.WriteLine("Program continues");
}
Error: Cannot divide by zero
Program continues

Note that Console.WriteLine(result) never runs — once Divide throws, execution jumps straight to the matching catch, skipping everything else left in the try block. Execution after the whole try/catch continues normally.

finally always runs

try
{
    Console.WriteLine("Attempting reload...");
    throw new Exception("Gateway timeout");
}
catch (Exception ex)
{
    Console.WriteLine("Caught: " + ex.Message);
}
finally
{
    Console.WriteLine("Cleanup: closing connection");
}
Attempting reload...
Caught: Gateway timeout
Cleanup: closing connection

A finally block runs whether or not an exception was thrown, and whether or not it was caught — it's the right place for cleanup (closing a connection, releasing a lock) that must happen either way.

Official documentation Microsoft's Exception-handling statements reference lists every way control can reach a finally block, not just the exception case: "Control might leave the try block as a result of normal execution, execution of a jump statement (that is, return, break, continue, or goto), or propagation of an exception out of the try block." When a catch does handle the exception, the same reference confirms the order: "the finally block runs after the catch block finishes."
Official documentation — why catch order matters when you have several The same reference is explicit about how multiple catch clauses are actually evaluated: "When an exception occurs, the runtime checks catch clauses in the specified order, from top to bottom. At most, only one catch block runs for any thrown exception." And: "A catch clause without any specified exception type matches any exception and, if present, must be the last catch clause." Put a broad catch (Exception ex) before a specific one and the specific clause becomes unreachable — the broad one always matches first.
Catching Exception is a code smell, not a best practice catch (Exception ex) catches literally everything, including bugs you'd rather see crash loudly (like a null reference from your own typo). Catch the most specific exception type you're actually expecting to handle. Reload's own code has plenty of blanket catch (Exception) blocks that just log and swallow — that's a real, documented pattern in this codebase, not a theoretical anti-pattern. Best practice

  • Catch the most specific exception type you actually know how to handle. catch (DivideByZeroException ex) above, not a blanket catch (Exception ex) that would also silently swallow a bug you'd rather see fail loudly.
  • Order multiple catch clauses from most specific to least specific, always. A broad clause placed before a specific one makes the specific one unreachable — the runtime checks them top to bottom and stops at the first match.
  • Put cleanup that must always happen (closing a connection, releasing a resource) in finally. Or better, in a using block, which you'll meet properly in C#/.NET Deep Dives → Garbage Collection & Object Lifetime.

Better ways

Reload's own real code frequently catches broadly and logs-then-swallows (Fiuu C# Conventions → Error Handling) — a deliberate, if debated, house pattern for this specific codebase. That's a real, working choice for a production system where an unhandled exception in one transaction shouldn't take down the whole process — but it's not the default you should reach for in new, general-purpose code without that same reasoning behind it.

Check your understanding

In the first example, why does "10" (or any result value) never get printed?

  • Console.WriteLine can't print doubles without a format string.
  • Divide throws before it returns anything, so execution jumps straight to the catch block and skips that line entirely.
  • result is declared with the wrong type.

A try block is followed by catch (Exception ex) first, then catch (DivideByZeroException ex) second. A DivideByZeroException is thrown. Which catch block runs?

  • The first one — catch (Exception ex) — since it's checked first and matches everything, including this specific exception type.
  • The second one — catch (DivideByZeroException ex) — since it's the more specific match.
  • Both run, one after the other.
