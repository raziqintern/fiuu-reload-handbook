JavaScript Basics

Functions & Scope

A function packages up a piece of logic so you can name it and reuse it — the same reason C# has methods.

Two ways to write one

// traditional function declaration
function calculateFee(amount) {
  return amount * 0.01;
}

// arrow function — shorter, very common in modern JS
const calculateFeeArrow = (amount) => amount * 0.01;

console.log(calculateFee(100));
console.log(calculateFeeArrow(100));

Both do the same thing here. Arrow functions are everywhere in modern JS, especially as short one-off callbacks — you'll see the arrow form far more often than the traditional one in real code.

Official documentation — the real difference isn't just shorter syntax MDN's Arrow function expressions reference names the one difference that actually matters, not a cosmetic one: "Arrow functions don't have their own bindings to this, arguments, or super, and should not be used as methods." More precisely: "Arrow functions establish this based on the scope the arrow function is defined within, and the this value does not change based on how the function is invoked." A traditional function gets its own, separate this every time it's called — an arrow function never does; it always reuses whatever this already meant in the surrounding code.

What that difference actually looks like, run to prove it rather than just asserted — the same object method extracts a callback and invokes it as a bare function call, exactly what setTimeout does internally when its delay fires:

const terminal = {
  status: "online",
  reportLaterTraditional() {
    // a traditional function here gets its OWN this — and called
    // as a bare function (not terminal.something()), that this is not terminal
    return function () {
      console.log("Traditional function this.status:", this.status);
    };
  },
  reportLaterArrow() {
    // an arrow function has no this of its own — it reuses
    // reportLaterArrow's this, which IS terminal, no matter how it's later called
    return () => {
      console.log("Arrow function this.status:", this.status);
    };
  },
};

// This is exactly what setTimeout does internally when its delay
// fires: it calls the callback as a bare function, with no object
// in front of the dot — callback(), not terminal.callback().
const traditionalCallback = terminal.reportLaterTraditional();
const arrowCallback = terminal.reportLaterArrow();
traditionalCallback();
arrowCallback();
The wrong scenario: using an arrow function as an object method itself The one place to specifically avoid an arrow function is the method itself, not just its callbacks — reportLater: () => { console.log(this.status) } written as the object's own method would capture whatever this existed outside the object literal (often not the object at all), not terminal. Arrow functions are for callbacks defined inside a real method, where reusing that method's own this is exactly what you want — not for the method declaration itself.

Scope: where a variable is visible

function processReload() {
  let status = "processing"; // only exists inside this function
  console.log("Inside:", status);
}

processReload();
console.log(typeof status); // "undefined" — status doesn't exist out here
Why scope matters for debugging "Variable is undefined" is one of the most common JS errors you'll see in a browser console. Nine times out of ten it's a scope problem: the variable was declared inside a function (or an if block, or a loop) and something outside that block is trying to read it.

Try it yourself

A function that mirrors a real validation step — notice it returns early instead of nesting deeper ifs.

function validateReload(amount, method) {
  if (amount <= 0) return "Amount must be positive";
  if (amount > 500) return "Exceeds max reload limit";
  if (!method) return "Payment method required";
  return "OK";
}

console.log(validateReload(50, "tng"));
console.log(validateReload(-5, "tng"));
console.log(validateReload(50, null));

Best practice

  • Give a function one job. validateReload only validates — it doesn't also save the reload or send a confirmation. This is the same Single Responsibility idea you'll meet formally in Software Design → SOLID Principles, just at function scale instead of class scale.
  • Name a function by what it does, as a verb phrase. validateReload, not reloadStuff — the name should make a call site readable without needing to jump to the definition.
  • Use an arrow function for a callback inside a method; never as the method itself. A callback should usually reuse its surrounding this — that's what arrow functions are for. A method declaration needs its own this, bound to the object it's called on — that's what a traditional function gives you.

Better ways

Returning a human-readable error string works for a quick example, but doesn't scale to a real app that needs to react differently to different failures (show a specific field error, retry automatically, log differently). A common upgrade: return a small object or code ({ ok: false, reason: "AMOUNT_TOO_LOW" }) that calling code can branch on programmatically, and translate to user-facing text only at the very end, near the UI.

Check your understanding

A variable declared with let inside a function — where can it be read from?

  • Anywhere in the file, after the line it was declared on.
  • Only inside that function (and any nested block within it).
  • Inside any other function that runs afterward.

An object method uses setTimeout(function () { console.log(this.status); }, 10) inside it, with a traditional function as the callback. What does this.status log?

  • The object's own status property, since the callback is defined inside the object's method.
  • Not the object's status — a traditional function gets its own separate this when called, and setTimeout doesn't call it in a way that makes this point back to the object.
  • It throws an error, because this isn't defined inside a callback.

Why is an arrow function specifically discouraged as an object's own method (e.g. reportLater: () => { console.log(this.status) }), even though it's shorter to write?

  • Because an arrow function has no this of its own — it reuses whatever this meant in the surrounding code, which usually isn't the object the method is attached to.
  • Because arrow functions can't accept any parameters.
  • Because arrow functions can't return a value from inside an object.
