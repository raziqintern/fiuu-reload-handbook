Worked Example: Hiding a Field Isn't Gating It

Two related BackOffice bugs on the Dealer pages (issues #2168 and #2454) share one root cause: code that decides what a user sees and code that decides what gets validated or saved are two separate, easily-desynced things in this codebase.

Case 1: a validator that's only disabled sometimes

DealerCreate.aspx has a Payment Type radio group that should hide the Wallet Type field (and its required-field validator) when "Consignment" is selected. The same toggle logic existed three separate times:

  • An inline .change() handler (lines 16-31) — toggles CSS visibility, fires on every radio change.
  • onChangePaymentType() (lines 42-60) — an exact duplicate of the CSS logic above, called once on page load.
  • checkPaymentType() (lines 62-78) — the only one of the three that also touches ValidatorEnable, and it only runs at the moment Save is clicked.
The trap: three copies of "the same" logic, only one complete Selecting "Consignment", then changing the radio back to a placeholder and saving, could leave RFVWalletType's enabled state out of sync with what's actually visible — because the only function that ever corrects it runs once, right before Save, instead of continuously alongside the CSS toggle. If anything else ever submits the form (the Enter key, a future second button), the validator's state is wrong again, because nothing keeps it tied to the actual selection outside that one click handler.

The fix consolidates all three into one function that updates CSS visibility and ValidatorEnable together, called from both the radio's change handler and once on page load — so there is exactly one place that can ever get this wrong, not three that have to be kept manually in sync:

function syncWalletTypeRequirement(radionValue) {
    if (radionValue == "Consignment") {
        document.getElementById("trprepaidtransfer").style.display = "none";
        document.getElementById("trwallettype").style.display = "none";
        $(".offline-sales").hide();
        ValidatorEnable(document.getElementById("RFVWalletType"), false);
    } else if (radionValue == "Prepaid") {
        document.getElementById("trprepaidtransfer").style.display = "";
        document.getElementById("trwallettype").style.display = "";
        $(".offline-sales").show();
        ValidatorEnable(document.getElementById("RFVWalletType"), true);
    }
}

Case 2: a hidden tab doesn't stop the code behind it from running

Issue #2454 reported Finance-only users unable to save changes to the SAP tab on DealerEdit.aspx — a genuine save-blocker, not cosmetic. RestrictedPage.CheckTabAccess (lines 165-182) already does this correctly on the surface: it sets tab.Visible = False server-side (not just CSS) for tabs a Finance-only user shouldn't see. But visibility and validation turned out to be two separate, disconnected mechanisms:

Validation runs unconditionally, regardless of tab visibility btnSave_Click calls ValidateEditDealer() (lines 317-419) for every user, with no check of which tabs are actually visible to them. That method validates name, payment/wallet type, dates, operation hours, currency, and address — none of it SAP-related, all of it on tabs a Finance-only user's session had already hidden. The hidden tab stopped the user from seeing those fields; it did nothing to stop the server from demanding they be valid anyway.

Tracing further into SaveDealer() (line 1050) surfaced a second, previously-unreported instance of the exact same gap: an unconditional Platform Indicator checkbox check (lines 1128-1133) that also lives on the general Dealer tab, not SAP — the same category of bug, just not the one the issue reported. And SaveDealer() builds one monolithic object from every control on the page (lines 1285-1337) — general fields and SAP fields together — then persists it in a single call, meaning a Finance-only save overwrites the whole record, not just the SAP fields that user is actually allowed to touch.

What was confirmed vs. what stayed open Whether that wholesale overwrite is actually safe depends on whether ASP.NET correctly round-trips a hidden tab's control values through ViewState across a postback when the tab's Visible is False — a real ambiguity with TabPanel/AjaxControlToolkit that static reading of the code alone can't settle. That's the honest, disciplined way to report a finding like this: state exactly what the code confirms (the two unconditional validation/checkbox gaps) separately from what still needs live verification (whether the overwrite is harmless or a data-corruption risk) — rather than guessing at an answer either way.

The generalizable lesson

A visibility check and a logic guard are not the same line of code Hiding a field or tab — with CSS, or with a server-side Visible = False — only changes what the user sees. It does nothing on its own to whatever validation, save, or business logic runs afterward, unless that code explicitly checks the same condition used to hide the UI. Whenever a field or tab is gated by a role or permission, search for every validator, every save-path field read, and every downstream write that touches it — each one needs its own copy of that same guard, not just the markup.

Best practice

When a page conditionally hides fields based on role or state, treat "is this visible" and "is this validated/saved" as two separate questions that both need an answer — don't assume one implies the other. If you find a duplicated toggle function like Case 1's three copies, that's a signal worth investigating on its own: duplicated logic is exactly where one copy quietly ends up incomplete relative to the others.

Check your understanding

A tab is hidden server-side with tab.Visible = False for users without a certain permission. What does this worked example say you still need to check?

  • Nothing — server-side Visible = False is sufficient on its own to protect that tab's fields.
  • Whether every validator and save-path read of that tab's fields also checks the same permission — hiding it doesn't stop other code from processing it.
  • Whether the browser's JavaScript console shows any errors when the tab is hidden.

You find the same toggle logic duplicated across three event handlers on a page, and only one of them updates a validator's enabled state. What should you be suspicious of?

  • That the one correct copy might only run under a narrower set of conditions than the other two, leaving a gap on any path that skips it.
  • That the page will run slower because the same logic executes multiple times.
  • Nothing — as long as all three produce the same visual result, they're equivalent.
