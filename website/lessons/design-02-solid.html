Software Design & Best Practices

SOLID Principles

Five naming conventions for design smells you already have an instinct for. Knowing the names lets you talk about them precisely — and lets you recognise them in real code you've already seen on this site.

S — Single Responsibility

A class should have one reason to change. This is exactly why reload splits each module into Model/Provider/Service (Fiuu C# Conventions → Layering): a Provider changes only when data-access logic changes; a Service changes only when business rules change. Mixing both into one class means a change to either reason touches the same file.

Official documentation Microsoft's Architectural principles reference states the rule in the same terms: "It states that objects should have only one responsibility and that they should have only one reason to change... Following this principle helps to produce more loosely coupled and modular systems, since many kinds of new behavior can be implemented as new classes, rather than by adding additional responsibility to existing classes."

O — Open/Closed

Code should be open to extension, closed to modification — you should be able to add new behavior without editing existing, working code. The PaymentMethod hierarchy from OOP Pillars demonstrates this: adding a new payment method means writing a new subclass, not editing the loop that calls process().

L — Liskov Substitution

Any subclass should be usable anywhere its parent type is expected, without breaking things. If CardPayment.process() secretly required an extra step the caller didn't know about, substituting it for TngPayment would silently break — that's a Liskov violation. The polymorphism example only works cleanly because both subclasses honor the same contract.

I — Interface Segregation

Don't force a class to implement methods it doesn't need. A bloated IPaymentService with 15 methods, where most implementations only genuinely need 3, pressures every new implementer into writing empty/throwing stubs for the rest. Smaller, focused interfaces (reload's real ITerminalService has exactly the methods a terminal service needs, nothing more) are easier to implement correctly.

D — Dependency Inversion

Official documentation Microsoft's own reference states the direction of the inversion precisely: "The direction of dependency within the application should be in the direction of abstraction, not implementation details... Applying the dependency inversion principle allows A to call methods on an abstraction that B implements, making it possible for A to call B at run time, but for B to depend on an interface controlled by A at compile time (thus, inverting the typical compile-time dependency)." The word "inversion" refers to exactly that flip — without it, the natural compile-time dependency graph would run the same direction as the runtime call graph; the principle deliberately breaks that symmetry.
You've already seen this in real reload code High-level code should depend on abstractions, not concrete implementations. TerminalService depending on IAccountService (an interface) rather than a concrete AccountService class — resolved lazily via EngineContext.Current.Resolve<IAccountService>(), see Layering — is dependency inversion in action. The Service layer never needs to know which concrete class actually implements the interface.

What the inversion actually buys you, made concrete — the same TerminalService class, swapped between two different IAccountService implementations with zero changes to TerminalService itself:

public interface IAccountService
{
    double GetBalance(string accountId);
}

public class RealAccountService : IAccountService
{
    public double GetBalance(string accountId) => 100.0; // a real DB lookup, in production
}

public class FakeAccountService : IAccountService
{
    public double GetBalance(string accountId) => 999.0; // a stand-in, e.g. for a test
}

public class TerminalService
{
    private readonly IAccountService _accountService;
    public TerminalService(IAccountService accountService)
    {
        _accountService = accountService; // depends on the interface, never the concrete class
    }
    public void ReportBalance(string accountId)
    {
        Console.WriteLine("Balance: " + _accountService.GetBalance(accountId));
    }
}

class Program
{
    static void Main()
    {
        new TerminalService(new RealAccountService()).ReportBalance("A1");
        new TerminalService(new FakeAccountService()).ReportBalance("A1");
    }
}
Balance: 100
Balance: 999

TerminalService's own source code never mentions RealAccountService or FakeAccountService — it was written once, against the interface, and works correctly with either. That's the practical payoff: swapping implementations (a real service in production, a fake one in a test) needs zero changes to the class doing the depending.

Best practice

  • Split a class the moment it has two genuinely unrelated reasons to change. Validation rules and persistence logic are the classic pair — reload's own Model/Provider/Service split exists precisely to keep them apart.
  • Depend on an interface in a constructor parameter whenever the concrete implementation might reasonably change. A production/test swap, or a future second provider, becomes a one-line change instead of a rewrite.
  • Keep an interface small enough that every real implementer needs every method on it. A method that most implementations have to stub out or throw from is a sign the interface should be split.

Check your understanding

A single class handles both validating a reload request AND writing the transaction to the database. What SOLID principle does this most directly violate?

  • Single Responsibility — the class now has two unrelated reasons to change.
  • Liskov Substitution — the class can't be substituted for its parent.
  • Interface Segregation — the interface has too many methods.

TerminalService takes an IAccountService in its constructor rather than creating a new RealAccountService() internally. What does this specifically enable, per the Dependency Inversion example above?

  • It makes TerminalService run faster.
  • Swapping which concrete IAccountService implementation is used (real vs. fake, for example) without changing TerminalService's own code at all.
  • It changes GetBalance's return type based on which implementation is used.
