Comment Style

The last stop in this track: how much commenting actually exists, and where it earns its keep. Full source: conventions/comment-style.md.

XML doc comments are rare — about 1 in 10 files

Of 626 .cs files under class-library, only 62 contain an XML doc comment (///) anywhere at all. Public *Service/*Provider classes are overwhelmingly undocumented at the member level — method and parameter names (GetTerminalSummaryByTransNo(string transNo)) are expected to carry the meaning on their own, and mostly do. There's no IntelliSense-visible description of edge cases or failure modes for a consumer of the shared library.

What this means for you as a reader Don't go looking for doc comments to understand what a method does — you likely won't find them. Read the method name, its parameter names, and (per the Naming lesson) the layer suffix on its class. That's the primary documentation this codebase actually has.

Inline comments are sparse — but load-bearing when present

Most methods have zero inline comments. When one does appear, it's because the behavior is genuinely non-obvious and the author knew it:

long subNumber = Int64.Parse(cardNumber.Substring(cardNumber.Length - 10, 9)); //last digit is serve as parity bit
long fileIndex = (subNumber - 1) / 2000000;
int cardIndex = (int)(subNumber % 2000000);
cardIndex = cardIndex == 0 ? 1999999 : cardIndex - 1; // Fix the index due to 2000000 should be last position

reload/class-library/Reloads/TNG/Validators/CardNumberValidator.cs:53-56

The philosophy: comments explain business magic, not mechanics This codebase's comments explain domain magic numbers and business rules that genuinely can't be inferred from the code — not what the code is mechanically doing. The trade-off: a file dense with magic numbers like this one is still hard to follow even with the comments it has, because there's no overview comment explaining the file format or scheme as a whole. If you touch a file like this, consider whether a short summary comment at the top would have saved you the time you just spent understanding it — and add one if so.

A comment that reveals the codebase's own history

foundFile = true;
break; // TODO: might not be correct. Was : Exit For

reload/class-library/Database/Helpers/DBConnectionHelper.cs:61-63

"Was: Exit For" is a tell that this file was mechanically ported from VB.NET (Exit For is VB's loop-break keyword) rather than written fresh in C#. If you're editing Fiuu.Database code and something feels slightly foreign for idiomatic C#, this is likely why.

SQL headers: a consistent template, shallow content

-- =============================================
-- Author:		Chee Hong
-- Create date: 2024-05-06
-- Description:	Celcom Transactions
-- Used by:     Celcom Pinless
-- =============================================

reload_db/MAINT/TRANSACTION/StoredProcedure/Celcom.Transactions_Ins.sql:9-14

This is almost certainly a leftover from SSMS's built-in "Create Stored Procedure" template — kept as a convention rather than deliberately designed. The Description: line is frequently just the table name restated, not an actual description of behavior or pre/post-conditions.

Check your understanding

You're trying to understand what a public Service method does and there's no XML doc comment on it. What should you actually rely on, based on this codebase's real documentation philosophy?

  • Search the rest of the file for XML doc comments on similar methods.
  • The method's name, its parameter names, and its class's layer suffix (Service/Provider/Model) — that's what carries the meaning here.
  • Every method is expected to have an inline comment explaining its behavior.
