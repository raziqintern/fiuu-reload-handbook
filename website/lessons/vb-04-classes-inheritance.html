VB.NET Fundamentals

Classes, Inheritance & Interfaces

VB.NET's OOP keywords are more explicit than C#'s in exactly the places that matter for reading BackOffice code — MustOverride/Overrides instead of C#'s abstract/override, and Implements written twice: once on the class, once again on every member.

Property instead of get/set, New instead of a matching-name constructor

Public Class Terminal
    Public Property TerminalId As String
    Public Property MerchantName As String
    Public Property IsOnline As Boolean

    Public Sub New(terminalId As String, merchantName As String)
        Me.TerminalId = terminalId
        Me.MerchantName = merchantName
        Me.IsOnline = True
    End Sub
End Class

Module Program
    Sub Main()
        Dim t As New Terminal("TNG-0042", "7-Eleven KL")
        Console.WriteLine(t.TerminalId & " - " & t.MerchantName & " - " & t.IsOnline)
    End Sub
End Module
TNG-0042 - 7-Eleven KL - True

Compare this to the C# version in C# Fundamentals → Classes — same three properties, same constructor logic. Public Property X As T is VB's equivalent of C#'s public T X { get; set; }; the constructor is always named New instead of repeating the class name; Me is VB's this.

MustInherit & MustOverride — real, verified, and central to how BackOffice enforces access control

VB.NET's abstract-class keyword is MustInherit (not abstract), and an abstract member is MustOverride (not an abstract method with no body). This isn't a hypothetical translation — it's the actual base class every access-controlled BackOffice page inherits from:

Public MustInherit Class RestrictedPage
    ...
    Protected MustOverride ReadOnly Property ModuleName As ModuleNames
    Protected MustOverride ReadOnly Property PageAction As EnumPageAction
    ...
End Class

Every real page that needs access control inherits from it and is forced by the compiler to supply both properties — there's no way to inherit RestrictedPage and forget one, the way you could forget to check permissions manually in an ad hoc base class:

Namespace WebForms
    Public Class TerminalFirmwareVersionList
        Inherits RestrictedPage

        Protected Overrides ReadOnly Property ModuleName As ModuleNames
            Get
                Return ModuleNames.TerminalFirmwareVersion
            End Get
        End Property

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb:11-19

Official documentation Microsoft's MustOverride reference ties the two keywords together as one compiler-enforced rule, not just a convention: "The property or procedure that specifies MustOverride must be a member of a class, and the class must be marked MustInherit." It also documents the incomplete-declaration syntax used above: "When you specify MustOverride, you do not supply any additional lines of code for the property or procedure, not even the End Function, End Property, or End Sub statement." — exactly why RestrictedPage's ModuleName/PageAction properties above end at the declaration line with no body.
The four related keywords, and when each applies
KeywordMeansWhen to use it
MustOverrideNo implementation here — every derived class must supply one (like C#'s abstract)A member where there's genuinely no sensible default — RestrictedPage has no idea what module a specific page belongs to
OverridableHas a real default implementation, but a derived class may replace itA sensible default exists, but some derived classes legitimately need to customize it
NotOverridableExplicitly forbids further overriding (VB.NET methods are NotOverridable by default unless marked Overridable — this keyword is for un-sealing an inherited Overrides chain)Rare — you're overriding a member yourself but want to stop any further subclass from overriding it again
ShadowsHides a base class member of the same name entirely — not a real override, a new, unrelated member that happens to share a nameDeliberately breaking the inheritance relationship for one member — uncommon, and worth a comment explaining why when you see it
Official documentation — Shadows is not a weaker Overrides, it's a different relationship entirely Microsoft's Shadows reference defines the mechanism precisely: "Specifies that a declared programming element redeclares and hides an identically named element... in a base class." Critically, it also documents that a shadowing member doesn't even need a compatible signature: "If you shadow a property or procedure with another property or procedure, the parameters and the return type do not have to match those in the base class property or procedure." This is the real difference from Overrides: an Overrides member must honor the base member's contract (same signature, substitutable via polymorphism); a Shadows member is simply a new, independent member that reuses the name — calling code that holds a reference typed as the base class still reaches the base member, not the shadowed one.

A fuller worked example: RestrictedPage's whole inheritance chain, not just the abstract members

RestrictedPage is worth reading end-to-end once, because it demonstrates every inheritance keyword this lesson covers inside one real, shipped class — not MustOverride alone.

Public MustInherit Class RestrictedPage
    Inherits System.Web.UI.Page

    Protected Overrides Sub OnInit(e As System.EventArgs)
        ViewStateUserKey = Session.SessionID
        MyBase.OnInit(e)
    End Sub

    Protected Overrides Sub OnLoad(e As System.EventArgs)
        ...
        OnAuthenticate(args)
        ...
        MyBase.OnLoad(e)
    End Sub

    Protected Overridable Sub OnAuthenticate(e As RestrictedPageEventArgs)
        Profiles.CheckAccessRight(e.FunctionId, e.Action)
        ...
    End Sub
End Class

Four distinct inheritance relationships, all in this one class:

  • Inherits System.Web.UI.Page — RestrictedPage itself is a subclass of ASP.NET's own Page class. Every real BackOffice page that inherits RestrictedPage is therefore two levels deep: Page → RestrictedPage → TerminalFirmwareVersionList (or whichever page).
  • Protected Overrides Sub OnInit/OnLoad — these already exist on Page with real behavior; RestrictedPage replaces them, but calls MyBase.OnInit(e)/MyBase.OnLoad(e) to still run the original Page behavior afterward, rather than discarding it entirely.
  • Protected Overridable Sub OnAuthenticate — unlike ModuleName/PageAction (MustOverride, covered above), this one has a real default implementation (checking access rights, then SAP-tab visibility) — a derived page may override it for custom authentication logic, but most pages don't need to and simply inherit the default behavior unchanged.
  • The two MustOverride properties from before — no default at all, every derived page must supply its own.
Official documentation Microsoft's own Me, My, MyBase, and MyClass reference names exactly this pattern: "The MyBase keyword behaves like an object variable referring to the base class of the current instance of a class. MyBase is commonly used to access base class members that are overridden or shadowed in a derived class." MyBase.OnInit(e) is precisely this — RestrictedPage's own OnInit adds session-key setup on top of whatever System.Web.UI.Page's own OnInit already does, rather than replacing it outright. Skipping the MyBase call would silently drop whatever the base Page class needs its own OnInit to do — a real, easy-to-miss way an Overrides method can break its base class's contract.
Why this specific chain matters for BackOffice's actual access control This is the mechanism behind every "you don't have permission" redirect in BackOffice: OnLoad (which every page inherits, unmodified) calls the Overridable OnAuthenticate, which calls Profiles.CheckAccessRight(...) using the MustOverride ModuleName/PageAction values the concrete page was forced to supply. A page author never has to remember to call a permission check manually — it runs automatically as part of the page lifecycle every derived page already participates in, purely because it inherits from RestrictedPage. This is what "the compiler enforces it" (from the MustOverride section above) actually buys in production: the permission check isn't something a developer could forget to wire up, because it's baked into a lifecycle method nobody overrides.

Implements — written on the class, then again on every member

The biggest real syntax difference from C# interfaces: VB.NET makes you say Implements twice — once declaring the class implements the interface, and again on each member that satisfies it, naming exactly which interface member it fulfills:

Public Interface ITerminalService
    Function Login(terminalId As String) As Boolean
End Interface

Public Class TerminalService
    Implements ITerminalService

    Public Function Login(terminalId As String) As Boolean Implements ITerminalService.Login
        Console.WriteLine("Logging in terminal: " & terminalId)
        Return True
    End Function
End Class
Official documentation Microsoft's Implements Statement reference confirms both halves of the double declaration are separately mandatory: "The Implements statement must immediately follow the Class or Structure statement," and per-member, "To implement an individual member, you specify the Implements keyword (which is separate from the Implements statement) when you declare the member." It also states what happens if a member is skipped: "When you implement an interface, you must implement all the members declared in the interface. Omitting any member is considered to be a syntax error." — there's no equivalent of a C# compile warning here; a missed interface member simply doesn't compile.
Why the double declaration exists — and what it buys you Unlike C#, a VB.NET method's name doesn't have to match the interface member it implements — Public Function DoLogin(...) Implements ITerminalService.Login is perfectly legal, and the Implements clause is what actually wires it up. This is genuinely more explicit than C# (you can always see exactly which interface member a method satisfies by reading its own signature, not by matching names), but it also means a method can implement an interface member under a completely different name than the interface declares — read the Implements clause, not just the method name, to know what a method actually satisfies.

Best practice

  • Reach for MustInherit/MustOverride when every subclass genuinely needs to supply its own answer and there's no sensible shared default. Like RestrictedPage forcing every page to declare its own module and permission action. Reach for Overridable with a real default implementation when most subclasses would want the same behavior and only a few need to customize it.
  • Keep an implementing method's name matching the interface member name, even though VB.NET doesn't require it. A mismatched name (DoLogin implementing ITerminalService.Login) is technically legal but makes the code harder to search and reason about for no real benefit.
  • Reach for Shadows only when deliberately breaking the inheritance relationship for one member, and say why in a comment. Because a Shadows member isn't reachable through a base-typed reference, using it by accident (instead of Overrides) silently produces two independent members with the same name — a real, hard-to-spot bug source.
  • When overriding a lifecycle method that already has real base-class behavior (like OnInit/OnLoad), call MyBase.MethodName(...) unless you specifically intend to replace that behavior entirely. RestrictedPage's own OnInit/OnLoad both do this — skipping the MyBase call is a real, easy way to silently break whatever the base class needed that method to do.

Better ways

Public Property X As T auto-properties are convenient, exactly like C#'s { get; set; } — but the same caution applies: if setting the property is really a meaningful action with rules attached (not just a raw field write), a real method (Sub Deactivate()) communicates that intent better than a property anyone can silently overwrite.

Check your understanding

RestrictedPage declares Protected MustOverride ReadOnly Property ModuleName As ModuleNames. What does this force on every class that inherits RestrictedPage?

  • Nothing — it's optional, derived classes may keep RestrictedPage's own default behavior if they want.
  • Every derived class must supply its own implementation of ModuleName — there is no default to fall back on.
  • Every derived class must define a parameterless constructor.

In VB.NET, Public Function DoLogin(id As String) As Boolean Implements ITerminalService.Login is valid, even though the method is named DoLogin, not Login. Why does this compile?

  • The Implements clause explicitly states which interface member this method satisfies — VB.NET doesn't require the method's own name to match the interface's member name.
  • VB.NET interfaces use fuzzy name matching by default.
  • This only works for interface members marked as optional.

A base class has Public Sub Notify(). A derived class declares its own Public Shadows Sub Notify() with a completely different parameter list. Code elsewhere holds a variable declared as the base class type, pointing at an instance of the derived class, and calls .Notify(). Which version runs?

  • The base class's Notify() — a base-typed reference resolves to the base member, since Shadows doesn't participate in polymorphism the way Overrides does.
  • The derived class's Notify(), because the actual object at runtime is the derived type.
  • It's a compile error — Shadows requires the same parameter list as the base member.

A class declares Implements ICustomerInfo, where the interface defines a property, a procedure, and an event. The class supplies the property and the procedure, but forgets the event. What happens?

  • It compiles with a warning about the missing event.
  • It's a compile error — every member declared in the interface must be implemented, with no exceptions for events specifically.
  • It compiles fine — VB.NET supplies a default no-op implementation for any interface member the class doesn't define.

RestrictedPage's real OnInit override calls MyBase.OnInit(e) after setting ViewStateUserKey. What would break if that MyBase.OnInit(e) call were removed?

  • Nothing — MyBase calls are only needed for error handling.
  • Whatever System.Web.UI.Page's own OnInit implementation does would never run — Overrides fully replaces the base method unless the derived method explicitly calls back into it via MyBase.
  • The MustOverride properties (ModuleName/PageAction) would stop being required.

RestrictedPage's OnAuthenticate is declared Protected Overridable, unlike ModuleName/PageAction which are MustOverride. What does a derived BackOffice page actually have to do about each one?

  • It must supply its own ModuleName/PageAction (no default exists), but overriding OnAuthenticate is entirely optional — most pages just use RestrictedPage's own default authentication logic unchanged.
  • It must override all three, since inheriting from a MustInherit class requires overriding every member.
  • It can leave all three at their inherited defaults, since RestrictedPage is MustInherit.
