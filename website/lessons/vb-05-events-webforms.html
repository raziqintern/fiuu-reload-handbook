Events: WithEvents, Handles & AddHandler

Every Handles Me.Load and Handles btnExcel.Click in every BackOffice page relies on a mechanism this lesson makes explicit — and knowing the alternative (AddHandler) matters the moment you need to wire up something the designer didn't generate for you.

WithEvents is what makes Handles possible

Handles only works on a variable declared WithEvents — this isn't automatic for every object, it's a specific declaration that tells the compiler "this variable can raise events I might want to handle." Every WebForms control on a page gets exactly this treatment, generated for you:

Protected WithEvents form1 As Global.System.Web.UI.HtmlControls.HtmlForm
Protected WithEvents ScriptManager1 As Global.System.Web.UI.ScriptManager
Protected WithEvents applicationTitle As Global.System.Web.UI.HtmlControls.HtmlGenericControl

reload/web/DEV/NET/Applications/BackOffice/Web/BackOffice.Master.designer.vb:41,50,59

That's why a code-behind file can just write Handles btnExcel.Click without ever seeing an explicit "subscribe to this event" statement anywhere — the .designer.vb partner file (auto-generated, regenerated whenever the designer view changes) already declared every markup control WithEvents, and Handles does the actual wiring at compile time:

Protected Sub Page_Load(ByVal sender As Object, ByVal e As System.EventArgs) Handles Me.Load
Protected Sub btnExcel_OnClick(ByVal sender As Object, ByVal e As EventArgs) Handles btnExcel.Click

reload/web/DEV/NET/Applications/BackOffice/Web/WebForms/TerminalFirmwareVersionList.aspx.vb:31,321

Official documentation Microsoft's Handles Clause reference confirms the requirement precisely: "The events must be raised by either the base class for the current class, or by an object declared using the WithEvents keyword." The method's own name plays no role in that resolution at all — the reference's own examples wire up handlers named EventHandler, TestEvents, and Button_Click to differently-named events purely via the Handles clause.
The method name doesn't matter — the Handles clause does btnExcel_OnClick could be renamed to anything at all without breaking the wiring, because Handles btnExcel.Click — not the method's name — is what tells the compiler this method runs when btnExcel raises Click. The _OnClick naming is a strong, near-universal convention in this codebase, purely for human readability; the compiler doesn't need it to work.

AddHandler / RemoveHandler — for everything Handles can't reach

Handles needs a WithEvents variable known at compile time — a control declared in markup and generated into the designer file qualifies. It can't handle events on shared (static) members, events on a Structure, or anything created dynamically at runtime (a control built in code, not markup). For those, AddHandler/RemoveHandler are the only option — a real, verified example from this exact codebase:

AddHandler My.Application.Shutdown, AddressOf AutoSaveSettings

reload/web/DEV/NET/Applications/BackOffice/Web/My Project/Settings.Designer.vb:47

My.Application.Shutdown is a shared application-lifecycle event — there's no per-instance WithEvents variable to attach Handles to, so AddHandler (paired with AddressOf to point at the handler method) is the only mechanism that reaches it.

Official documentation Microsoft's AddHandler Statement reference names the essential difference directly: "The AddHandler statement connects procedures to events at run time," versus Handles, which is fixed at compile time as part of the method declaration itself. The same reference documents the cleanup requirement mentioned below in its RemoveHandler discussion: a handler attached anonymously (an inline lambda with no name) "cannot be removed later," which is exactly why a long-lived AddHandler subscription should point at a named method or a variable holding the lambda, not an anonymous inline one, if it will ever need to be removed.
When you'd actually need AddHandler in a WebForms page: dynamically created controls If a page builds controls in code — a row added to a panel in a loop, a button created at runtime rather than declared in markup — that control was never processed by the designer, so no WithEvents field exists for it and Handles has nothing to attach to. Wiring its click event requires AddHandler dynamicButton.Click, AddressOf HandleDynamicClick at the point the control is created. This is also the one case where you're responsible for cleanup: a handler added with AddHandler keeps the target object alive as long as the event source is alive, so a long-lived event source (not a per-request WebForms control, which dies with the page anyway, but a longer-lived singleton or shared object) needs a matching RemoveHandler to avoid leaking the handler's target — the same shape of leak-by-omission this codebase has seen elsewhere with unreleased resources (see Debugging Reload → Worked Example: Tracing a Bug).

Best practice

  • For any control that exists in the page's markup, use Handles. It's what the whole codebase already does, it's compiler-checked (a typo'd control name is a compile error, not a silent no-op), and it needs no manual cleanup.
  • Reach for AddHandler only when Handles genuinely can't reach the event. A dynamically created control, a shared/static event, or an event on a type that isn't WithEvents-declared. When you do, track whether the event source outlives the request; if it does, pair every AddHandler with a RemoveHandler at the appropriate cleanup point.
  • Name every AddHandler target method (or store a lambda in a variable) if you'll ever need to remove it. An anonymous inline lambda handler is documented as unremovable later — there's no way to reference it in a later RemoveHandler call.

Better ways

If you find yourself wanting to attach the same handler to many controls at once (e.g. every button in a toolbar should trigger the same "mark dirty" logic), a loop with AddHandler at page-build time is more maintainable than repeating the same method name across a dozen Handles clauses — but only reach for it once Handles has genuinely become repetitive, not as a default style choice.

Check your understanding

A WebForms code-behind file has Protected Sub SomeMethod(sender As Object, e As EventArgs) Handles btnSave.Click. What declaration does this rely on existing somewhere for btnSave?

  • A Protected WithEvents btnSave As ... declaration, typically in the page's auto-generated .designer.vb file.
  • Nothing specific — Handles works by matching the method name to the control name automatically.
  • An AddHandler call somewhere else in the same file.

A page builds a new Button control in code inside Page_Load (not declared anywhere in the .aspx markup) and needs to run code when it's clicked. Why won't a Handles clause work here?

  • The control was never declared as a WithEvents field by the designer — Handles needs one to attach to, and dynamically created controls don't have one.
  • Handles only works for Page-level events like Load, never control events like Click.
  • The button needs to be declared Public instead of Private for Handles to see it.

An inline, unnamed lambda is passed directly to AddHandler Obj.Ev_Event, Sub() MsgBox("hi"). Later, the code wants to detach that exact handler with RemoveHandler. What happens?

  • It works — RemoveHandler can reference the same lambda expression again by writing it out identically.
  • It can't be done — an unnamed inline lambda handler has no way to be referenced again, so it can never be removed with RemoveHandler.
  • It throws at runtime, because RemoveHandler requires the underlying object to be declared WithEvents.
