Big O Notation

This track is language-agnostic computer-science fundamentals — the thinking tools that apply whether you're writing JavaScript, C#, or VB.NET. It sits here because you now know enough syntax (from HTML/JS Basics) to see it in real, runnable code.

Big O measures growth, not stopwatch time

Big O notation describes how the amount of work a piece of code does grows as its input gets bigger — not how many milliseconds it takes on your specific machine. "This is O(n)" means "if you double the input size, expect roughly double the work," regardless of whether that machine is fast or slow.

See it happen: O(n) vs. O(n²)

Run this, then change 10 to 100 in both calls and run it again — watch how differently the two numbers scale.

function countOperations(n) {
  let count = 0;
  for (let i = 0; i < n; i++) {
    count++;
  }
  return count;
}

function countNestedOperations(n) {
  let count = 0;
  for (let i = 0; i < n; i++) {
    for (let j = 0; j < n; j++) {
      count++;
    }
  }
  return count;
}

console.log("Single loop,  n=10: ", countOperations(10));
console.log("Nested loop,  n=10: ", countNestedOperations(10));
console.log("Single loop,  n=100:", countOperations(100));
console.log("Nested loop,  n=100:", countNestedOperations(100));

Multiplying the input by 10 multiplies the single loop's work by 10 (linear — O(n)), but multiplies the nested loop's work by 100 (quadratic — O(n²)). That gap only gets more extreme as inputs grow — this is the entire reason Big O matters: it predicts which code will fall over first as real-world data grows.

The classes you'll actually encounter

NotationMeaningExample
O(1)Constant — same work regardless of input sizeReading array[5] by index
O(log n)Shrinks the remaining work by a fraction each stepBinary search (next lesson)
O(n)Linear — work scales directly with input sizeLooping through every item once
O(n log n)Slightly worse than linearEfficient sorting algorithms
O(n²)Quadratic — a loop inside a loop over the same dataComparing every item to every other item
Why a new engineer should care about this at all Code that's "obviously correct" and works fine in testing with 10 rows can become a real production incident at 100,000 rows if it's secretly O(n²). Recall Debugging Reload → Known Patterns & Pitfalls's review comment about unbounded report queries — that's this exact concern from a different angle: an operation whose cost scales with data size needs a limit, or its growth rate needs to be genuinely linear, not quadratic.

Check your understanding

A function loops through a list of n transactions once, doing a small fixed amount of work per transaction. What's its Big O?

  • O(1) — it's fast.
  • O(n) — the work scales directly with the number of transactions.
  • O(n²) — because there's a loop involved.
