Big O measures growth, not stopwatch time

Big O notation describes how the amount of work a piece of code does grows as its input gets bigger — not how many milliseconds it takes on your specific machine. "This is O(n)" means "if you double the input size, expect roughly double the work," regardless of whether that machine is fast or slow.

Example: see it happen — O(n) vs. O(n²)

Predict both outputs, then reveal. Notice multiplying n by 10 multiplies the single-loop result by 10, but the nested-loop result by 100.

static int CountOperations(int n)
{
    int count = 0;
    for (int i = 0; i < n; i++)
    {
        count++;
    }
    return count;
}

static int CountNestedOperations(int n)
{
    int count = 0;
    for (int i = 0; i < n; i++)
    {
        for (int j = 0; j < n; j++)
        {
            count++;
        }
    }
    return count;
}

static void Main()
{
    Console.WriteLine("Single loop, n=10:  " + CountOperations(10));
    Console.WriteLine("Nested loop, n=10:  " + CountNestedOperations(10));
    Console.WriteLine("Single loop, n=100: " + CountOperations(100));
    Console.WriteLine("Nested loop, n=100: " + CountNestedOperations(100));
}
Single loop, n=10:  10
Nested loop, n=10:  100
Single loop, n=100: 100
Nested loop, n=100: 10000
Function CountOperations(n As Integer) As Integer
    Dim count As Integer = 0
    For i As Integer = 0 To n - 1
        count += 1
    Next
    Return count
End Function

Function CountNestedOperations(n As Integer) As Integer
    Dim count As Integer = 0
    For i As Integer = 0 To n - 1
        For j As Integer = 0 To n - 1
            count += 1
        Next
    Next
    Return count
End Function

Sub Main()
    Console.WriteLine("Single loop, n=10:  " & CountOperations(10))
    Console.WriteLine("Nested loop, n=10:  " & CountNestedOperations(10))
    Console.WriteLine("Single loop, n=100: " & CountOperations(100))
    Console.WriteLine("Nested loop, n=100: " & CountNestedOperations(100))
End Sub

The classes you'll actually encounter

NotationMeaningExample
O(1)Constant — same work regardless of input sizeReading array[5] by index
O(log n)Shrinks the remaining work by a fraction each stepBinary search (next lesson)
O(n)Linear — work scales directly with input sizeLooping through every item once
O(n log n)Slightly worse than linearEfficient sorting algorithms
O(n²)Quadratic — a loop inside a loop over the same dataComparing every item to every other item

Best practice

  • Know the Big O of any loop you write over data whose size isn't fixed and small — "this runs fine in testing" doesn't tell you how it behaves at 100x the data.
  • Watch for accidental nesting: calling an O(n) method (like .FirstOrDefault(predicate)) inside a loop that already runs n times silently creates an O(n²) operation.

Better ways

If you find yourself nesting a search inside a loop over the same collection, a Dictionary<TKey, TValue> keyed lookup (O(1)) is very often the fix — see Stacks, Queues & Dictionaries.

Why a new engineer should care about this at all Code that's "obviously correct" and works fine in testing with 10 rows can become a real production incident at 100,000 rows if it's secretly O(n²). Recall Debugging Reload → Known Patterns & Pitfalls's review comment about unbounded report queries — that's this exact concern from a different angle: an operation whose cost scales with data size needs a limit, or its growth rate needs to be genuinely linear, not quadratic.

Check your understanding

A method loops through a list of n transactions once, doing a small fixed amount of work per transaction. What's its Big O?

  • O(1) — it's fast.
  • O(n) — the work scales directly with the number of transactions.
  • O(n²) — because there's a loop involved.
