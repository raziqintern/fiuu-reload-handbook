Debugging Reload

Reading the Logs First

You've now seen why this matters: error handling swallows exceptions into sentinel values, and the log is often the only place the real story survives. This lesson turns that into a habit.

The core fact this whole track is built on

A -1, false, or null return value is ambiguous by design Under reload's dominant catch-log-return-sentinel pattern (Conventions → Error Handling), a Provider method returning -1 could mean "legitimately nothing found" or "an exception was thrown and swallowed." The two are indistinguishable from the return value alone. When debugging "why did this silently not work", check the log before you re-read the C# a third time.

Search by correlation key, not chronologically

Recall the >>>/<<< bracket convention from Conventions → Logging: outbound calls are logged with a [Key: ...] correlation id, usually the business reference. Given a specific failing transaction, search the log for its reference id directly — don't scroll from the top of the file.

The root cause: logging and handling are two separate responsibilities that keep getting merged into one catch block

"Log the exception" and "handle/recover from the exception" are logically independent decisions — a layer can do either, both, or neither. The bug in this section happens whenever two layers in the same call chain both decide to log, because neither one knows the other already did. This isn't specific to reload's LogHelper convention — it's a general call-stack problem that shows up anywhere exceptions propagate through more than one layer.

The most misleading thing you'll see in a log: duplicate entries for one real error

This is a real, explicitly-named review complaint — reviewer khenggek flags it repeatedly across unrelated merge requests:

"Please check whether the reference will write to event viewer. There is no point in writing to viewer and throw the same exception again. This will cause it to write to event viewer twice for the same error and will be misleading." — MR !844
"Please always check the method reference. Is there try catch at the reference? If yes, you should not put try catch here as you are just logging and throwing exception again and causing double writing to event viewer..." — MR !470

A method catches an exception, logs it, and rethrows — but the caller also catches and logs the same exception. Result: one real failure produces two log entries with different call-stack framing, which looks like two separate problems during incident triage.

Official documentation — this is a known problem at the framework level too, not just a reload code-review nitpick Microsoft's own ASP.NET Core 10 breaking-change notice documents the exact same failure mode inside ASP.NET Core's own exception-handling middleware. Previous behavior: "the exception handler middleware recorded diagnostics about exceptions handled by IExceptionHandler" — meaning the middleware logged the exception even when an app's own IExceptionHandler had already logged it. Reason for the fix in .NET 10: "Their IExceptionHandler implementation reported that the exception was handled, but the error handling middleware still recorded the error in the app's telemetry." Microsoft's own framework shipped this exact "handled here, but logged again one layer up" bug for multiple major versions before fixing it in .NET 10 — the reload review complaints above are catching, by hand, precisely the class of bug Microsoft needed a breaking change to fix in their own middleware.
The rule Log in exactly one place per exception. Either let it propagate unlogged to a handler further up that will log it, or catch and log it here without rethrowing to something that will log it again. If you see the same error message twice in a log with slightly different context, suspect this pattern before you suspect two real, independent failures.
What if the caller doesn't log at all? The opposite failure mode is just as real: if the inner method's catch swallows the exception (logs it, then returns a sentinel like -1 or false instead of rethrowing — see Conventions → Error Handling) and the caller has no idea an exception happened, the caller can't add any of its own context (which terminal, which request) to that log entry. Either extreme — logging twice with no coordination, or logging once with no context from the caller — comes from the same root problem: no single layer owns "who logs this exception," so each layer decides independently.

What actually gets logged — and what doesn't

Full outbound request/response JSON payloads, generally. Exceptions, with whatever customMessage the author bothered to add. Row-count/no-op conditions, sometimes, as informational writes rather than errors. What's not guaranteed: a consistent method surface across modules (each module's LogHelper is different — see Logging), or redaction of sensitive fields before logging.

Best practice

  • Before re-reading C# a third time on a "why did this silently not work" report, go straight to the log and search by the transaction's reference id or terminal id. The correlation-key convention exists specifically so you don't have to scroll chronologically.
  • If you're adding a new try/catch in a call chain, decide up front whether this layer logs or the caller does — never assume "logging here is harmless, it's just extra information." As the ASP.NET Core case above shows, "log defensively at every layer just in case" is exactly how duplicate, misleading log entries get created, even in mature, widely-used frameworks.

Check your understanding

You find the same exception message logged twice for one transaction, with slightly different surrounding text. What should you suspect first?

  • Two unrelated bugs happened to occur at almost the same time.
  • A method logged the exception and rethrew it to a caller that also logs — the double-exception-logging anti-pattern.
  • The log file rotated and duplicated an old entry.

Per Microsoft's own ASP.NET Core 10 breaking-change notice, what was the actual problem with the exception handler middleware's previous behavior?

  • It logged an exception via its diagnostics even when the app's own IExceptionHandler had already handled and reported that same exception.
  • It failed to catch unhandled exceptions, letting them crash the app.
  • It made exceptions slower to throw by adding extra stack unwinding.
