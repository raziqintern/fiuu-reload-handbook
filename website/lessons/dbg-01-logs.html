Debugging Reload

Reading the Logs First

You've now seen why this matters: error handling swallows exceptions into sentinel values, and the log is often the only place the real story survives. This lesson turns that into a habit.

The core fact this whole track is built on

A -1, false, or null return value is ambiguous by design Under reload's dominant catch-log-return-sentinel pattern (Conventions → Error Handling), a Provider method returning -1 could mean "legitimately nothing found" or "an exception was thrown and swallowed." The two are indistinguishable from the return value alone. When debugging "why did this silently not work", check the log before you re-read the C# a third time.

Search by correlation key, not chronologically

Recall the >>>/<<< bracket convention from Conventions → Logging: outbound calls are logged with a [Key: ...] correlation id, usually the business reference. Given a specific failing transaction, search the log for its reference id directly — don't scroll from the top of the file.

The most misleading thing you'll see in a log: duplicate entries for one real error

This is a real, explicitly-named review complaint — reviewer khenggek flags it repeatedly across unrelated merge requests:

"Please check whether the reference will write to event viewer. There is no point in writing to viewer and throw the same exception again. This will cause it to write to event viewer twice for the same error and will be misleading." — MR !844
"Please always check the method reference. Is there try catch at the reference? If yes, you should not put try catch here as you are just logging and throwing exception again and causing double writing to event viewer..." — MR !470

A method catches an exception, logs it, and rethrows — but the caller also catches and logs the same exception. Result: one real failure produces two log entries with different call-stack framing, which looks like two separate problems during incident triage.

The rule Log in exactly one place per exception. Either let it propagate unlogged to a handler further up that will log it, or catch and log it here without rethrowing to something that will log it again. If you see the same error message twice in a log with slightly different context, suspect this pattern before you suspect two real, independent failures.

What actually gets logged — and what doesn't

Full outbound request/response JSON payloads, generally. Exceptions, with whatever customMessage the author bothered to add. Row-count/no-op conditions, sometimes, as informational writes rather than errors. What's not guaranteed: a consistent method surface across modules (each module's LogHelper is different — see Logging), or redaction of sensitive fields before logging.

Check your understanding

You find the same exception message logged twice for one transaction, with slightly different surrounding text. What should you suspect first?

  • Two unrelated bugs happened to occur at almost the same time.
  • A method logged the exception and rethrew it to a caller that also logs — the double-exception-logging anti-pattern.
  • The log file rotated and duplicated an old entry.
