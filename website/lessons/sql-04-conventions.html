Stored Procs, MAINT & NOLOCK

The real, reverse-engineered SQL-side conventions from conventions/sql-conventions.md — this is what a real stored procedure in this codebase actually looks like.

Stored procedure naming: <Schema>.<Table>_<Verb>[_By_<Columns>]

Verbs are always one of four abbreviations — Ins, Sel, Upd, Del:

Celcom.Transactions_Ins
Celcom.Transactions_Sel_By_ServiceTypeId_ReferenceId
Celcom.Transactions_Upd
Celcom.Transactions_Upd_IsGenerated_By_ReferenceId
dbo.AllocationOrderItems_Del_By_AllocationOrderId

reload_db/MAINT/TRANSACTION/StoredProcedure/

This naming is load-bearing, not decorative The C# side references these procedures through generated constant holders whose member names mirror the SQL name exactly — Fiuu.Provider.Database.TNG.StoredProcedures.TerminalActivities_Ins calls the stored procedure named TerminalActivities_Ins. The SQL object name and the C# constant are kept in lockstep by convention, with no codegen step visible in this repo enforcing it. Rename one without the other and the C# code silently calls a procedure that no longer exists.

Every real procedure body follows the same shape

USE [TRANSACTION]
GO
SET ANSI_NULLS ON
GO
SET QUOTED_IDENTIFIER ON
GO
-- Author/Create date/Description/Used by header
CREATE OR ALTER PROCEDURE [Celcom].[Transactions_Ins]
    @MServiceTypeId INT
    , @ReferenceId VARCHAR(50)
    ...
AS
BEGIN
    SET NOCOUNT ON;
    ...
END
GO

Consistent elements across every procedure sampled: CREATE OR ALTER PROCEDURE (not the older IF EXISTS ... DROP pattern), leading-comma parameter lists, and SET NOCOUNT ON; as the very first statement in the body.

NOLOCK on every read — a deliberate, universal choice

-- Real reload_db style (SQL Server syntax — this specific hint
-- isn't meaningful in the SQLite engine here, but the shape is real):
-- FROM [Transaction].[Celcom].[Transactions] WITH (NOLOCK)

SELECT * FROM TerminalActivities;

WITH (NOLOCK) appears on essentially every read stored procedure in the sampled codebase. It tells SQL Server "don't wait for locks, just read whatever's there even if it's mid-transaction" — a deliberate throughput-over-consistency trade-off for a high-volume transactional system. The cost: you can occasionally read a row that's about to be rolled back, or momentarily miss a row mid-insert. Worth knowing before you assume a read result is always perfectly consistent.

Official documentation Microsoft's Table Hints (Transact-SQL) reference defines NOLOCK as exactly equivalent to READUNCOMMITTED, and spells out the trade-off precisely: "Specifies that dirty reads are allowed. No shared locks are issued to prevent other transactions from modifying data read by the current transaction, and exclusive locks set by other transactions don't block the current transaction from reading the locked data. Allowing dirty reads can cause higher concurrency, but at the cost of reading data modifications that then are rolled back by other transactions." The same reference also notes a real restriction worth knowing: "READUNCOMMITTED and NOLOCK can't be specified for tables modified by insert, update, or delete operations" — NOLOCK is a read-side hint only, never valid on the table an UPDATE/DELETE/INSERT is actually writing to.

The M-prefix, on the SQL side too

Foreign keys into a lookup/status table are prefixed M (for "Master") in the database, matching the C# side you'll see in the Conventions track: MServiceTypeId, MWorkFlowStatusId, MSourceTypeId. Same convention, same intent, both layers.

Patch scripts: real, but inconsistently tagged

Column-naming and stored-procedure style are consistent; ticket references in patch-script filenames are not. The same "add a column" operation appears under at least six different spellings across real filenames:

dbo.AllocationOrders_AddColumn_GIT-790.sql
dbo.AllocationOrderItems_Add_Column_GIT_1382.sql
dbo.ApiStockOrders_Add_Column_RMSO-219.sql
dbo.ReconMOLPayDetails_Temp_Alter_Column_GIT#1114.sql

At least four ticket-tag spellings are in simultaneous use (RMSO-nnn, GIT-nnn, GIT_nnn, GITnnnn), with no single "correct" format ever unified. If you're searching for every script touching a given ticket, you cannot rely on one consistent grep pattern.

A reserved word among the database names

One of the databases in this estate is literally named TRANSACTION — a reserved T-SQL keyword. Querying it unbracketed doesn't fail with one clear message; it breaks the parser and produces a wall of unrelated-looking errors instead:

-- Fails: "Incorrect syntax near 'TRANSACTION'", plus a cascade of
-- "The multi-part identifier '...' could not be bound" on every column
SELECT * FROM TRANSACTION.dbo.OfflineSalesOrders;

-- Works: bracket the database name specifically
SELECT * FROM [TRANSACTION].dbo.OfflineSalesOrders;
Only the database name needs the brackets Once you're inside the query, the columns themselves (o.Id, o.InvoiceNo) don't need bracketing — only [TRANSACTION] does, since that's the one identifier colliding with a T-SQL keyword. If your SSMS session is already connected directly to the TRANSACTION database, you can drop the prefix entirely and just write dbo.OfflineSalesOrders.

A real optimization: making an expensive join conditional

A stored procedure searching INVENTORY.dbo.Stocks unconditionally joined out to VoidTransactions on every call, purely to support one optional void-date filter — meaning every search paid that join's cost even when nobody asked for it. The fix is a pattern worth recognising whenever a search procedure has several optional filter parameters:

-- Before: VoidTransactions joined on every call, filter used or not
SELECT ...
FROM [INVENTORY].[dbo].[Stocks] WITH (NOLOCK)
LEFT OUTER JOIN [TRANSACTION].[dbo].[VoidTransactions] VT WITH (NOLOCK)
    ON Stocks.SerialNo1 = VT.SerialNo AND Stocks.ProductId = VT.ProductId
WHERE (@VoidedStartDate IS NULL OR VT.VoidedDate BETWEEN @VoidedStartDate AND @VoidedEndDate)
  -- ...other filters...

-- After: base filters run first into a #temp table; the optional
-- join only runs at all when the caller actually supplied that filter
SELECT ... INTO #StocksFiltered
FROM [INVENTORY].[dbo].[Stocks] WITH (NOLOCK)
WHERE -- ...other filters, unrelated to VoidTransactions...

IF @VoidedStartDate IS NOT NULL
BEGIN
    SELECT main.* FROM #StocksFiltered main
    INNER JOIN [TRANSACTION].[dbo].[VoidTransactions] VT WITH (NOLOCK)
        ON main.SerialNo1 = VT.SerialNo AND main.ProductId = VT.ProductId
        AND VT.VoidedDate BETWEEN @VoidedStartDate AND @VoidedEndDate
END
ELSE
BEGIN
    SELECT * FROM #StocksFiltered
END

reload_db/MAINT/INVENTORY/StoredProcedure/dbo.Stocks_Sel_By_Search.sql

The general shape When a search procedure has an optional filter that needs its own join, don't join unconditionally and gate only the result with a WHERE @param IS NULL OR ... clause — the join still runs on every call either way. Land the base result in a #temp table first, then branch (IF @param IS NOT NULL) into whichever version of the final SELECT actually needs the extra join. It's the same underlying instinct as SQL Server's own OPTION (RECOMPILE) query hint — per Microsoft's Query Hints reference, it forces the optimizer to build a fresh plan for one statement based on the actual parameter values passed that call, instead of reusing a cached plan optimized for a different, earlier call's values (a problem called parameter sniffing — a plan cached for a search that matched 3 rows performs badly reused for one matching 3 million). Don't make every call pay for a filter almost nobody uses on any given search — whether that's a conditional join or a recompile hint, both trade a little per-call overhead for avoiding a plan that's wrong for the actual data.

Best practice

  • Follow the <Schema>.<Table>_<Verb> naming exactly when adding a new stored procedure to an existing module. Inconsistent naming here breaks the informal but load-bearing convention linking it to its C# constant.
  • Know that WITH (NOLOCK) means "I accept dirty reads." Reach for it deliberately for high-volume reporting reads, not as an unconsidered copy-paste habit for every query regardless of consistency needs.
  • Never use NOLOCK on the target table of an INSERT/UPDATE/DELETE. It's documented as invalid there — NOLOCK is a read-side hint only.

Better ways

SCOPE_IDENTITY() is the safer alternative to @@IDENTITY for retrieving a just-inserted row's id — it returns the id from the current scope's insert specifically, immune to a trigger on the table inserting its own row and returning the wrong id instead.

Official documentation Microsoft's SCOPE_IDENTITY reference spells out exactly why this matters with a real worked example: insert into a table TZ whose trigger inserts into a second table TY, and "SCOPE_IDENTITY returns the last identity value in the same scope. This was the insert on table TZ" (result: 4) while "@@IDENTITY returns the last identity value inserted to TY by the trigger... This fired because of an earlier insert on TZ" (result: 115) — two different numbers, from the exact same statement, because @@IDENTITY isn't scoped to the insert you actually asked about.

Check your understanding

Why does renaming a stored procedure in reload_db without updating the C# side silently break things, instead of failing to compile?

  • The link between the C# constant name and the SQL procedure name is convention-only — nothing checks it at compile time.
  • C# has a compiler feature that validates stored procedure names against the database.
  • The rename automatically updates every C# reference.

A table TZ has an insert trigger that inserts into a second table TY. Immediately after INSERT TZ VALUES (...), which function reliably returns the identity value generated in TZ specifically, not TY?

  • @@IDENTITY, since it always reflects the most recent insert in the session.
  • SCOPE_IDENTITY(), since it's scoped to the current insert and unaffected by what a trigger inserts elsewhere.
  • IDENT_CURRENT('TZ'), since it's the newest of the three functions.
