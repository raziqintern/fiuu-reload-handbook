Boxing & Unboxing

Builds directly on Value vs. Reference Types — this is what happens when the two worlds have to meet.

The problem: sometimes a value type needs to act like a reference type

object (and any interface) can only ever hold a reference to something on the heap. But int is a value type that normally lives on the stack. When you assign an int to an object-typed variable, the runtime has to do something to reconcile that — it boxes it: allocates a small object on the heap, copies the value into it, and gives you a reference to that box.

Example: boxing and unboxing, explicitly

int number = 42;
object boxed = number;      // boxing: a heap allocation is created here
int unboxed = (int)boxed;   // unboxing: the value is copied back out

Console.WriteLine(boxed);
Console.WriteLine(boxed.GetType());
Console.WriteLine(unboxed);
42
System.Int32
42
Dim number As Integer = 42
Dim boxed As Object = number       ' boxing: a heap allocation is created here
Dim unboxed As Integer = CInt(boxed) ' unboxing: the value is copied back out

Console.WriteLine(boxed)
Console.WriteLine(boxed.GetType())
Console.WriteLine(unboxed)
42
System.Int32
42

boxed.GetType() reports System.Int32 — the boxed object remembers its original value type. Unboxing ((int)boxed / CInt(boxed)) copies the value back into a plain stack-based int. Both directions involve a real copy; boxing additionally involves a real heap allocation.

Official documentation Microsoft's Boxing and Unboxing reference defines the mechanism precisely: "When the common language runtime (CLR) boxes a value type, it wraps the value inside a System.Object instance and stores it on the managed heap." It also confirms the two variables genuinely become independent after boxing: changing the original int afterward leaves the boxed copy unchanged, because "the original value type and the boxed object use separate memory locations, and therefore can store different values."
What if you unbox to the wrong type? A real, specific exception, not a silent conversion The same reference is exact about the requirement: "For the unboxing of value types to succeed at run time, the item being unboxed must be a reference to an object that was previously created by boxing an instance of that value type." Miss that, and: "Attempting to unbox null causes a NullReferenceException. Attempting to unbox a reference to an incompatible value type causes an InvalidCastException." Its own worked example unboxes an int-boxed value as short instead of int and gets exactly "Specified cast is not valid." — boxing remembers the exact original type, and unboxing to anything else, even a similarly-sized numeric type, fails.
Why this matters: it's a hidden performance cost Boxing looks like a harmless assignment, but it's a heap allocation and a memory copy every single time it happens. Do it once, irrelevant. Do it inside a hot loop processing thousands of transactions, and you've created thousands of tiny heap allocations the garbage collector now has to clean up — a real, measurable performance cost that's invisible just from reading the code, unless you know to look for it. 
int i = 123;
object o = i;  // boxed as System.Int32

try
{
    int j = (short)o;  // wrong type — o is a boxed int, not a boxed short
    Console.WriteLine("Unboxing OK.");
}
catch (InvalidCastException e)
{
    Console.WriteLine(e.Message + " Error: Incorrect unboxing.");
}
Specified cast is not valid. Error: Incorrect unboxing.

Where this used to bite people: non-generic collections

Before generics existed in .NET, collections like ArrayList and Hashtable stored everything as object — adding an int to an ArrayList boxed it, and reading it back out unboxed it, on every single operation. This is one of the concrete reasons generic collections (List<T>, Dictionary<TKey,TValue> — see Generics & Collections Internals) replaced them almost entirely: List<int> stores actual ints directly, with zero boxing.

Best practice

  • Always prefer the generic collection types (List<T>, Dictionary<TKey,TValue>) over their non-generic predecessors. Reload's own code already does this consistently.
  • Be alert to boxing hiding behind an innocent-looking method signature that takes object. Logging helpers that accept params object[] (common for formatted log messages) box every value-type argument you pass them.
  • Unbox to the exact original type, never a same-size lookalike. A value boxed as int must be unboxed as int — unboxing it as short, long, or any other type throws InvalidCastException, even when the numeric ranges would otherwise be compatible.

Check your understanding

Why did switching from ArrayList to List<int> improve performance for code storing lots of integers?

  • List<int> can hold more items than ArrayList.
  • ArrayList boxes every int into an object on every add/read; List<int> stores actual ints with no boxing.
  • List<int> is just newer syntax for the exact same underlying behavior as ArrayList.

object o = (int)123; then long j = (long)o; — unboxing the boxed int as a long instead. What happens, even though every int value fits inside a long?

  • It succeeds — any numeric type that can hold an int's value works for unboxing it.
  • It throws InvalidCastException — unboxing requires the exact original boxed type, and long is not the same type as the boxed int, regardless of range compatibility.
  • It succeeds, widening the int to a long the same way an implicit numeric conversion would.
