What reload actually is

A prepaid top-up / retail payment platform: physical and software point-of-sale terminals at dealers/stores submit transactions (telco airtime reload, e-wallet reload, gift cards, bill payment), which get validated, priced, persisted, and routed to the relevant external partner network — plus a back-office web portal for merchant/dealer/product administration, and a family of scheduled jobs for reporting and reconciliation.

The single most important correction to a natural first assumption

It's one monorepo, not several separate repos It's natural to assume web_api, web_app, reload_portal, terminal_application, and console_app are each their own git repository. They aren't. All of them are subfolders inside the single reload repo, under reload/web/DEV/NET/Applications/. Only reload, reload_db, and the class-library submodule are real, independent repos.

The three-tier shared-library pattern

Shared code lives in three different places, and they overlap in ways that reflect real, incomplete migration history rather than clean layering:

1. reload/web/DEV/NET/Components/*        (source, inside the reload repo itself:
                                            CEPP, Logging, Lookup, MasterFramework,
                                            Provider, ReloadsPatching, UMobile)

2. reload/class-library (submodule)        (source: AWSCore, Database, Reloads/TNG,
                                            Reloads/Game, Secure/*  —  PLUS prebuilt
                                            .dll files committed at its repo root)

3. reload/web/Libraries/NET/*              (older, per-version vendored DLL drop —
                                            still referenced by some apps in parallel
                                            with tier 2, not fully replaced by it)
Why this matters practically Don't assume "app X depends on module Y" as a blanket rule — verify it via the actual ProjectReference/HintPath in that app's project file. Some apps (like BackOffice/Web) reference the same module name from both tier 2 and tier 3 simultaneously, for different pieces — this is a live, only partially-completed consolidation, not a finished clean architecture. Per Microsoft's own Common MSBuild Project Items reference, these are two genuinely different mechanisms: HintPath is "the relative or absolute path of the assembly" for a direct prebuilt-DLL reference (tier 2's own committed DLLs, or tier 3), while ProjectReference "represents a reference to another project" resolved through that project's real build output — which is why a source-level search for "who uses module Y" can miss a consumer that's actually wired through HintPath to a DLL instead.

Best practice

  • Verify an architectural claim against the actual .csproj/ProjectReference/HintPath entries before repeating it as fact. This whole topology doc exists because the natural first assumption (separate repos per app) turned out to be wrong.
  • When a shared module could be reached through either a ProjectReference or a HintPath-based DLL, check both before concluding "app X depends on module Y" or "nothing depends on module Y." The three-tier shared-library situation means either mechanism could be in play, and only one of them shows up in a source-level search.

Check your understanding

A new hire asks "which repo is the reload_portal code in?" Based on what's actually been verified, what's the accurate answer?

  • It's a separate repo alongside web_app and web_api.
  • That's an open, unresolved question — no separate reload_portal codebase was actually found; don't treat any answer as settled without checking further.
  • It's inside Reloads/Terminal/Api, the same project as web_api.

BackOffice/Web references a shared module by name from both tier 2 (reload/class-library) and tier 3 (reload/web/Libraries/NET/*) at once, for different pieces of functionality. What does this actually tell you about the codebase?

  • A module consolidation from tier 3 to tier 2 is underway but incomplete — this app hasn't fully migrated off the older vendored DLLs yet.
  • This is a build configuration error that would prevent the app from compiling.
  • This is the intended, final architecture, and new apps should replicate this same three-tier pattern.
