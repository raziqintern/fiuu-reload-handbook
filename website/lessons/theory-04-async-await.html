Async/Await Fundamentals

Reload constantly calls out to partner APIs (TNG, INCOMM, banks) — slow, network-bound operations. Async/await is how modern .NET code waits for those without freezing everything else.

The problem it solves

A network call might take 200ms. If the calling thread just sits there blocked waiting for it, that thread can't do anything else for those 200ms — on a server handling many requests at once, that's a real scalability problem. async/await lets the thread be released back to do other work while the operation is in flight, then resume this method exactly where it left off once the result is ready.

Example: the shape of async code

using System.Threading.Tasks;

static async Task<string> FetchPartnerResponseAsync()
{
    await Task.Delay(100); // simulates a slow network call
    return "partner API response";
}

static async Task Main()
{
    Console.WriteLine("Starting request...");
    string result = await FetchPartnerResponseAsync();
    Console.WriteLine("Got: " + result);
    Console.WriteLine("Done.");
}
Starting request...
Got: partner API response
Done.
Imports System.Threading.Tasks

Async Function FetchPartnerResponseAsync() As Task(Of String)
    Await Task.Delay(100) ' simulates a slow network call
    Return "partner API response"
End Function

Async Function RunAsync() As Task
    Console.WriteLine("Starting request...")
    Dim result As String = Await FetchPartnerResponseAsync()
    Console.WriteLine("Got: " & result)
    Console.WriteLine("Done.")
End Function
Starting request...
Got: partner API response
Done.

This reads top-to-bottom exactly like ordinary synchronous code — that's deliberate, and the whole point of the feature. But at the await line, control is handed back to the caller until Task.Delay (standing in for a real network call) actually finishes; the thread isn't blocked sitting there the whole time.

The rule almost everyone breaks once Never call .Result or .Wait() on a Task to force synchronous blocking on async code — this can deadlock in some hosting contexts (classic ASP.NET, some UI frameworks), because the thread that's blocked waiting is sometimes the exact same thread the async method needs back to finish. The fix is to await all the way up the call chain, not to block partway through it.

Best practice

  • Name async methods with an Async suffix (as above) — a real, widely-followed .NET convention that flags at a glance which methods need await.
  • An async method with no await inside it runs synchronously anyway (with a compiler warning) — if nothing in the method is actually slow/async, it usually shouldn't be async at all.

Check your understanding

Why is calling .Result to force-block on an async partner-API call risky, instead of just being a harmless way to "go back to synchronous"?

  • It can deadlock in certain hosting contexts, because the blocked thread may be the same one the async call needs to resume on.
  • It makes the network call itself slower.
  • The code simply won't compile if you try it.
