Software Design & Best Practices

Git & Version Control

Reload's own repos (reload, reload_db, the class-library submodule) are all Git — and the review culture you'll meet in Debugging Reload → What Reviewers Actually Flag is entirely built on top of Git's branch/merge-request workflow. This lesson is the mechanics underneath that culture.

The core mental model

Git tracks snapshots of your entire project over time, called commits. Each commit points to the commit before it, forming a history. A branch is just a movable label pointing at one commit — creating a branch doesn't copy any files, it just gives you a new label to move independently of master/main while you work.

Official documentation Git's own Pro Git book defines a branch in exactly these terms: "A branch in Git is simply a lightweight movable pointer to one of these commits." That's why it's essentially free to create: "a branch in Git is actually a simple file that contains the 40 character SHA-1 checksum of the commit it points to, branches are cheap to create and destroy... in sharp contrast to the way most older VCS tools branch, which involves copying all of the project's files into a second directory." Nothing about the project's files is duplicated — only a small pointer is created.

The everyday command loop

git status                  # what's changed since the last commit?
git add path/to/file.cs     # stage a specific change
git commit -m "message"     # snapshot the staged changes
git push                    # send your commits to the shared remote (e.g. GitHub/GitLab)
git pull                    # bring down commits others have pushed
Stage deliberately, not with git add . git add . stages every changed file in the current directory, including ones you didn't mean to touch (stray config, debug prints, an accidentally-edited unrelated file). Reviewing git status and adding specific files is slower but catches mistakes before they're committed — and definitely before they're pushed for someone else to review.

Branches: work in isolation, merge when ready

git checkout -b fix/duplicate-transaction-race   # create and switch to a new branch
# ...make changes, commit them...
git push -u origin fix/duplicate-transaction-race # push the branch to the remote

A branch name that describes the actual change (like the one above, echoing the real issue #1483 from Debugging Reload → Worked Example) is far more useful in a project's history six months later than my-branch or fix.

What a merge request/pull request actually is

A merge request (GitLab's term — GitHub calls the same thing a pull request) is a proposal: "merge the commits on this branch into master." It's the unit reviewers actually look at — a diff of every change, plus a place for line-by-line comments. This is the exact mechanism behind every quoted reviewer comment in the Debugging Reload track — khenggek and deepcode_ai are both commenting on merge requests, not on individual commits.

Merge conflicts: two changes to the same lines

If two branches both modify the same lines of the same file, Git can't automatically decide which version wins — that's a merge conflict. Resolving one means manually choosing (or combining) the correct final content for those lines before the merge can complete. This isn't a Git failure; it's Git correctly refusing to silently discard someone's work.

Official documentation Git's own git-merge reference states exactly when this happens: "When both sides made changes to the same area... Git cannot randomly pick one side over the other, and asks you to resolve it by leaving what both sides did to that area." It marks the conflicting section directly in the file, using the RCS-style markers: 
<<<<<<< yours:sample.txt
Conflict resolution is hard;
let's go shopping.
=======
Git makes conflict resolution easy.
>>>>>>> theirs:sample.txt

Everything above the ======= is your branch's version of those lines; everything below is the other branch's. Resolving the conflict means editing the file down to the single correct version and removing all three marker lines, before the merge can be committed.

Best practice

  • Stage deliberately, never with git add . as a reflex. Review git status first so you know exactly what's about to be committed.
  • Name a branch after the actual change, not a placeholder like my-branch or fix. A descriptive name is what makes the project's history readable six months later.
  • When resolving a merge conflict, remove every one of the three marker lines, not just pick a side. Leaving a stray <<<<<<</=======/>>>>>>> in committed code is a real, if embarrassing, mistake — it compiles as garbage or breaks the build outright.

Check your understanding

Why create a new branch instead of committing directly to master while working on a fix?

  • Branches automatically run tests before allowing a commit.
  • It isolates your in-progress work from the stable shared history, and gives reviewers a clear diff to review before it's merged.
  • It creates a separate copy of the entire repository on disk.

Why is creating a new Git branch essentially instantaneous, even in a huge repository, per Git's own documentation?

  • It copies every project file into a new directory in the background.
  • A branch is just a small file holding a 40-character commit checksum — creating one only writes that tiny pointer, regardless of the project's actual size.
  • Git compresses the whole repository before creating the branch.

A merged file still contains a line reading exactly ======= in the middle of otherwise normal code. What does this indicate?

  • A merge conflict marker was left behind unresolved — both conflicting versions are still present in the file.
  • It's a normal code comment separator, harmless to leave in.
  • It's Git automatically documenting where a merge happened, safe to keep.
