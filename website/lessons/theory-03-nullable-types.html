Nullable Types

Value types normally can't be null — an int is always some actual number. Sometimes "no value at all" is itself a meaningful, distinct state you need to represent.

The problem: not every missing value is zero

If a database column allows NULL, mapping it straight to a plain int loses information: is the value genuinely 0, or was it actually absent? Nullable<T> (written T?) wraps a value type so it can hold either a real value or nothing, distinctly.

Example: HasValue, ??, and ?.

int? maybeAmount = null;
Console.WriteLine(maybeAmount.HasValue);
Console.WriteLine(maybeAmount ?? -1); // null-coalescing: fallback when null

maybeAmount = 25;
Console.WriteLine(maybeAmount.HasValue);
Console.WriteLine(maybeAmount.Value);
False
-1
True
25
Dim maybeAmount As Integer? = Nothing
Console.WriteLine(maybeAmount.HasValue)
Console.WriteLine(If(maybeAmount, -1)) ' null-coalescing: fallback when null

maybeAmount = 25
Console.WriteLine(maybeAmount.HasValue)
Console.WriteLine(maybeAmount.Value)
False
-1
True
25

.HasValue tells you whether there's really a value inside. Reading .Value when HasValue is false throws — so ?? (C#) / If(x, fallback) (VB.NET) is the safe way to read a nullable with a default.

Example: the null-conditional operator avoids the crash entirely

public class Terminal
{
    public string Id;
}

static void Main()
{
    Terminal t = null;
    Console.WriteLine(t?.Id ?? "no terminal");
}
no terminal
Public Class Terminal
    Public Id As String
End Class

Sub Main()
    Dim t As Terminal = Nothing
    Console.WriteLine(If(t?.Id, "no terminal"))
End Sub
no terminal

t?.Id means "if t is null, the whole expression is null — don't even try to read .Id." This is C#/VB.NET's native defense against exactly the class of bug you saw in JavaScript Basics → DOM, Events & the Console's "Cannot read properties of undefined" — here it's called a NullReferenceException, and ?. lets you skip past a possibly-null reference instead of crashing on it.

This is a real, named pattern in reload's own conventions Recall Conversion.DBNullToNullableDecimal from Fiuu C# Conventions → Data Access — part of the shared helper family that maps a database NULL into exactly this kind of nullable value type, precisely so "the column was NULL" and "the column was zero" stay distinguishable once the data reaches C#.

Best practice

Reach for T? whenever "no value" is a real, meaningful state for that field — not as a lazy substitute for proper validation. A required amount field should never be nullable; an optional "last synced" timestamp genuinely should be.

Check your understanding

A database column allows NULL for an optional discount percentage. Why map it to decimal? instead of a plain decimal defaulting to 0?

  • decimal? is faster to read from the database.
  • A plain decimal defaulting to 0 can't distinguish "no discount was ever set" from "a discount of exactly 0 was explicitly set."
  • decimal? automatically validates the value is a legitimate percentage.
