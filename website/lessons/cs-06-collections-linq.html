C# Fundamentals

Collections & LINQ

The last stop in this track. LINQ is C#'s answer to JavaScript's .filter()/.map()/.reduce() — same ideas, C# spelling.

List<T> and basic LINQ

using System.Linq;

List<double> amounts = new List<double> { 10, 25.5, 100, 5 };

double total = amounts.Sum();
Console.WriteLine("Total: " + total);

List<double> large = amounts.Where(a => a > 20).ToList();
Console.WriteLine("Over 20 count: " + large.Count);
Total: 140.5
Over 20 count: 2

List<double> is a resizable, strongly-typed list — the <double> means "this list only ever holds doubles", enforced by the compiler. .Where(...) filters, matching JavaScript's .filter() almost exactly; the a => a > 20 part is a lambda expression, C#'s equivalent of a JS arrow function.

LINQ over a list of objects

This mirrors the array-of-objects lesson from the JavaScript track — same logic, real C# types:

public class Transaction
{
    public string TransNo { get; set; }
    public double Amount { get; set; }
    public string Status { get; set; }
}

class Program
{
    static void Main()
    {
        var transactions = new List<Transaction>
        {
            new Transaction { TransNo = "TXN-1001", Amount = 10.0, Status = "Success" },
            new Transaction { TransNo = "TXN-1002", Amount = 25.5, Status = "Pending" },
            new Transaction { TransNo = "TXN-1003", Amount = 5.0, Status = "Failed" }
        };

        var pending = transactions.Where(t => t.Status == "Pending").ToList();
        Console.WriteLine("Pending count: " + pending.Count);

        var transNos = transactions.Select(t => t.TransNo).ToList();
        Console.WriteLine(string.Join(", ", transNos));
    }
}
Pending count: 1
TXN-1001, TXN-1002, TXN-1003

var lets the compiler infer the type from the right-hand side — it's still statically typed underneath (transactions is genuinely a List<Transaction>), it's just a shorthand so you don't have to spell the type out twice. .Select(...) transforms every item, matching JS's .map().

List<double> emptyList = new List<double>();

try
{
    double firstValue = emptyList.First();
    Console.WriteLine(firstValue);
}
catch (InvalidOperationException)
{
    Console.WriteLine("First() threw InvalidOperationException");
}

double firstOrDefaultValue = emptyList.FirstOrDefault();
Console.WriteLine("FirstOrDefault() returned: " + firstOrDefaultValue);
First() threw InvalidOperationException
FirstOrDefault() returned: 0
FirstOrDefault's "default" depends on the type — it isn't always null For a reference type (a class, like Transaction), FirstOrDefault() on an empty sequence returns null. For a value type like double or int, there's no null to return — it returns that type's own default value instead (0 for numbers, false for bool). This is exactly why checking a FirstOrDefault() result against null silently does nothing useful when the element type is a value type — the check needs to compare against that type's actual default, or the code needs to check .Any() before calling FirstOrDefault() at all.

Official documentation Microsoft's Enumerable.First reference documents the exact failure mode: "The First<TSource>(IEnumerable<TSource>) method throws an exception if source contains no elements." Specifically InvalidOperationException, listed in its own Exceptions table as occurring when "The source sequence is empty." The same reference names the fix directly: "To instead return a default value when the source sequence is empty, use the FirstOrDefault method."

Best practice

  • Prefer LINQ (.Where/.Select/.Sum) over hand-written loops for filtering, transforming, and aggregating. It's shorter, and it says what you want instead of how to loop to get it.
  • Call .FirstOrDefault(...), not .First(...), whenever "no match" is a real possible outcome. .First() throws InvalidOperationException on an empty result; .FirstOrDefault() returns null/default, matching the real reviewer complaint about unguarded FirstOrDefault() results in Debugging Reload → What Reviewers Actually Flag.

Better ways

Chaining .Where(...).ToList() and then immediately calling .Select(...) on the result (as in the example above) works, but each .ToList() forces the whole sequence to materialize before the next step runs. For a longer pipeline, skipping the intermediate .ToList() calls lets LINQ's lazy evaluation combine the steps more efficiently — worth knowing once you're chaining more than two or three operations together.

Check your understanding

transactions.Select(t => t.TransNo) — what does this produce?

  • Only the transactions whose TransNo is set.
  • A new sequence containing just the TransNo string from every transaction, in order.
  • The number of transactions that have a TransNo.

A method calls amounts.FirstOrDefault(a => a > 1000) on a List<double>, and no amount actually exceeds 1000. The result is checked with if (result == null) to detect "no match." Does this work?

  • Yes — FirstOrDefault() always returns null when nothing matches, regardless of type.
  • No — double is a value type, so FirstOrDefault() returns 0 (its default value) on no match, not null. The == null check doesn't detect this correctly.
  • It throws an exception, since FirstOrDefault() can't handle value types.
