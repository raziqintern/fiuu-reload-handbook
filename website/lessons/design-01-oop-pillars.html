Encapsulation: hide the internals, expose a controlled surface

class Terminal {
  constructor(id, balance) {
    this._id = id;
    this._balance = balance; // leading underscore: "internal, don't touch directly"
  }
  deposit(amount) {
    if (amount <= 0) throw new Error("Deposit must be positive");
    this._balance += amount;
  }
  getBalance() {
    return this._balance;
  }
}

const t = new Terminal("TNG-0042", 100);
t.deposit(50);
console.log(t.getBalance());

Nothing forces you to go through deposit() — you could still write t._balance = -999 directly. Encapsulation here is a convention (the underscore, the method that validates), not a hard technical lock — the same underscore-prefix convention you saw on reload's real _provider/_accountCompo fields in Fiuu C# Conventions → Layering.

Inheritance and polymorphism: one call, different behavior

class PaymentMethod {
  process(amount) {
    throw new Error("process() must be implemented by a subclass");
  }
}

class TngPayment extends PaymentMethod {
  process(amount) {
    return `Processed RM${amount} via TNG`;
  }
}

class CardPayment extends PaymentMethod {
  process(amount) {
    return `Processed RM${amount} via Card`;
  }
}

const methods = [new TngPayment(), new CardPayment()];
for (const m of methods) {
  console.log(m.process(25));
}

Inheritance: both classes extend PaymentMethod, inheriting its shape. Polymorphism: the loop calls m.process(25) identically for both objects, but each runs its own version — the caller doesn't need to know or care which concrete class it's holding.

Abstraction: expose what, hide how

You've already seen this formally: ITerminalService in C# Fundamentals → Classes, Objects & Interfaces is pure abstraction — it declares what Login does (takes a terminal id, returns a bool) without exposing how TerminalService implements it. The caller depends only on the abstraction.
