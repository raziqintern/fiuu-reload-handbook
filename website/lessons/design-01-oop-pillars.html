Example: encapsulation — hide the internals, expose a controlled surface

public class Terminal
{
    private string _id;
    private double _balance; // leading underscore: "internal, don't touch directly"

    public Terminal(string id, double balance)
    {
        _id = id;
        _balance = balance;
    }

    public void Deposit(double amount)
    {
        if (amount <= 0) throw new Exception("Deposit must be positive");
        _balance += amount;
    }

    public double GetBalance()
    {
        return _balance;
    }
}

class Program
{
    static void Main()
    {
        Terminal t = new Terminal("TNG-0042", 100);
        t.Deposit(50);
        Console.WriteLine(t.GetBalance());
    }
}

Public Class Terminal
    Private _id As String
    Private _balance As Double ' leading underscore: "internal, don't touch directly"

    Public Sub New(id As String, balance As Double)
        _id = id
        _balance = balance
    End Sub

    Public Sub Deposit(amount As Double)
        If amount <= 0 Then Throw New Exception("Deposit must be positive")
        _balance += amount
    End Sub

    Public Function GetBalance() As Double
        Return _balance
    End Function
End Class

Module Program
    Sub Main()
        Dim t As New Terminal("TNG-0042", 100)
        t.Deposit(50)
        Console.WriteLine(t.GetBalance())
    End Sub
End Module

Nothing technically forces callers through Deposit() in either language — private only blocks access from outside the class, and within it the field is freely mutable. Encapsulation here means bundling the data with the one method that's allowed to safely change it, matching the underscore-prefix convention you saw on reload's real _provider/_accountCompo fields in Fiuu C# Conventions → Layering.

Example: inheritance, polymorphism, and real abstraction

public abstract class PaymentMethod
{
    public abstract string Process(double amount);
}

public class TngPayment : PaymentMethod
{
    public override string Process(double amount)
    {
        return $"Processed RM{amount} via TNG";
    }
}

public class CardPayment : PaymentMethod
{
    public override string Process(double amount)
    {
        return $"Processed RM{amount} via Card";
    }
}

class Program
{
    static void Main()
    {
        PaymentMethod[] methods = { new TngPayment(), new CardPayment() };
        foreach (PaymentMethod m in methods)
        {
            Console.WriteLine(m.Process(25));
        }
    }
}

Public MustInherit Class PaymentMethod
    Public MustOverride Function Process(amount As Double) As String
End Class

Public Class TngPayment
    Inherits PaymentMethod
    Public Overrides Function Process(amount As Double) As String
        Return $"Processed RM{amount} via TNG"
    End Function
End Class

Public Class CardPayment
    Inherits PaymentMethod
    Public Overrides Function Process(amount As Double) As String
        Return $"Processed RM{amount} via Card"
    End Function
End Class

Module Program
    Sub Main()
        Dim methods() As PaymentMethod = {New TngPayment(), New CardPayment()}
        For Each m As PaymentMethod In methods
            Console.WriteLine(m.Process(25))
        Next
    End Sub
End Module

Inheritance: both classes : PaymentMethod / Inherits PaymentMethod, inheriting its shape. Polymorphism: the loop calls m.Process(25) identically for both objects, but each runs its own version — the caller doesn't need to know or care which concrete class it's holding. Abstraction: abstract/MustInherit means PaymentMethod itself can never be instantiated directly (new PaymentMethod() is a compile error) — it exists purely to declare the contract every payment method must fulfil, exactly like ITerminalService in C# Fundamentals → Classes, Objects & Interfaces.

Best practice

Prefer an interface (ITerminalService-style) when unrelated classes need to share a contract with no shared implementation; prefer an abstract base class (like PaymentMethod above) when they also share some real, reusable logic. Reload uses interfaces for its Service layer contracts and — in InComm specifically — an abstract Template Method base for shared protocol logic (see Design Patterns reload Actually Uses).
