Graphs & Traversal

Drop the "exactly one parent" rule from a tree and you get a graph — nodes and connections where more than one path can lead to the same place. You've already seen a real one, drawn on this site.

The shape: nodes and edges, paths can converge

A graph is a set of nodes and a set of edges connecting them. Unlike a tree, a node can be reached from more than one other node, and cycles are allowed. That "more than one path leads here" property is exactly what makes graph traversal need one extra piece of bookkeeping a tree traversal doesn't: a record of what's already been visited.

You'll see this exact shape again later The reload_db data-flow diagram in Architecture Map → reload_db — TRANSACTION routing to TNG/BILL_PAYMENT/TICKET, all of which reference CEPP — is a real graph, not a tree. CEPP is reachable from every one of those databases; it has multiple incoming edges. That's precisely the shape a tree structurally cannot represent.

Example: Breadth-First Search (BFS)

BFS explores a graph one "layer" out at a time, using a queue — visit a node, then all of its direct neighbors, then all of their unvisited neighbors, and so on.

static Dictionary<string, List<string>> graph = new Dictionary<string, List<string>>
{
    ["TRANSACTION"] = new List<string> { "TNG", "BILL_PAYMENT", "CEPP" },
    ["TNG"] = new List<string> { "CEPP" },
    ["BILL_PAYMENT"] = new List<string> { "CEPP" },
    ["CEPP"] = new List<string>()
};

static List<string> BreadthFirstSearch(string start)
{
    var visited = new HashSet<string>();
    var queue = new Queue<string>();
    var order = new List<string>();

    queue.Enqueue(start);
    visited.Add(start);

    while (queue.Count > 0)
    {
        string current = queue.Dequeue();
        order.Add(current);
        foreach (string neighbor in graph[current])
        {
            if (!visited.Contains(neighbor))
            {
                visited.Add(neighbor);
                queue.Enqueue(neighbor);
            }
        }
    }
    return order;
}

static void Main()
{
    Console.WriteLine(string.Join(" -> ", BreadthFirstSearch("TRANSACTION")));
}
TRANSACTION -> TNG -> BILL_PAYMENT -> CEPP
Dim graph As New Dictionary(Of String, List(Of String)) From {
    {"TRANSACTION", New List(Of String) From {"TNG", "BILL_PAYMENT", "CEPP"}},
    {"TNG", New List(Of String) From {"CEPP"}},
    {"BILL_PAYMENT", New List(Of String) From {"CEPP"}},
    {"CEPP", New List(Of String)()}
}

Function BreadthFirstSearch(start As String) As List(Of String)
    Dim visited As New HashSet(Of String)()
    Dim queue As New Queue(Of String)()
    Dim order As New List(Of String)()

    queue.Enqueue(start)
    visited.Add(start)

    While queue.Count > 0
        Dim current As String = queue.Dequeue()
        order.Add(current)
        For Each neighbor As String In graph(current)
            If Not visited.Contains(neighbor) Then
                visited.Add(neighbor)
                queue.Enqueue(neighbor)
            End If
        Next
    End While
    Return order
End Function

Sub Main()
    Console.WriteLine(String.Join(" -> ", BreadthFirstSearch("TRANSACTION")))
End Sub
TRANSACTION -> TNG -> BILL_PAYMENT -> CEPP

Trace the visited set by hand: CEPP is a neighbor of three different nodes (TRANSACTION, TNG, BILL_PAYMENT), but it only appears once in the output — the first time it's discovered, it's marked visited, and every later attempt to re-queue it is skipped. Remove the visited check entirely and this exact graph would queue CEPP three times over (and on a graph with actual cycles, it would loop forever) — the check isn't optional bookkeeping, it's what makes graph traversal terminate correctly at all.

Official documentation This visited-check is only cheap because of what HashSet<T> specifically guarantees: Microsoft's HashSet<T>.Contains reference states plainly in its Remarks: "This method is an O(1) operation." That's exactly why visited is a HashSet<string> and not a List<string> here — checking membership in a list would be an O(n) scan on every single node visited, from Arrays & Time Complexity, turning an already-necessary check into an accidental performance problem too.

BFS vs. DFS

Breadth-First SearchDepth-First Search
Structure usedQueue (FIFO)Stack (LIFO), or plain recursion
ExploresLayer by layer, outwardAs deep as possible down one path before backtracking
Good forShortest path in an unweighted graph"Does any path exist," exhaustive exploration, simpler code

Best practice

  • Always track visited nodes in a graph traversal. Unlike a tree, a graph can have cycles, and skipping this check risks an infinite loop, not just repeated work.
  • Use a HashSet<T> for the visited set, never a List<T>. The whole point of the check is a fast O(1) membership test — a list's O(n) .Contains would silently turn an efficient traversal into a quadratic one.
  • Reach for BFS specifically when you need the shortest path in an unweighted graph. DFS will find a path, not necessarily the shortest one.

Better ways

The graph above is small enough to write by hand as a Dictionary<string, List<string>> (an adjacency list). For a graph with weighted edges (e.g. "this route costs 3 hops, this one costs 1"), plain BFS no longer guarantees the cheapest path — that's what Dijkstra's algorithm exists for, a natural next step once BFS/DFS feel comfortable.

Check your understanding

In the BFS example above, why does CEPP appear only once in the output despite being a neighbor of three different nodes?

  • Dictionary keys are automatically deduplicated by the language.
  • The visited set ensures each node is only ever enqueued the first time it's discovered, regardless of how many other nodes point to it.
  • CEPP only actually has one real connection; the others are duplicates in the graph definition.

The BFS example uses HashSet<string> visited instead of List<string> visited. Both would work correctly — why is HashSet the better choice?

  • A List<T> can't hold more than a fixed number of items.
  • Checking membership (.Contains) is a documented O(1) operation on HashSet<T>, versus an O(n) scan on a List<T> — and this check runs on every node the traversal touches.
  • A HashSet<T> preserves insertion order, which a List<T> doesn't.
