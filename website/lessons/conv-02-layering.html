Layering: Provider / Service / Model

This is the single most important mental model for reading reload's C# code. Full source: conventions/layering-and-architecture.md.

The shape, repeated per module

Each business module (Reloads/TNG, Secure/Astro, ...) repeats the same three-layer split:

LayerResponsibilityExample
ModelPlain DTO/POCO, no behaviorReloads/TNG/Models/Account.cs
ProviderData access only — talks to SQL via stored proceduresReloads/TNG/Providers/TerminalProvider.cs
ServiceBusiness logic, implements I<Name>Service, orchestrates Providers + other ServicesReloads/TNG/Services/TerminalService.cs

Providers are new'd up directly; Services are resolved via a locator

public class TerminalService : ITerminalService
{
    private TerminalProvider _provider;
    private TerminalProvider Provider
    {
        get { return _provider ?? (_provider = new TerminalProvider()); }
    }

    private IAccountService _accountCompo;
    private IAccountService AccountCompo
    {
        get { return _accountCompo ?? (_accountCompo = EngineContext.Current.Resolve<IAccountService>()); }
    }

reload/class-library/Reloads/TNG/Services/TerminalService.cs:8-26

Two things to notice, because they're both consistent rules, not accidents:

  • The Provider is created directly with new — no dependency injection for that layer. Every Service sampled does this.
  • Cross-Service dependencies go through a service locator (EngineContext.Current.Resolve<T>), lazily, via this exact _field ?? (_field = ...) idiom — not constructor injection. This pattern recurs in every Service that depends on another Service (19 files reference it across class-library).
If you're used to constructor injection, this will look wrong — it isn't a bug Modern .NET tutorials teach constructor injection almost exclusively. This codebase deliberately (if implicitly) uses the lazy-property service-locator pattern instead. Don't "fix" it to constructor injection in a PR unless that's the actual scope of the change — it's a working, consistent, if dated, pattern across the whole estate.

No repository/unit-of-work abstraction, no ORM

There's no generic IRepository<T>, no Entity Framework DbContext, and no transaction spanning multiple Provider calls. Each Provider method opens a connection, executes exactly one stored procedure, and returns. If a real operation needs multiple writes to stay consistent, that atomicity is expected to live inside the stored procedure itself — not orchestrated in C#.

Inheritance/template-method for variabilityOnly in InComm (protocol-heavy, ISO 8583); other modules use flat Services
Practical takeaway When you open a module you haven't seen before, look for the Model/Provider/Service split first — it'll almost certainly be there. Don't assume anything else (base classes, DI style, inheritance) is shared with the last module you read; check that module's own conventions before copying a pattern across module boundaries.

Best practice — for working inside this specific codebase

  • When adding a new Service in an existing module, follow that module's existing pattern for cross-Service dependencies (the lazy-resolve property shown above) rather than introducing constructor injection — a mixed style in one module is more confusing than either style used consistently.
  • New Providers should be new'd up directly from their owning Service, matching every sampled example — don't route Provider creation through the DI container just because Services already use one.

Better ways

If you're building something genuinely new rather than extending an existing module, constructor injection is the more testable, more modern pattern the wider .NET ecosystem has moved toward — it makes a class's dependencies visible in one place (its constructor signature) instead of hidden inside lazy-resolve properties scattered through the class body. Just don't retrofit it onto existing, working modules as an unscoped "improvement."
