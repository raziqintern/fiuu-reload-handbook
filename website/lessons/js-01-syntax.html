Variables & Syntax

JavaScript is what runs inside the browser tab, separate from anything C# is doing on the server. Every "Try it Yourself" box on this site is itself a small JavaScript program — this is a good moment to actually understand how they work.

Declaring variables

Modern JavaScript has three ways to declare a variable. Use let by default, const when the value never gets reassigned, and avoid var (an older, quirkier version kept only for backwards compatibility).

let amount = 25.5;
const currency = "MYR";
let isConfirmed = false;

console.log(amount, currency, isConfirmed);

amount = amount + 10;
console.log("New amount:", amount);
Official documentation MDN's let reference names the concrete difference from var: "Compared with var, let declarations have the following differences: let declarations are scoped to blocks as well as functions." Its own example shows exactly what that means in practice — a variable re-declared inside a nested block with var silently overwrites the outer one; the same code with let keeps them genuinely separate. MDN also states the reasoning behind preferring const specifically: "Many style guides... recommend using const over let whenever a variable is not reassigned in its scope. This makes the intent clear that a variable's type... can never change."
Real, verified: var is still genuinely present in production reload code var downloadTimer;, var cookieName = "DownloadChecker";, and three more var declarations sit in the same script block on a real BackOffice page — a concrete reminder that "avoid var" is guidance for code you write today, not a claim that it's extinct in this codebase. Older inline <script> blocks predate the let/const convention and were never retrofitted.

What "block-scoped" actually changes, side by side — the exact same shape of code, only the keyword different:

function varTest() {
  var x = 1;
  {
    var x = 2; // same variable — this overwrites the outer one
    console.log(x); // 2
  }
  console.log(x); // 2 — the outer x was silently changed
}

function letTest() {
  let x = 1;
  {
    let x = 2; // a genuinely different variable, scoped to this block
    console.log(x); // 2
  }
  console.log(x); // 1 — the outer x was never touched
}

varTest();
letTest();

With var, the inner declaration isn't a new variable at all — it's the same one, reused, because var only respects function boundaries, not { } blocks. With let, the inner x is a distinct variable that happens to share a name; once its block ends, the outer x is exactly as it was. This is the real, structural reason var can silently corrupt a variable a few lines away that looks completely unrelated at a glance.

Official documentation MDN's JavaScript data types guide names this behavior directly, not as an edge case: "JavaScript is also a weakly typed language, which means it allows implicit type conversion when an operation involves mismatched types, instead of throwing type errors." It also names exactly why this matters in practice: "Implicit coercions are very convenient, but can create subtle bugs when conversions happen where they are not expected, or where they are expected to happen in the other direction (for example, string to number instead of number to string)." — precisely the form field scenario below.
The trap that catches everyone once JavaScript will happily let you add a number and a string — and it won't throw, it'll silently convert. 5 + "5" is "55" (a string), not 10. This "helpful" coercion is a real source of bugs when data arrives from a form field (always a string) and you forget to convert it with Number(...) first.

console.log(Number(quantity) + price); // now it's real addition

console.log(typeof quantity);
console.log(typeof price);

Best practice

  • Default to const; switch to let only when you actually need to reassign. A codebase full of const tells a reader at a glance which values never change.
  • Convert data from an external source (a form field, an API response) to its real type explicitly and immediately, right where it enters your code. Don't let a "string that's secretly always a number" drift through several functions before something finally breaks on it.
  • Never introduce a new var in code you're writing today, even inside a file that already has some. Match the surrounding file's other conventions, but a brand-new declaration is a place where let/const costs nothing and avoids the exact function-vs-block scoping trap shown above.

Better ways

Number(quantity) is one of several conversion options and it's a reasonable default, but it silently returns NaN for genuinely invalid input rather than telling you something's wrong. For code that must actively reject bad input rather than quietly limp along with NaN, check isNaN(...) (or validate the string's shape) before trusting the converted value.
