Git Archaeology: What Blame Can't Tell You

Two real investigations into "why does this line exist" and "is it safe to reset this pointer" — and where each one ran into a limit that isn't about knowing the right git command, but about knowing when a command's answer isn't the real answer.

The question: why does this line exist?

A page disabled a dropdown after a search ran, with no comment explaining why. Before assuming it was a bug worth removing, the reasonable move is to find out whether it was ever a deliberate requirement — and git log -S"the exact line" (or git blame) is the standard way to find the commit that introduced a specific piece of code.

git log -S"ddlStockType.Enabled = False" -- path/to/StockAllocationEdit.aspx.vb
The trail led to a bulk rename, not the real origin The commit that came back had the message "[SIT] {Reload} GIT#1770" — but reading that ticket showed it was a project-wide namespace consolidation ("rename MOL.App.CEPP.BackOffice.Web to Fiuu.App.BackOffice.Web"), not a change to this page's search behavior at all. The whole file had been reintroduced wholesale as part of that rename/move — which is exactly the kind of commit git log -S and blame will surface as "the" origin, because as far as git's line history is concerned, that's the most recent commit that touched this exact line at this exact path. The actual original authorship, from whenever the file lived under its old namespace, doesn't reliably carry across a wholesale move like that.

This is a known, structural limit of line-level history, not a mistake in how the command was used: a rename/move (especially one bundled into a large, unrelated commit) can sever the trail a tool like blame or log -S walks, even when --follow/rename-detection is in play. The tool isn't wrong — it's answering "what commit last touched this line at this path," which isn't always the same question as "who decided this behavior should exist, and why."

Knowing when to stop guessing and ask a person Once the trail dead-ends at a commit that's provably about something else (a rename, a bulk formatting pass, a dependency bump), further git archaeology on the same line is unlikely to produce a real answer. That's the point to say so plainly — "I can't find a documented reason this exists; it's worth asking someone who's worked on this page before" — rather than presenting a guess with the same confidence as a verified fact.

The question: is it safe to reset this pointer?

A second, unrelated situation: a working branch carried a class-library submodule reference pointing at commit 0bbe934f. The target environment's current reference pointed at a different commit, 60e7c19, dated four days later. The tempting move — since the environment's commit looked newer — was to leave it alone; a more dangerous one would have been to "fix" a perceived mismatch by resetting the environment's pointer back to the branch's own value.

git merge-base --is-ancestor 0bbe934f 60e7c19 && echo "ancestor" || echo "diverged"
Newer isn't the same as "descended from" Checking ancestry directly showed the two commits had diverged from a common point — neither was an ancestor of the other. The branch's own reference wasn't even about the same change: it turned out to be a different ticket's class-library revision, carried along incidentally from an earlier merge, not anything the branch's own work had introduced. Resetting the environment's pointer to that value would have moved it backward relative to unrelated fixes that had landed there in the meantime — a real regression a passing build would never catch, since a successful build only proves the referenced API surface still compiles, not that other tickets' changes are still present.

The generalizable move: before resetting or aligning any shared reference — a submodule commit, a deployment tag, any pointer more than one team's changes flow through — check ancestry (git merge-base, or git log --graph across both refs) rather than comparing dates or assuming "the one my change needs" is safe to force onto a shared target. Two histories that look related can have quietly diverged, and a confident-looking reset can be the more dangerous action, not the safe default.

Best practice

  • git log -S/blame answer "what commit last touched this exact line at this exact path" — not "who decided this behavior, and why." When the answer is a rename, reorg, or other bulk commit, treat that as a dead end, not a citation, and say so rather than guessing further.
  • Before resetting any shared pointer (a submodule reference, a promoted branch, a deploy tag) to match what your own change needs, confirm the two values are actually ancestor/descendant of each other with git merge-base --is-ancestor — "looks newer" and "is a descendant" are not the same claim, and only one of them is safe to act on.

Check your understanding

git log -S"some line" on a suspicious piece of code returns a commit whose message is a large, unrelated refactor ("standardize project namespaces across the solution"). What should you conclude?

  • The commit is very likely just where the file got relocated/rewritten wholesale — it's probably not when this specific behavior was actually decided, and the trail likely can't be followed further back reliably.
  • The behavior was definitely introduced specifically for that refactor ticket, since that's what git says.
  • This means git blame/log -S is broken and shouldn't be trusted for this file going forward.
