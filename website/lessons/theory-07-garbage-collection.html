Garbage Collection & Object Lifetime

This is the lesson that explains the real reload incident (issue #2592) introduced in the previous lesson — and the one piece of theory that would have caught it before it shipped. It gets a full worked-example treatment later in Debugging Reload.

What the GC actually does

In C/C++, you manually free memory you allocated. In .NET, the garbage collector does this for you: it periodically scans for heap objects nothing references anymore, and reclaims their memory automatically. This is why you don't call delete or free() in C#/VB.NET — and it's genuinely one of the biggest sources of memory bugs in unmanaged languages that .NET mostly eliminates.

Official documentation Microsoft's Cleaning up unmanaged resources guide states the limit precisely: "Although the garbage collector is able to track the lifetime of an object that encapsulates an unmanaged resource, it doesn't know how to release and clean up the unmanaged resource." It can tell the wrapper object is unreachable and reclaim that memory — it has no idea the object was also holding a file handle, socket, or crypto key that needs its own separate release step.
The critical limit: the GC only knows about .NET memory The garbage collector manages managed memory — objects on the .NET heap. It has no idea about, and cannot clean up, unmanaged resources: an open file handle, a network socket, a database connection, a cryptographic key handle from the OS. If your object holds one of those and you don't explicitly release it, the GC eventually collecting the wrapper object does not mean the underlying OS resource gets released at the same time — sometimes not for a long while, sometimes not correctly at all.
What if you skip Dispose and rely on a finalizer instead? Non-deterministic, and that's the whole problem The same reference names the fallback mechanism and its real cost: "Define a finalizer. Finalization enables the non-deterministic release of unmanaged resources when the consumer of a type fails to call IDisposable.Dispose." A finalizer isn't a substitute for calling Dispose — it's a safety net for when someone forgets to, and it runs on the GC's own schedule, not the moment the resource is actually done being used. This is exactly the shape of the real TNG incident: the handle would eventually be released by a finalizer, "eventually" being however long the object happened to survive before a GC pass reached it — nowhere near fast enough once handles were piling up faster than that.

This is exactly what caused a real reload incident

Issue #2592, one more time Every TNG reload transaction opened a .pfx certificate file and RSA-decrypted a session key from scratch, and never released the handle — the full investigation is a worked example later in Debugging Reload → Worked Example: Tracing a Bug. This is precisely the gap above: the GC would eventually collect the .NET wrapper object around that handle, but the underlying OS-level crypto handle isn't guaranteed to be released promptly just because the GC ran — and Windows serializes access to crypto key material, so as unreleased handles piled up, every new lookup got slower. The garbage collector was never going to save this code — it wasn't designed to.

The real fix: IDisposable and using

For exactly this class of resource, .NET has a deterministic cleanup mechanism separate from the GC: implement IDisposable, and wrap usage in a using block (C#) / Using block (VB.NET) that guarantees Dispose() runs the moment you're done with it — immediately, not "whenever the GC gets around to it."

class ConnectionHandle : IDisposable
{
    public ConnectionHandle() { Console.WriteLine("Handle opened"); }
    public void Dispose() { Console.WriteLine("Handle released"); }
}

static void Main()
{
    using (var handle = new ConnectionHandle())
    {
        Console.WriteLine("Using the handle...");
    } // Dispose() runs automatically here, even if an exception is thrown above
    Console.WriteLine("Done.");
}

Had the TNG certificate-handling code wrapped its handle in a using block like this, the handle would have been released the moment each transaction finished with it — no pileup, no incident.

Best practice

  • Anything that opens a file, network connection, database connection, or OS-level handle should implement IDisposable and always be used inside a using block. Never rely on the GC for these.
  • When reviewing code that opens such a resource, check for the matching release as carefully as you'd check for a missing null check. It's the same class of "easy to miss, expensive when missed" bug.
  • Never treat a finalizer as an acceptable substitute for calling Dispose promptly. A finalizer is a documented safety net for when someone forgets — its release timing is non-deterministic and tied to the GC's own schedule, not to when the resource actually stopped being needed.

Check your understanding

Why didn't the .NET garbage collector prevent the real TNG certificate-handle leak incident?

  • The garbage collector was running too infrequently in that environment.
  • The GC only manages .NET-managed memory — it doesn't know about or promptly release unmanaged OS-level resources like a crypto key handle.
  • The code needed to call the garbage collector manually.

A class holding a file handle defines a finalizer as its only cleanup mechanism — it never implements IDisposable/Dispose. Is the file handle eventually released?

  • No, never — a finalizer with no Dispose call never actually runs.
  • Yes, eventually — but only whenever the GC happens to run a collection that reaches this object, which could be much later than when the resource was actually done being used.
  • It's a compile error — a class can't define a finalizer without also implementing IDisposable.
