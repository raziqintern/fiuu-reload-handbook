Garbage Collection & Object Lifetime

This is the lesson that explains the real reload incident referenced twice already on this site — and the one piece of theory that would have caught it before it shipped.

What the GC actually does

In C/C++, you manually free memory you allocated. In .NET, the garbage collector does this for you: it periodically scans for heap objects nothing references anymore, and reclaims their memory automatically. This is why you don't call delete or free() in C#/VB.NET — and it's genuinely one of the biggest sources of memory bugs in unmanaged languages that .NET mostly eliminates.

The critical limit: the GC only knows about .NET memory The garbage collector manages managed memory — objects on the .NET heap. It has no idea about, and cannot clean up, unmanaged resources: an open file handle, a network socket, a database connection, a cryptographic key handle from the OS. If your object holds one of those and you don't explicitly release it, the GC eventually collecting the wrapper object does not mean the underlying OS resource gets released at the same time — sometimes not for a long while, sometimes not correctly at all.

This is exactly what caused a real reload incident

Issue #2592, revisited Every TNG reload transaction opened a .pfx certificate file and RSA-decrypted a session key from scratch, and never released the handle (Debugging Reload → Worked Example: Tracing a Bug). This is precisely the gap above: the GC would eventually collect the .NET wrapper object around that handle, but the underlying OS-level crypto handle isn't guaranteed to be released promptly just because the GC ran — and Windows serializes access to crypto key material, so as unreleased handles piled up, every new lookup got slower. The garbage collector was never going to save this code — it wasn't designed to.

The real fix: IDisposable and using

For exactly this class of resource, .NET has a deterministic cleanup mechanism separate from the GC: implement IDisposable, and wrap usage in a using block (C#) / Using block (VB.NET) that guarantees Dispose() runs the moment you're done with it — immediately, not "whenever the GC gets around to it."

class ConnectionHandle : IDisposable
{
    public ConnectionHandle() { Console.WriteLine("Handle opened"); }
    public void Dispose() { Console.WriteLine("Handle released"); }
}

static void Main()
{
    using (var handle = new ConnectionHandle())
    {
        Console.WriteLine("Using the handle...");
    } // Dispose() runs automatically here, even if an exception is thrown above
    Console.WriteLine("Done.");
}

Had the TNG certificate-handling code wrapped its handle in a using block like this, the handle would have been released the moment each transaction finished with it — no pileup, no incident.

Best practice

  • Anything that opens a file, network connection, database connection, or OS-level handle should implement IDisposable and always be used inside a using block — never rely on the GC for these.
  • When reviewing code that opens such a resource, check for the matching release as carefully as you'd check for a missing null check — it's the same class of "easy to miss, expensive when missed" bug.

Why didn't the .NET garbage collector prevent the real TNG certificate-handle leak incident?

  • The garbage collector was running too infrequently in that environment.
  • The GC only manages .NET-managed memory — it doesn't know about or promptly release unmanaged OS-level resources like a crypto key handle.
  • The code needed to call the garbage collector manually.
